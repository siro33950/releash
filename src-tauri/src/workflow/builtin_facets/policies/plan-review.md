## Specレビューポリシー

- 明確な判定を提示する: LGTM（問題なし）または NEEDS_FIX（問題あり）
- 各問題について、問題の説明と具体的な記述例を提案する
- 重大な問題と軽微な提案を区別する
- 実装方法（how）には踏み込まない。「何を」「なぜ」の記述のみを評価する
- 各シナリオが観測可能な振る舞いとして検証可能か確認する。検証手段のない要件はNEEDS_FIXとする
- 複数の解釈が可能な曖昧な表現を検出する
- 境界値・空入力・タイムアウト等の技術的エッジケースは振る舞い定義のスコープ外（ユニット/統合テストの責務）であり、Specレビューでは指摘しない
- ビジネスルール違反シナリオ（ドメインルールに基づく拒否・制御）の欠落のみを指摘する
- Spec 3文書（requirements.md / behavior.md / design.md）の内容品質と整合性を確認する。既存コードベースとの整合性（依存関係、型、モジュール構成、API設計、パターン）は implementation review の責務であり、ここでは扱わない
- design.md は実装に進める設計境界として十分かを評価する。存在確認だけで合格させない。一方で詳細な実装手順・関数名・型シグネチャの不足は指摘しない
- セキュリティ観点では「何を/なぜ」のレベル（認可要件・機密データ方針・信頼境界）のみを評価する。具体的な対策手段（サニタイズ・エスケープ・暗号アルゴリズム等）はコードレビューの責務
