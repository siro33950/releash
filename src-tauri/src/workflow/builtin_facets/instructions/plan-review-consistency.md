{{project_name}} プロジェクトのSpecドキュメント内部の整合性をレビューする。

## 入力

Specファイル（パスはステップ出力で提供）を読み込む。

## 検証項目

Specの「要求 / 振る舞い定義 / アーキテクチャ概要」3セクション間の整合性のみを確認する。実装・コード・既存パターンとの整合性はコードレビューの責務であり、ここでは扱わない。

### 1. ドメイン用語の一貫性

- 同一概念に同一の用語が使われているか
- 要求で導入された概念が振る舞い定義・アーキテクチャ概要で別名にすり替わっていないか

### 2. 要求と振る舞いの整合

- 要求にあるが振る舞い定義に対応Scenarioがない項目がないか
- 振る舞い定義に要求にない振る舞いが紛れていないか

### 3. 振る舞いとアーキテクチャ概要の整合

- 振る舞い定義に登場する状態・操作・データに対応する責務配置・状態Ownerが書かれているか
- アーキテクチャ概要の責務配置で振る舞いの実現が可能か（地図レベルで矛盾していないか）

## フラグしない

- 既存コードのパターンや依存関係との整合性（コードレビューの責務）
- レイヤー責務違反の検出（実装段階で確認）
- API・インターフェース設計の妥当性
- エラーハンドリング方針の細部
- 既存の技術的負債への言及
- アーキテクチャの全面的な見直し提案

## 判定

- **LGTM**: 要求・振る舞い・アーキテクチャ概要の3セクション間で用語・対応関係に矛盾なし
- **NEEDS_FIX**: 用語の不一致、要求と振る舞いの対応漏れ、振る舞いと責務配置の不整合あり

## 構造化出力の提出

判定（`review-verdict` Contract に従う JSON）は、step 完了時に `releash workflow output submit` で engine に提出する。

```sh
releash workflow output submit <run_id> \
  --step <step_name> \
  --type review-verdict \
  --json '{"verdict":"LGTM"}'   # または NEEDS_FIX の場合は findings を含める
```

提出が成功するまで step は完了として扱われない。失敗時は `releash workflow output validate` でフォーマットを確認してから再提出する。
