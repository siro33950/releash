## 前提

Specファイル（ステップ出力で提供）を読み込み、`## 振る舞い定義` セクションが存在することを確認する。

## アーキテクチャ概要の目的

振る舞い定義を実現するための「実装の地図」を作成する。詳細な実装手順ではなく、責務の配置と境界を明確にすることで、実装時の判断基盤を提供する。

## 整理すべきセクション

以下の5セクションで構成する:

1. **責務配置**（必須）: 各領域（モジュール/レイヤー）が担当すること・担当しないことを整理する
2. **データ/通信フロー**（必須）: 主要な操作のデータフローを短く示す（例: UI → Tauri command → Rust service → storage → event）
3. **状態Owner**（必須）: 各状態のOwner（どのレイヤー/モジュールが管理するか）を明示する
4. **境界**（必須）: 各層が守るべき責務の境界を示す
5. **実装に委ねること**（必須）: 実装中に判断してよい項目を明示する（helper関数名、内部データ変換、細かいコンポーネント分割、テストケースの具体的配置等）

## 書かないこと

- 実装順序の指定
- 関数内の処理手順
- 疑似コード
- 詳細な型定義やシグネチャ
- テストケースの具体的な内容

## Specファイル更新

Specファイルの `## アーキテクチャ概要` セクションを追加または更新する:

```markdown
## アーキテクチャ概要

### 責務配置
- [領域名]: [担当すること] / [担当しないこと]

### データ/通信フロー
- [操作名]: [フローの概要]

### 状態Owner
- [状態名]: [Owner]

### 境界
- [境界の説明]

### 実装に委ねること
- [実装時に判断してよい項目]
```

## 出力

Specファイル更新後、`spec-file-path` Contract に従う JSON を `releash workflow output submit` で提出する。

```sh
releash workflow output submit <run_id> \
  --step <step_name> \
  --type spec-file-path \
  --json '{"spec_file_path":"docs/spec/issues-XXX.md"}'
```

提出が成功するまで step は完了として扱われない。失敗時は `releash workflow output validate` でフォーマットを確認してから再提出する。
