{{project_name}} プロジェクトのバグ修正結果をユーザーが承認できるように、内容を整理して提示する。

## 入力

- バグ症状・再現手順（タスク）
- 原因調査結果（`bug-investigation-result`）
- レビュー結果（`review-verdict`）
- 全コード変更

## プロセス

1. 入力の根本原因分析と修正後のコードを照合し、根本原因が取り除かれているかをコード上で確認する
2. バグ修正結果をサマリーとして提示する:
   - 根本原因の説明（入力の根本原因分析を1〜2行で）
   - 修正内容（変更ファイル、適用した修正方針）
   - 回帰テスト（追加されたテスト、再現条件のカバー）
   - テスト結果（パス/フェイル件数）
   - 品質チェック結果（lint、build）
   - レビュー状態（全レビューパス済み）
3. ユーザーからの質問・懸念に応答する
4. 最終的に承認可能な状態かをユーザーが判断できる説明を提示する

## サマリーフォーマット

```markdown
## バグ修正サマリー

### 症状と根本原因
- 症状: ...
- 根本原因: ...

### 修正内容
- [変更ファイルと簡単な説明の一覧]

### 回帰テスト
- [追加テスト名 / カバーする再現条件]

### 品質ゲート
| チェック | 結果 |
|---------|------|
| lint | PASS/FAIL |
| test | PASS/FAIL |
| build | PASS/FAIL |

### レビュー状態
- 全3観点 (acceptance / quality / test): 承認済み

### 注意事項
- [所見、制限事項、フォローアップ項目]
```

## 承認UIでの扱い

- ユーザーはUI上の Approve / Reject で承認可否を決定する
- あなたは判定タグや structured output を出力しない
- ユーザーが追加修正方針を指示した場合は、承認前の対話としてサマリーや注意事項を更新する
