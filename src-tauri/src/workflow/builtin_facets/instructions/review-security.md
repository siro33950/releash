{{project_name}} プロジェクトのコード変更をセキュリティの観点でレビューする。

## 入力

- `spec-directory` Contract で渡される `spec_dir` の Spec 3文書
- 実装ステップからのコード変更

## ファクトチェック義務

推測で指摘しない。報告前に必ず実コードを読んで検証する。

## スコープルール

| スコープ | 説明 | FAIL対象 |
|---------|------|---------|
| scope:diff | 今回の変更で導入された問題 | はい |
| scope:touched | 変更ファイル内の既存問題 | 報告のみ |
| scope:external | 変更対象外の問題 | 報告しない |

## 検証手順（OWASP Top 10レベル）

Spec は文脈として参照するが、レビュー範囲を Spec 充足だけに狭めない。Spec に明記されていない実コード上の脆弱性も NEEDS_FIX とする。

### 1. インジェクション

- SQLインジェクション: ユーザー入力がSQLクエリに直接結合されていないか
- コマンドインジェクション: ユーザー入力がシェルコマンドに渡されていないか
- XSS: ユーザー入力がHTML/JSにエスケープなしで出力されていないか
- プリペアドステートメント/パラメタライズドクエリの使用を確認する

### 2. 認証・認可

- 全エンドポイント/APIが適切に認証されているか
- リソースアクセスチェックが設置されているか
- バイパス可能な経路がないか

### 3. データ保護

- コード内にハードコードされた認証情報やシークレットがないか
- ログ出力に機密データがないか
- APIレスポンスに機密データがないか

### 4. 入力バリデーション

- 全外部入力が検証されているか
- 型制約と値の範囲が強制されているか
- 必要な箇所にサニタイズが適用されているか

### 5. パストラバーサル

- ユーザー入力がファイルパス構築に使用されていないか
- パストラバーサルパターン（../）がブロックされているか
- パスサニタイズが適用されているか

## 指摘フォーマット

各指摘にはファイル:行、問題の説明、severity（critical/high/medium/low）、修正提案を含める。

## 判定

- **LGTM**: scope:diffにセキュリティ問題なし
- **NEEDS_FIX**: scope:diffにセキュリティ問題あり

## 構造化出力の提出

判定（`review-verdict` Contract に従う JSON）は、step 完了時に `releash workflow output submit` で engine に提出する。

```sh
releash workflow output submit <run_id> \
  --step <step_name> \
  --type review-verdict \
  --json '{"verdict":"LGTM"}'   # または NEEDS_FIX の場合は findings を含める
```

提出が成功するまで step は完了として扱われない。失敗時は `releash workflow output validate` でフォーマットを確認してから再提出する。
