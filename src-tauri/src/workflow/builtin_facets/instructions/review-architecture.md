{{project_name}} プロジェクトのコード変更をアーキテクチャ整合性の観点でレビューする。

## 入力

- `spec-directory` Contract で渡される `spec_dir` から `design.md` を中心に Spec 3文書を読み込む
- 実装ステップからのコード変更
- プロジェクトのアーキテクチャガイドライン（存在する場合）

## ファクトチェック義務

推測で指摘しない。報告前に必ず実コードを読んで検証する。

## スコープルール

| スコープ | 説明 | FAIL対象 |
|---------|------|---------|
| scope:diff | 今回の変更で導入された問題 | はい |
| scope:touched | 変更ファイル内の既存問題 | 報告のみ |
| scope:external | 変更対象外の問題 | 報告しない |

## 担当範囲（観点の一意分配）

本モジュールは **レイヤー間の責務境界とドメインモデルの整合性** を担当する。design.md との整合を見たうえで、既存アーキテクチャ原則に反するコードも指摘する。
類似観点の担当境界を以下に明示する:

| 観点 | 本モジュールの対象 | 他モジュールの担当 |
|------|-------------------|------------------|
| レイヤー責務 | レイヤー間（Domain / Usecase / Infrastructure / Adaptor）の責務境界 | review-structure（関数・クラス・モジュール単位の責務） |
| ユビキタス言語 | ドメイン用語・モデル名・型名の一貫性、外部サービス名・DB名のドメイン漏洩 | review-quality（変数名・関数名等のコーディング命名） |

## 検証手順

### 1. レイヤー責務（レイヤー間の責務境界）

対象: Domain / Usecase / Infrastructure / Adaptor 等のレイヤー間の責務分離

- ビジネスロジックが正しいレイヤーにあるか
- Tauriコマンドがフロントエンド-バックエンド境界として適切に使用されているか
- ドメインロジックがUI/インフラ/コントローラ層に漏洩していないか

※ 関数・クラス・モジュール単位の責務分離は review-structure（責務と凝集度）が担当。

### 2. 依存方向

- import文が内側（ドメインに向かって）を向いているか
- ドメイン層が外部技術から独立を維持しているか
- 新規依存が正当化されているか

### 3. ユビキタス言語（ドメイン用語・モデル名・型名）

対象: ドメイン概念に紐づく命名の整合性

- 外部サービス名やデータベース名がドメインモデル・インターフェース・型名に漏洩していないか
- 同一ドメイン概念に対する命名が一貫しているか（例: User と Account の混在等）
- 新しいドメイン用語が既存のプロジェクト語彙と整合しているか

※ 変数名・関数名・メソッド名等のコーディングレベルの命名一貫性は review-quality（命名の一貫性）が担当。

## 指摘フォーマット

各指摘にはファイル:行、問題の説明、修正提案を含める。

## 判定

- **LGTM**: scope:diffの全アーキテクチャチェックがパス
- **NEEDS_FIX**: scope:diffのいずれかが要改善

## 構造化出力の提出

判定（`review-verdict` Contract に従う JSON）は、step 完了時に `releash workflow output submit` で engine に提出する。

```sh
releash workflow output submit <run_id> \
  --step <step_name> \
  --type review-verdict \
  --json '{"verdict":"LGTM"}'   # または NEEDS_FIX の場合は findings を含める
```

提出が成功するまで step は完了として扱われない。失敗時は `releash workflow output validate` でフォーマットを確認してから再提出する。
