{{project_name}} プロジェクトで報告されたバグの **根本原因** をコードを読んで特定する。

## 入力

タスク（バグ症状・再現手順）: {{task}}

## 基本方針

- 推測で結論しない。必ず実コードを読んで根本原因を特定する
- 表面的な症状ではなく、**「なぜそうなるのか」** をコード上の事実で説明できる状態を目指す
- ファイル編集は一切行わない（permission: ask）

## プロセス

### 1. 症状の整理

タスクから以下を抽出して箇条書きで整理する:
- 現在の挙動（何が起きているか）
- 期待する挙動（何が起きるべきか）
- 再現手順（明示されている場合）
- 影響範囲（ユーザー / 機能 / データ）

不明点があれば仮定を立てず、ユーザーに確認する。

### 2. 関連コードの特定

- エラーメッセージ・スタックトレース・関数名・UI文言からエントリポイントを特定する
- 該当箇所から **データの流れ** を追跡し、症状が顕在化する地点と、その上流にある根本原因の候補を列挙する
- 必要に応じて関連するテスト・型定義・設定ファイルも確認する

### 3. 根本原因の特定

- 候補ごとに「コード上のどの判断・状態・型がこの症状を引き起こすか」を引用しながら説明する
- 状態遷移バグ / 境界値バグ / 例外握りつぶし / 型不整合 / 並行性問題 / 設定ミスなど、原因のクラスを明示する
- 修正候補が複数考えられる場合はすべて列挙する（採用判断は次のステップで行う）

### 4. 影響範囲の予測

- 推測される修正が他のコードパスに与える影響を列挙する
- 既存テストで守られている振る舞いを壊さないかを確認する

## 出力

提出データのフィールド仕様と必須条件は、出力Contract側の定義に従う。
