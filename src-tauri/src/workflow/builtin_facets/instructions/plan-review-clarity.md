{{project_name}} プロジェクトのSpecドキュメントを明確性の観点でレビューする。

## 入力

Specファイルを読み込む（パスはステップ出力で提供）。

## 基本方針

振る舞い定義は **ビジネスルールがどう振る舞うかをアクター視点で抽象表現したもの**。明確性とは「ビジネス意図として一意に解釈可能か」を意味し、テストの判定可能性や実装条件の具体性ではない。

## 検証項目

### 1. ビジネス意図の一意性

- 各 Scenario の Given/When/Then が、ビジネスルールの振る舞いとして一意に解釈できるか
- 主観的・定性的な表現（「適切に」「良い感じに」「必要に応じて」等）が判断基準なく使われていないか
- ドメイン用語の意味が要求セクションと整合しているか

### 2. 実装/テスト汚染の混入チェック（NEEDS_FIX 対象）

Given/When/Then に以下が混入していたら NEEDS_FIX とする。これらは Scenario をテスト受け入れ基準や実装ステップに堕落させ、後続の実装を不必要に縛る。

| カテゴリ | 検出例 | あるべき表現 |
|---|---|---|
| 具体的な入力値・データ | `email="foo@example.com" / 金額 1000` | `有効なメールアドレス / 正の金額` |
| UI操作 | `ボタンをクリック / フォームを送信` | `購入を要求する` |
| API/技術的呼び出し | `POST /signup を呼ぶ / SQL を実行` | `アカウント作成を要求する` |
| DB/技術的状態 | `users テーブルに行が追加される` | `アカウントが作成される` |
| レスポンスコード・画面文言 | `200 が返る / "登録完了" が表示される` | `アカウント作成の完了が本人に伝わる` |
| テスト判定基準 | `expect(...).toBe(...)` 相当の判定式 | （振る舞い定義に書かない） |

### 3. アーキテクチャ概要の着手可能性

- アーキテクチャ概要が振る舞い定義を実装するための「地図」として読めるか
- `[NEEDS CLARIFICATION]` マーカーが残っていないか

詳細な実装手順・関数名・型シグネチャ・処理フローの不足は指摘しない。地図として最低限の方向性が示されていれば良い。

## フラグしない

- 文章のスタイルや表現の好み
- Scenarioの記述順序
- Markdownのフォーマット
- 詳細な実装手順・疑似コード・関数シグネチャの欠如
- 責務配置や境界の記述粒度（実装中に判断可能なレベルの粗さは許容）
- テストケースの不在（振る舞い定義はテスト集ではない）
- テスト可能性そのもの（テストは振る舞い定義ではなくビジネスルールに対して書く）

## 判定

- **LGTM**: 全 Scenario がビジネス意図として一意に解釈可能で、実装/テスト汚染がなく、アーキテクチャ概要が着手可能、`[NEEDS CLARIFICATION]` が残っていない
- **NEEDS_FIX**: ビジネス意図の曖昧さ、実装/テスト汚染の混入、`[NEEDS CLARIFICATION]` の残存、または着手不可能なアーキテクチャ概要のいずれかがある

## 構造化出力の提出

判定（`review-verdict` Contract に従う JSON）は、step 完了時に `releash workflow output submit` で engine に提出する。

```sh
releash workflow output submit <run_id> \
  --step <step_name> \
  --type review-verdict \
  --json '{"verdict":"LGTM"}'   # または NEEDS_FIX の場合は findings を含める
```

提出が成功するまで step は完了として扱われない。失敗時は `releash workflow output validate` でフォーマットを確認してから再提出する。
