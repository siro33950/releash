承認済みSpecに基づいて {{project_name}} プロジェクトのコードを実装する。

## 入力

Specファイル（ステップ出力で提供）を読み込む。以下のセクションを含む:
- `## 要求` — 要求
- `## 振る舞い定義` — ビジネスルールの振る舞い（Gherkin で Feature/Rule/Scenario として表現）
- `## アーキテクチャ概要` — アーキテクチャ概要（責務配置・境界・フロー・状態Owner）

## 基本方針

振る舞い定義は **ビジネスルールの振る舞いをアクター視点で抽象表現したもの**。実装の目的は **ビジネスルール（Rule）が成立するコード** を書くこと。Scenario の Given/When/Then は、ビジネスルールが顕在化する代表的な状況の例示であり、それぞれを「実装ステップ」「テスト受け入れ基準」として逐次充足するためのものではない。

## プロセス

### 1. ビジネスルールの抽出

- 振る舞い定義の全 Rule を列挙する
- 各 Rule について、ビジネスルールの不変条件・状態遷移を文章で把握する
- Scenario は「Rule が顕在化する代表的な状況」として理解の補助に使う（実装制約として扱わない）
- アーキテクチャ概要の責務配置・境界と突き合わせる

### 2. アーキテクチャ概要の活用

アーキテクチャ概要は実装の地図として参照する。ビジネスルールの充足が最優先。
- **責務配置**: 各変更が正しいレイヤー/モジュールに配置されているか確認する
- **境界**: レイヤー間の境界を尊重した実装にする
- **フロー**: データ/通信フローに沿った実装にする
- **状態Owner**: 状態管理が指定されたOwnerに配置されているか確認する

### 3. 実装

各ビジネスルールを充足するコード変更を行う:
1. 対象ファイルと関連ファイルを先に読み込む
2. ビジネスルールが守られるための必要最小限の変更を実施する
3. 各コンポーネント実装後に関連テストを実行する
4. 失敗があれば次に進む前に修正する

### 4. 自己検証

実装完了後、各ビジネスルールがコード上で守られているか検証する:
- 可能な場合はテストを記述する（ビジネスルール単位 — Scenario と1対1である必要はない）
- E2Eレベルの振る舞いはコードマッピング（ビジネスルールに対応するコードパスの特定）で確認する

### 実装ルール

- ビジネスルール（Rule）を充足するコード変更のみ行う
- ビジネスルールが求める以上の機能を追加しない
- Scenario の Given/When/Then を「実装ステップ」として逐次解釈しない（具体的な入力値・UI操作・API呼び出しが Scenario に書かれていても、それはビジネスルールを示すための例示であり、その文言通りに実装する義務はない）
- 変更後にlintとフォーマットを実行する
