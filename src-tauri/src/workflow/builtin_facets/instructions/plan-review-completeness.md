{{project_name}} プロジェクトのSpecドキュメントを完全性の観点でレビューする。

## 入力

Specファイルを読み込む（パスはステップ出力で提供）。

## 基本方針

振る舞い定義は **ビジネスルールの振る舞いをアクター視点で抽象表現したもの**。完全性とは「要求の各ビジネスルールが Scenario で表現されているか」を意味し、テストケースの網羅性や Scenario の Given/When/Then の細部の充実度ではない。

## 検証項目

### 1. 要求カバレッジ

- 全ての要求に対応するビジネスルール（Rule ブロック）が少なくとも1つあるか
- 要求範囲を超えた Rule/Scenario（スコープクリープ）がないか

### 2. ビジネスルールの完全性

- 主要なビジネスルール違反の振る舞い（例: 重複登録の拒否、権限不足の拒否）が Rule として表現されているか
- 「操作 → 状態変化」と「状態 → 表示」がビジネスルールとして異なる場合、別の Rule ブロックに分離されているか

境界値・空入力・並行実行・タイムアウト等の技術的エッジケースは振る舞い定義のスコープ外（ユニット/統合テストの責務）。これらの欠如は指摘しない。

### 3. 暗黙の要求

- アクセス制御が必要な操作に認可要件が Rule として書かれているか
- 外部入力に対する入力検証の方針（受理範囲）がビジネスルールとして書かれているか
- 冪等性が必要な操作にその方針がビジネスルールとして書かれているか（該当時）

### 4. アーキテクチャ概要の必須セクション存在

以下の5セクションが存在することのみを確認する（記述粒度は問わない）:

- 責務配置
- データ/通信フロー
- 状態Owner
- 境界
- 実装に委ねること

各セクションの記述が「実装の地図」として読めれば充足とする。詳細さは問わない。

## フラグしない

- 実装方法の詳細（how）
- 境界値・空入力・タイムアウト等の技術的エッジケース
- エラー伝播戦略・例外処理方針の細部
- 将来的な拡張可能性
- 「あると便利」レベルの追加 Scenario 提案
- Scenario の Given/When/Then の細分化不足（ビジネスルールが表現されていれば充足）
- 疑似コード・型シグネチャ・関数名の欠如

## 判定

- **LGTM**: 全要求がビジネスルール（Rule）でカバーされ、ビジネスルール違反・暗黙の要求が表現され、アーキテクチャ概要の必須5セクションが存在する
- **NEEDS_FIX**: 未カバーの要求、ビジネスルール違反・暗黙の要求の Rule 欠落、または必須セクションの欠落あり
