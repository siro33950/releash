## 前提

Specファイル（ステップ出力で提供）を読み込み、`## 要求` セクションが存在することを確認する。

## 基本方針: 振る舞いはビジネスルールの抽象表現

振る舞い定義は **ビジネスルールがどんな状況で・何が起きたとき・どう振る舞うか** をアクター視点で抽象表現したもの。テストの受け入れ基準や実装ステップではない。

実装条件・テスト判定基準を Given/When/Then に混入させると、後続の実装ステップを「Scenarioテキストの逐次充足」に縛り、本来の要求を超えた実装制約が生まれる（実装汚染）。これは禁止する。

### 何を書くか / 何を書かないか

| Given/When/Then | OK（ビジネスルール振る舞い） | NG（実装/テスト汚染） |
|---|---|---|
| Given | `ユーザーが有効なアカウントを持っている` | `users テーブルに email="foo@example.com" の行がある` |
| When | `ユーザーがアカウント作成を要求する` | `送信ボタンをクリックする / POST /signup を呼び出す` |
| Then | `アカウントが作成されたことが本人に伝わる` | `画面に "登録完了" と表示され、DB に新しい行が追加される / レスポンスが 200 で返る` |

具体的な入力値・UI操作・API呼び出し・DB状態・レスポンスコード・テスト判定基準は Scenario に書かない。

## Gherkin 構造（必須）

```gherkin
Feature: [機能名 — ビジネス領域]
  Rule: [ビジネスルール名 — このルールが守るべき不変条件・状態遷移]
    Scenario: [このルールが顕在化する代表的な状況]
      Given [アクターの前提状況をビジネス用語で]
      When [アクターの行為をビジネス用語で]
      Then [ビジネスルール上の結果をビジネス用語で]
```

- **Feature**: 機能のビジネス領域
- **Rule（必須）**: 各ビジネスルールを Rule ブロックで分離する。「操作 → 状態変化」と「状態 → 表示」はビジネスルールが異なるので別の Rule にする
- **Scenario**: そのビジネスルールが顕在化する代表的な状況を 1 振る舞い = 1 Scenario で示す
- **Given/When/Then**: アクター視点のビジネス用語のみ。実装/テスト用語は使わない

## Gherkin 作成方針

- **Declarativeスタイル**: 「何が起きるか」を書く。「どう操作するか」「どう実装するか」は書かない
- **1シナリオ = 1振る舞い**
- **ビジネス言語**: ドメイン用語を使用する。技術用語（API名、DBテーブル名、UIコンポーネント名）は持ち込まない
- **Ruleによる分離（必須）**: ビジネスルールが異なる振る舞いは別 Rule に分ける

## スコープ

ビジネスルールに関わる振る舞いのみ。境界値・空入力・タイムアウト等の技術的エッジケースは振る舞い定義のスコープ外（ユニット/統合テストの責務）。

```gherkin

  Rule: [ビジネスルール名]

      When [行為]
      Then [結果]

```
