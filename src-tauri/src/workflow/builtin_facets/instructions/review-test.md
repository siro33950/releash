{{project_name}} プロジェクトのコード変更をテスト充足の観点でレビューする。

## 入力

- 入力で渡される Spec ファイル — テストカバレッジ評価のため振る舞い定義を読み込む
- 実装ステップからのコード変更

## 基本方針

振る舞い定義は **ビジネスルールの振る舞いをアクター視点で抽象表現したもの**。テスト充足レビューは「**ビジネスルール単位でテストが存在し、ビジネスルールが守られていることをテストが担保しているか**」を判定する。Scenario の Given/When/Then の文言と1対1で対応するテストケースが書かれているかを検証するのではない。

## ファクトチェック義務

推測で指摘しない。報告前に必ず実コードを読んで検証する。

## スコープルール

| スコープ | 説明 | FAIL対象 |
|---------|------|---------|
| scope:diff | 今回の変更で導入された問題 | はい |
| scope:touched | 変更ファイル内の既存問題 | 報告のみ |
| scope:external | 変更対象外の問題 | 報告しない |

## 共通FAIL基準（scope:diff）

- ビジネスルールに対応するテストなしで追加された新しい振る舞い

## 検証手順

### 1. ビジネスルールのテストカバレッジ（Rule単位）

`## 振る舞い定義` の各 Rule について:
- そのビジネスルールが守られていることを担保するテストコードを見つける（Scenario の文言と1対1のテストではなく、Rule の不変条件・状態遷移を検証するテストを探す）
- 判定: **カバー済み** / **不十分** / **テストなし**

### 2. テスト品質

| チェック | 内容 |
|---------|------|
| 構造 | AAA（Arrange/Act/Assert）またはGWT（Given/When/Then）パターン |
| 命名 | テスト名が意図を明確に伝えているか |
| 独立性 | 実行順序依存・共有状態依存がないか |
| モック適切性 | モックの粒度が適切か、過剰モックでないか |

### 3. エッジケースカバレッジ

- 境界条件がテストされているか
- 並行/並列シナリオがテストされているか（該当時）
- エラーパスがテストされているか

## フラグしない

- Scenario の Given/When/Then と1対1対応するテストケースの不在（ビジネスルールがテストで担保されていれば充足）
- Scenario の文言を引用したテスト名でないこと

## 指摘フォーマット

各指摘にはファイル:行、問題の説明、修正提案を含める。

## 判定

- **LGTM**: 全ビジネスルール（Rule）に十分なテストがあり、テスト品質が良好
- **NEEDS_FIX**: いずれかのビジネスルールにテストが不足、またはscope:diffのテスト品質に問題
