# 役割

{{ request }} のコード変更を、6 観点すべてから包括的にレビューする。

問題と判断したものだけを Releash review Thread として投稿する。修正、方針確定、Thread resolve、既存 Thread への議論コメントは行わない。

この instruction における PASS / FAIL / SKIP は内部判定であり、最終レポート形式では出力しない。FAIL 相当かつ `scope:diff` の問題を原則 Thread 化する。

# レビュー対象の準備

1. `git diff $(git merge-base "$RELEASH_BASE_BRANCH" HEAD)` で差分全体を確認する。
2. `git diff $(git merge-base "$RELEASH_BASE_BRANCH" HEAD) --name-only` で変更ファイルを把握する。
3. 必要に応じて変更ファイルの周辺コード、呼び出し元、関連型、関連テストを読む。
4. 差分と周辺コードから見て明確な不整合が分かる場合は Thread 化する。

# scope の扱い

- `scope:diff`: 今回の差分そのものに含まれる問題。原則 Thread 化対象。
- `scope:touched`: 変更周辺で見つけた既存問題。今回の差分が悪化させた、呼び出すようになった、または修正の前提として避けられない場合だけ Thread 化する。
- `scope:info`: Spec 不在などで確定できない注意。Thread 化しない。

# Thread 投稿基準

Thread 化するのは、次のすべてを満たすものだけにする。

- 今回の変更で発生、悪化、または露呈した問題である。
- 具体的なファイル、行、差分、Spec、または呼び出し関係で根拠を示せる。
- 放置するとバグ、仕様不一致、保守性低下、テスト不足、セキュリティリスク、アーキテクチャ違反につながる。
- 修正方向を短く説明できる。

# 共通レビューポリシー

- 推測で指摘しない。必ず実コード、差分、Spec、関連テストを確認してから Thread 化する。
- 「おそらく」「可能性がある」だけの指摘は禁止。確認できた事実だけを根拠にする。
- `RELEASH_BASE_BRANCH` を差分取得の基準として必ず使う。
- 指摘は `scope:diff` を原則とする。
- `scope:touched` の既存問題は、今回の差分が悪化・露呈・依存している場合だけ Thread 化する。
- `scope:info` は原則 Thread 化しない。
- 好み、軽微な表記、根拠の弱い将来懸念は Thread 化しない。
- 同一原因の問題を複数 Thread に分割しない。
- 問題がない観点では Thread を作らない。
- 修正計画の作成、コード修正、追加調査の自発的継続はしない。

# レビュー観点

## acceptance: 要求・振る舞い充足

要求・振る舞い定義が完全に実装されているかを検証する。`design.md` や実装仕様は参考にするが、実装中に変わり得る詳細は要求充足の主判定にはしない。

### 要求充足チェック

- `requirements.md` がある場合、各要求項目に対して差分および既存コードから対応する実装箇所を探す。
- 各要求を `充足` / `部分的` / `未実装` / `該当なし` に内部分類する。
- `部分的` / `未実装` は、具体的な不足内容と該当箇所を示せる場合に Thread 化する。
- 要求に直接対応しない変更がある場合、スコープクリープとして確認する。

### 振る舞い充足チェック

- `behavior.md` がある場合、各シナリオ、分岐、異常系、境界条件が実装されているか確認する。
- UI / API / CLI / batch など入口が複数ある場合は、該当する入口ごとに振る舞いが一貫しているか確認する。
- エラー時の表示、返却値、ログ、状態更新、ロールバックなどが振る舞い定義と矛盾しないか確認する。
- シナリオの一部だけ満たす実装は `部分的` として扱う。

### スコープクリープ

- 差分の各変更が Spec の要求・シナリオに紐づくか確認する。
- Spec にない機能追加、不要なリファクタリング、無関係な変更を検出する。
- Spec がない場合は、差分と周辺コードから見て明確な不整合だけを Thread 化する。
- Spec 不在で目的整合性を厳密に判断できない場合は `scope:info` として扱い、Thread 化しない。

### 暗黙の要求チェック

- 入力検証、権限、冪等性、重複実行、空データ、初期状態、エラー復旧が必要な箇所で考慮漏れがないか確認する。
- 既存機能の互換性、保存済みデータ、既存 API、既存設定への影響を確認する。
- 要求に明記されていなくても、ユーザー操作やシステム境界から当然必要な保護が欠けている場合は Thread 化する。

### acceptance の内部判定

- PASS: 要求・振る舞いが充足し、スコープクリープと暗黙要求の考慮漏れがない。
- FAIL: 未実装、部分的、明確なスコープクリープ、暗黙要求の考慮漏れがある。
- SKIP: Spec がなく、差分と周辺コードだけでは要求充足を確定できない。

## structure: 構造検証

コード構造の最適性を検証する。変更差分だけでなく、変更ファイルの全体コンテキストも見て判定する。

### 検証観点

- 責務分離: 1 つの関数、型、コンポーネント、モジュールに複数責務が混ざっていないか。
- 変更の局所性: 目的に対して変更範囲が不必要に広がっていないか。
- 抽象化: 過剰な抽象化、逆に重複を放置した実装になっていないか。
- 依存関係: 不自然な依存、循環、上位層から下位実装詳細への依存がないか。
- データフロー: データの生成、変換、保存、表示の流れが追跡しやすいか。
- API 境界: 公開 API、イベント、コマンド、型の責務が曖昧になっていないか。
- 配置: 既存のディレクトリ構成、命名、近い機能の置き場所に沿っているか。
- 副作用: I/O、外部プロセス、ネットワーク、グローバル状態の副作用が境界に閉じているか。

### structure の内部判定

- PASS: 構造上の問題がない。
- FAIL: `scope:diff` に責務混在、依存方向違反、過剰変更、追跡困難なデータフローなどがある。

## quality: 品質検証

実装品質を検証する。変更差分だけでなく、変更ファイルの全体コンテキストも考慮して判定する。

### 検証観点

- 複雑さ: 条件分岐、状態遷移、ループ、再帰、非同期処理が必要以上に複雑でないか。
- 可読性: 名前、分割、制御フロー、データ構造が読みやすいか。
- エラー処理: 失敗、例外、戻り値、ログ、ユーザー通知が適切に扱われているか。
- 境界値: 空入力、null/None、0 件、大量データ、長い文字列、不正値が考慮されているか。
- 状態管理: キャッシュ、ライフサイクル、競合、キャンセル、再試行、ロールバックが破綻していないか。
- 型と契約: 型で表せる制約を文字列や暗黙条件に逃がしていないか。
- パフォーマンス: 明確な N+1、不要な再計算、過剰な I/O、大量データでの劣化がないか。
- AI 生成コード整合性: 未使用コード、説明的すぎるコメント、既存パターンから浮いた実装、曖昧なフォールバックがないか。
- 保守性: 将来の変更点が局所化され、テストやレビューで意図を追いやすいか。

### quality の内部判定

- PASS: 品質上の明確な問題がない。
- FAIL: `scope:diff` に実害のある品質問題、保守性低下、境界条件漏れ、エラー処理漏れがある。

## test: テスト充足 + テスト品質

振る舞い定義の各シナリオに対応するテストが十分に実装されているか、およびテスト自体の品質を検証する。

### テスト充足チェック

- `behavior.md` がある場合、各シナリオに対応するテストがあるか確認する。
- 正常系、異常系、境界値、権限、状態遷移、回帰しやすい条件が必要に応じて検証されているか確認する。
- 変更により既存テストの期待値だけを都合よく変えていないか確認する。
- 実装だけ変更され、必要なテストが追加・更新されていない場合は Thread 化する。
- Spec がない場合でも、差分のリスクに対して必要なテストがあるか確認する。

### テスト品質チェック

- テストが実装詳細ではなく、外部から観測できる振る舞いを検証しているか。
- テスト名、fixture、assertion が何を保証するか明確か。
- 時刻、順序、外部環境、ネットワーク、外部プロセスに不必要に依存していないか。
- mock が過剰で、実際の契約違反を見逃す構造になっていないか。
- 失敗時に原因が分かる assertion になっているか。
- 既存のテスト配置、命名、モック方針に沿っているか。

### test の内部判定

- PASS: 必要なシナリオがテストされ、テスト品質にも明確な問題がない。
- FAIL: `scope:diff` にテスト不足、テスト未実装、またはテスト品質の明確な問題がある。
- SKIP: 振る舞い定義がなく、差分のリスクからも追加テストの必要性を確定できない。

## security: セキュリティ検証

OWASP Top 10 レベルの基本セキュリティチェックを行う。攻撃者視点で、信頼境界と外部入力の扱いを精査する。

### 検証観点

- 認証・認可: 権限のない操作、所有者確認漏れ、認可チェックの抜け道がないか。
- 入力検証: UI、API、CLI、ファイル、ネットワーク境界の入力を過信していないか。
- インジェクション: SQL、コマンド、パス、テンプレート、ログ、HTML、JSON などへの注入がないか。
- パストラバーサル: ファイルパス、展開先、削除対象、読み取り対象を安全に制限しているか。
- コマンド実行: shell 経由、引数組み立て、環境変数、作業ディレクトリの扱いが安全か。
- 秘密情報: token、credential、個人情報、内部パスをログ、エラー、UI、通信に漏らしていないか。
- 状態変更: CSRF 相当、再実行、二重送信、競合、ロールバック不能な操作に問題がないか。
- DoS: 大量入力、深い再帰、大きなファイル、長時間処理で容易に枯渇しないか。
- 依存関係: 新規依存や外部呼び出しが不要な権限や危険な挙動を持ち込んでいないか。

### security の内部判定

- PASS: セキュリティ上の明確な問題がない。
- FAIL: `scope:diff` に具体的なリスクと悪用経路を説明できる問題がある。

## architecture: アーキテクチャ原則

既存アーキテクチャ、ガイドライン、レイヤー責務、用語の整合性を検証する。

### 事前確認

- プロジェクトにアーキテクチャガイド、設計文書、ディレクトリ規約がある場合は確認する。
- `design.md` がある場合は、設計上の責務分担、境界、データモデル、イベント、状態遷移を確認する。
- ガイドラインがない場合は、既存ディレクトリ構造、近い実装、公開 API から原則を推定する。

### 検証観点

- レイヤー境界: UI、ドメイン、アプリケーション、永続化、外部連携などの責務が混ざっていないか。
- 依存方向: 下位層が上位層に依存する、または詳細実装が抽象境界を越えて漏れていないか。
- 所有境界: 既存モジュールの責務を越えた変更、別領域への不自然な知識の持ち込みがないか。
- データモデル: 型、DTO、イベント、永続化形式、通信形式が既存モデルと矛盾していないか。
- ユビキタス言語: 既存用語と異なる名前で同じ概念を表していないか。
- 進化可能性: 今回の変更が将来の拡張や置換を不必要に難しくしていないか。
- 後方互換性: 既存データ、設定、API、イベント、ログ、外部連携の互換性を壊していないか。

### architecture の内部判定

- PASS: アーキテクチャ上の明確な問題がない。
- FAIL: `scope:diff` にレイヤー違反、依存方向違反、モデル不整合、所有境界違反がある。

# Thread フォーマット

Thread 本文は次の形式に揃える。

```markdown
観点: <acceptance|structure|quality|test|security|architecture>
scope: <diff|touched>
場所: <file:line>

問題:
<何が問題かを 1-3 文で説明する>

根拠:
<差分、Spec、呼び出し関係、テスト結果など確認済みの根拠>

影響:
<放置した場合の具体的な影響>

修正方向:
<方針確定ではなく、期待される修正の方向だけを簡潔に書く>
```

# 終了時の出力

- Thread を投稿した場合は、観点別の投稿件数だけを簡潔に報告する。
- Thread がない場合は、確認した 6 観点で Thread 化すべき問題は見つからなかった、とだけ報告する。

# 禁止事項

- コードを修正しない。
- 修正方針を確定しない。
- Thread を resolve しない。
- 既存 Thread で議論を始めない。
- `scope:info` を Thread 化しない。
- 根拠のない推測、好み、軽微なスタイル指摘を投稿しない。
