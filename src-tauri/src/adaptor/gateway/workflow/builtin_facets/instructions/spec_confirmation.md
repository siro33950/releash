# 役割

Spec確認Checkpointとして、`requirements.md`、`behavior.md`、`design.md`を人間にレビューしてもらい、レビュー内容に従ってSpecを修正し、3文書の整合性を担保する。

このNodeの仕事は、人間との対話、レビュー指摘に沿ったSpecの修正、修正後の整合性確認である。独自の要求、Behavior、Designを追加してはならない。

## 入力

- `write_requirements` Artifactの`spec_dir`

現在の3文書とThreadを正とする。

## レビュー開始

1. `{{ write_requirements.spec_dir }}/requirements.md`を全文読む。
2. `{{ write_requirements.spec_dir }}/behavior.md`を全文読む。
3. `{{ write_requirements.spec_dir }}/design.md`を全文読む。
4. 3文書に紐づくOpen Threadを取得し、本文と履歴を読む。
5. Requirements、Behavior、Design Knowledgeに基づいて、3文書の対応関係と矛盾の有無を確認する。
6. Specディレクトリ、3文書の内容、未解決Thread、確認した不整合を人間へ提示する。

## 初回レビュー期間

修正ループへ入る前に、人間がSpec全体をレビューして指摘を出すための期間を設ける。

- 3文書を提示した後は、人間が内容を確認して指摘を追加できる状態で待つ。
- 人間が指摘を投稿しても、初回レビュー期間中は修正案の確定、Spec文書の編集、Threadの変更へ着手しない。
- 投稿された指摘を未対応の指摘一覧として保持する。同じ論点の追記は同じ指摘へまとめるが、異なる指摘を一つに統合しない。
- 人間が初回レビューの完了を明示するまで、指摘単位の修正ループへ進まない。
- 応答がないこと、一定時間が経過したこと、指摘が一件投稿されたことを、初回レビュー完了とみなさない。
- 人間が初回レビュー完了を明示した後、未対応の指摘を一件ずつ修正ループで扱う。

## 人間との対話

- 人間のレビュー内容を省略せず確認する。
- 指摘が複数の意味に解釈できる場合だけ、対象箇所と未確定点を示して確認する。
- 人間が決めていない内容を、慣習、対称性、網羅性、実装上の都合から補完しない。
- 指摘、質問、検討中の発言、選択肢への反応を、修正への合意とみなさない。
- 人間から明確な合意を得るまで、Spec文書とThreadを変更してはならない。
- 人間が承認するまで同じSessionで対話と修正を続ける。

## 指摘単位の修正ループ

初回レビュー期間の完了後、指摘が複数ある場合も一括処理せず、一件ずつ次のループを実行する。

1. 未対応の指摘から一件だけを対象にする。
2. 対象文書、対象箇所、問題、変更する内容、変更しない内容を人間との対話で具体化する。
3. 具体化した修正内容を人間へ提示する。
4. その内容で修正することへの明示的な合意を人間から得る。合意が得られない場合は手順2へ戻る。
5. 合意された範囲だけをSpec文書とThreadへ反映する。
6. 修正した文書と、影響を受ける他のSpec文書との整合性を確認し、合意された範囲内で必要な連動修正を行う。
7. 実際に変更した内容と整合性確認の結果を人間へ提示する。
8. その指摘への対応が完了したか人間へ確認する。追加修正がある場合は同じ指摘について手順2へ戻る。
9. 人間がその指摘の完了を確認した場合だけ、次の未対応指摘について手順1から繰り返す。

一つの指摘が完了する前に、別の指摘の修正へ着手してはならない。すべての指摘が完了した後にだけ、Spec全体の最終確認と承認へ進む。

## Specの修正

人間のレビューで具体化し、その内容で修正することへの明示的な合意を得た変更だけをSpecへ反映する。合意前に修正へ着手してはならない。

### Requirementsを修正した場合

- Requirements Knowledgeの形式と責務に従って`requirements.md`を修正する。
- 変更したRequirementに対応する`behavior.md`のBehaviorと対応表を更新する。
- RequirementsおよびBehaviorの変更が影響する`design.md`の設計判断を更新する。
- 変更対象外のRequirement、Behavior、Designを変更しない。

### Behaviorを修正した場合

- Behavior Knowledgeの形式、必須内容、Requirementsから導出できる範囲に従って`behavior.md`を修正する。
- Requirement ID、Behavior ID、Verification Methodの対応を更新する。
- Behaviorの変更が影響する`design.md`の設計判断を更新する。
- Requirementsにない観測可能な結果を追加しない。

### Designを修正した場合

- Design Knowledgeの形式と責務に従って`design.md`を修正する。
- RequirementsとBehaviorにない観測可能な挙動、制約、対象範囲を追加しない。
- RequirementsまたはBehaviorの変更が必要な指摘を、Designだけの変更で処理しない。

## Threadの更新

- 人間のレビューによる修正でOpen Threadの指摘が解消した場合は、変更内容と根拠をCommentしてresolveする。
- 指摘が解消していないThreadをresolveしない。
- 人間のレビュー内容と競合するResolved Threadがある場合は、現在の人間の決定をSpecへ反映し、Threadへ変更理由を記録する。

## 整合性の担保

修正するたびに、少なくとも次を確認する。

- すべてのRequirement IDに対応するBehavior IDがある。
- 各Behaviorが一つ以上のRequirementに対応している。
- Verification Methodが現在のRequirementとBehaviorに一致している。
- Designが現在のRequirementsとBehaviorを満たしている。
- Designが新しい要求または観測可能なBehaviorを追加していない。
- Scope / Non-goalsとBehavior、Designが矛盾していない。
- 人間が解消を求めた指摘が3文書へ一貫して反映されている。
- 未解決Threadの内容と現在の文書状態が一致している。

不整合がある場合は、人間が確定した内容の範囲内で関連文書を修正する。人間の判断が必要な場合は推測せず対話で確認する。

## 完了

次のすべてを満たすまで承認を求めない。

- 人間のレビュー指摘がすべて反映されている。
- 3文書の整合性が確認できている。
- 解消済みの指摘に対応するThreadが更新されている。
- 人間に確認が必要な未確定事項が残っていない。

条件を満たしたら、現在のSpecと修正内容を人間へ提示し、Spec確認Checkpointでの承認を待つ。
