{{project_name}} プロジェクトの `design.md` をユーザーとの対話で作成または更新する。

## 入力

`spec-directory` schema で渡される `spec_dir` を読み、以下を参照する。

- `${spec_dir}/requirements.md`
- `${spec_dir}/behavior.md`

## 目的

実装が要求・振る舞いの意図を外さないために、判断が分かれた所だけを最小限の合意として記録する。網羅的な設計仕様書ではない。

本ステップでは `design.md` を作成・更新する。設計を詰める途中で前段（`requirements.md` / `behavior.md`）との不整合に気づいたら、ユーザーに報告し、前段に戻って修正するかは判断を仰ぐ。

## 進め方

### 事前準備

1. `design.md` に下記フォーマットの全見出しを雛形として用意する。本文は空のまま。
2. `requirements.md` / `behavior.md` を読む。
3. 関連する既存実装コードを把握する。
4. リポジトリの規約・アーキテクチャドキュメント・lint/format 設定などを把握する。
5. 網羅的な実装計画を `${spec_dir}/design.notes.md` に書き出す。これを議論の起点にする。

### 議論

**目的**：設計判断についてユーザーと議論し、合意した内容を `design.md` に記録する。

**手順**：

1. design.md フォーマットの見出しを上から 1 つ取り上げる。
2. 当該見出しについて、`design.notes.md` の網羅的な実装計画と、それまでの議論で合意された内容を踏まえ、ユーザーと議論して決めるべき設計判断（複数の選択肢があり判断が必要な所・既存規約や既存パターンからの逸脱・トレードオフがある所）を 1 つ洗い出す。
3. その判断について複数案を考え、各案にトレードオフを添え、推奨案を示してユーザーに提案する。
4. 議論を続ける。ユーザーから別案・追加観点・反論が出尽くしたことを確認する。エージェント側からも追加の懸念点・別案を能動的に出す。
5. 合意候補が固まったら、その内容を**ドラフトとして整理してユーザーに提示**し、構造化された選択肢付きの質問で「このドラフトで `design.md` に記載してよいか」を問う。ユーザーが選択肢から「記載してよい」を明示的に選んだ時のみ `design.md` の該当見出しの下に**論点ごとの小見出し（####）を付けて**書く。自然言語の合意（「OK」「いいね」「書いて」など）は書き込みのトリガーにしない。
6. 当該見出しに議論すべき設計判断が残っていれば、次の論点を取り上げる。残っていないと思える場合は、構造化された選択肢付きの質問で「この見出しを閉じて次の見出しへ進んでよいか」をユーザーに問う。ユーザーが選択肢から「進んでよい」を明示的に選んだ時のみ、次の見出しを取り上げる。エージェントが見出しの移動を勝手に決めない。

**注意事項**：

- 判断がないと思える見出しもユーザーに「この見出しに該当する判断はありますか」と確認する。「判断なし」と合意できたら空のまま次へ進む。

### 完了条件

全見出しを消化したら、ユーザーに最終確認を促す。承認をもって本ステップを完了とする。

## design.md フォーマット

各見出しの下に、議論で確定した論点ごとに小見出し（####）を立てて書く。

```markdown
# Design

## The actual design

### Architecture
<!-- 責務分割・構造に関する設計判断 -->

#### <論点 1 のタイトル>
<論点 1 の確定内容>

#### <論点 2 のタイトル>
<論点 2 の確定内容>

### Interface
<!-- 外部から見えるインターフェースに関する設計判断 -->

### Data Model
<!-- データの持ち方に関する設計判断 -->

### Database
<!-- 永続化先・スキーマに関する設計判断 -->

### UI/UX
<!-- 画面・操作フローに関する設計判断 -->

### Algorithm
<!-- 非自明なロジックに関する設計判断 -->

### Infra
<!-- インフラ構成・デプロイに関する設計判断 -->

## Alternatives Considered
<!-- 採らなかった主要な設計案と、却下理由・トレードオフ -->

## Cross-cutting concerns
<!-- セキュリティ・パフォーマンス・可観測性などの横断的考慮事項のうち、判断が分かれたもの -->

## Risks
<!-- 既知のリスク・不確定要素・追加調査が必要な点 -->
```

## 書くこと

- 判断が分かれた所（複数の選択肢があり、トレードオフがあった所）の採用結果
- 既存の規約・既存パターンからの逸脱
- 採らなかった選択肢と却下理由（Alternatives Considered）

## 書かないこと

- 既存の規約・最低限のアーキテクチャに従うだけの自明な部分（コードレビューで発見される前提）
- 完全なスキーマ・インターフェース定義のコピペ
- コードや擬似コード（新規アルゴリズムの説明でない限り）
- 実装順序・ファイル編集手順・helper 関数名・テストケース名
- security 実装の詳細（sanitize / escape / path traversal 対策方法など）
