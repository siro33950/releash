Spec 3文書の整合性をチェックして報告し、ユーザーが Spec 全体を見渡して追記・修正できる締めのタイミングを提供する。

## 入力

`spec-directory` schema で渡される `spec_dir` を読み、以下を参照する。

- `${spec_dir}/requirements.md`
- `${spec_dir}/behavior.md`
- `${spec_dir}/design.md`

## 目的

実装に進む前の最後の確認点として、3文書間の整合性を点検し、ユーザーがその場で思いついた追加要件・変更を反映できるようにする。重いレビューループではなく、軽い整合性チェックと対話の場とする。

## 進め方

最初のターンで行うこと:

1. requirements.md / behavior.md / design.md を読み、相互の整合性を点検する。観点は次の通り:
   - requirements の各要求が behavior の Rule / Scenario でカバーされているか。
   - behavior の各 Rule が design の設計方針でカバーされているか。
   - 3文書間に矛盾、抜け、用語のブレがないか。
2. 整合性チェックの結果を簡潔に報告する。問題があれば具体的に指摘し、なければ問題なしと伝える。
3. ユーザーに、Spec 全体を見渡して追加したい点や直したい点がないか問いかける。

2 ターン目以降の各ターンで行うこと:

1. ユーザーが指摘した整合性の綻びや、思いついた追加要件・変更を受けて、該当する文書（requirements.md / behavior.md / design.md）をその場で直接修正する。
2. 何をどの文書に反映したかを簡潔に報告する。
3. 残る確認点があれば 1 つだけ問いかける。

整合性が取れ、ユーザーから追加の要望がなくなったら、最終確認を促す。承認をもって Spec 作成フェーズを完了とし、実装へ進む。

## 出力

整合性チェックと必要な修正が完了したら、同じ `spec_dir` を提出値として確定し、提出は出力Contract側の手順に従う。
