# Design

## 定義

`design.md`は、確定したRequirementsとBehaviorを、対象リポジトリの既存実装上でどう実現するかを記録する設計文書である。

責務分割、構造、インターフェース、データ、処理方法、エラー処理など、実装前に共有する必要がある設計判断を記載する。Requirementsにない観測可能な挙動、制約、対象範囲は追加しない。

## フォーマット

次の見出しと順序を変更しない。

```markdown
# Design

## The actual design

### Architecture
<!-- 責務分割・構造に関する設計判断 -->

#### <論点のタイトル>
<確定した設計>

### Interface
<!-- 外部から見えるインターフェースに関する設計判断 -->

### Data Model
<!-- データの持ち方 -->

### Database
<!-- 永続化先・スキーマ -->

### UI/UX
<!-- 画面・操作フロー -->

### Algorithm
<!-- 非自明なロジック -->

### Infra
<!-- インフラ構成・デプロイ -->

## Alternatives Considered
<!-- 採らなかった主要案と理由 -->

## Cross-cutting concerns
<!-- セキュリティ・性能・可観測性など -->

## Risks
<!-- 既知のリスク・未決定事項 -->
```

該当しない見出しは削除せず、`該当なし`と記載する。

## 記載内容

- RequirementsとBehaviorを満たす実装方針を記載する。
- 責務分割、データ構造、処理フロー、エラー処理を必要な範囲で具体化する。
- 対象リポジトリの規約、アーキテクチャ、既存実装パターンに従う。
- 設計判断の根拠となるコード、文書、規約を記載する。
- 採用しなかった主要案が実際にある場合だけ`Alternatives Considered`へ記載する。数合わせで案を作らない。
- セキュリティ、性能、可観測性など複数領域に関係する設計を`Cross-cutting concerns`へ記載する。
- 実装前に認識すべき既知のリスクを`Risks`へ記載する。

## 粒度境界

既存コード、規約、上流文書から一意に決まる記述は書かない。書くのは、選択肢が複数あり、かつ選択を誤るとRequirementsまたはBehaviorを満たせなくなる判断だけである。一意に決まるかどうかは、根拠となるコードまたは規約を指せるかで判定する。

Designが特定できるようにする各対象の境界は次のとおり。

- 責務owner — 書く: 新しい振る舞いを所有するmodule／layerと、既存ownerからの移動。書かない: layer規約から一意に決まる配置。
- 主要な変更対象 — 書く: 変更・新設するmoduleのpathと、そこが担う変更の要旨。書かない: 関数単位・行単位の変更列挙。
- interface — 書く: 外部から観測できる契約（公開command／API／protocolの名前、入出力、互換可否）と、内部境界のtrait名および責務一文。書かない: 内部traitの全signature、enum variantの全定義、戻り値型の網羅列挙。コード片は、既存規約から読み取れない契約を示す最小の一つに限る。
- data — 書く: 追加・変更するrecordの存在、所有者、identityとなるkey、保持しないと決めたもの、versioningの要否。書かない: 全fieldの列挙。既存公開型と同型で足りる場合は「既存Xと同型」と書く。
- control flow — 書く: 既存フローと異なる順序制約、原子性境界、失敗時の巻き戻し単位。書かない: 逐次手順の番号列挙、既存実装をなぞる記述。
- error処理 — 書く: 外部から観測できる失敗分類と、どの層で発生しどこまで型を保つか。書かない: 既存error variantを一つずつ「変換しない」と網羅する記述。
- 互換境界 — 書く: 壊す／壊さないの判断と、壊す場合の移行手段。書かない: 影響しない既存契約の列挙。
- 必要な検証 — 書く: Behaviorの受入条件のうち検証手段が自明でない箇所と、その手段の種別。書かない: テストケース名やfixtureの具体設計。
- Database — 書く: 要求に紐づくaccess pathと、それが必要な根拠。書かない: 自明なkey列挙、CHECK制約、列定義。

## 文書間の境界

- Requirementsにない観測可能な挙動、制約、対象範囲を追加しない。
- Requirementが「AのときB」と定めている場合、A以外の条件に対する外部挙動を設計で決めない。
- Behaviorにない受入条件を設計判断として作らない。
- RequirementsまたはBehaviorが未完了の場合、未決定事項を推測で補完せず、決定済みの範囲だけを設計する。
- 複数の実装方法が考えられても、既存規約と変更範囲から一つに決められる場合は、未決定の要求として扱わない。
