## 変える部分

- `.app` への daemon の同梱: `bundle.resources` が空で `externalBin` の指定が無い現状を変え、`Releash.app` が daemon の実行ファイルを含むようにする。根拠: R-001「`Releash.app` は daemon の実行ファイルを含み、UI は `.app` の外に別途配置した実行ファイルを必要とせずに daemon を起動できる」、B-001。ルート: 委任
- UI からの daemon の spawn と起動完了までの待機: desktop の起動で daemon を子プロセスとして起動し、backend が Ready に達して認証済みのクライアント ws 接続が成立するまで通常の操作を受け付けないようにする。現状は daemon を起動せず、client 用 discovery file を読めなければ `setup` がエラーを返して終了する。根拠: R-002「UI が daemon を子プロセスとして起動する。UI が通常の操作を受け付けるのは、daemon の backend が Ready に達し、認証済みのクライアント ws 接続が成立した後である」、R-007、B-001 / B-002 / B-007。ルート: 起動監督の判断は Rust が所有する（「固定するルート」）
- daemon の監視と異常終了時の再 spawn: 起動した daemon プロセスの終了を UI が観測し、再び起動する経路を設ける。現状は監視も再起動も無い。根拠: R-004「daemon が異常終了した場合、UI は待機間隔と試行上限の範囲で daemon を再び起動し、再接続した後は現在の状態が画面へ反映される」、B-004。ルート: 自動再起動の判定材料を daemon プロセスの終了の仕方と起動期限の超過に限る（「固定するルート」）
- 起動待ちの期限と期限超過時の後始末: 起動待ちに有限の期限を設け、超過したときは起動した子プロセスを停止し、その終了を確認してから次の起動を行うようにする。根拠: R-016「daemon の起動待ちには有限の期限がある。期限を超えた場合、UI は起動した子プロセスを停止し、その終了を確認してから次の起動を行う」、B-019。ルート: 委任（期限の具体値も委任）
- 自動再起動の待機間隔・試行上限・リセット条件: 待機間隔と試行上限を設け、Ready 直後のクラッシュの繰り返しで上限を回避できないようにする。根拠: R-017「自動再起動には待機間隔と試行上限がある。Ready に達した直後のクラッシュを繰り返しても試行上限は回避されず、UI は無限に再起動しない」、B-020。ルート: 委任（待機間隔・試行上限・リセット条件の具体値も委任）
- 自動再起動の対象の判定と、停止時の表示・利用者の再試行: 対象を daemon プロセスの異常終了と起動期限の超過に限り、対象外の失敗または上限到達では自動再起動を止めて理由と終了操作を表示し、再試行できる場合は利用者が明示的に再試行できるようにする。根拠: R-018「自動再起動の対象は、daemon プロセスの異常終了（終了コードが 0 以外、またはシグナルによる終了）と、起動期限の超過である。……自動再起動の対象外の失敗、または試行上限に達した場合、UI は自動再起動を止め、理由と終了操作を表示する」、B-017 / B-018 / B-020 / B-021。ルート: `StartupFailureKind` による分岐を作らない（「固定するルート」）
- 起動失敗の段階と理由の表示: spawn、backend の初期化、起動期限超過、起動後の異常終了を区別して段階と理由を表示し、クライアント ws が確立しない場合も表示できるようにする。現状は backend の初期化失敗の分類と correlation id が daemon の stderr と local log に留まり、終了コードはいずれの種別でも 1 である。根拠: R-015「daemon の起動が失敗した場合、UI は失敗した段階（spawn、backend の初期化、起動期限超過、起動後の異常終了）と理由を表示する。クライアント ws が確立しない場合も表示できる」、B-017 / B-018 / B-019 / B-020。ルート: 委任（失敗段階と理由を UI shell へ届ける経路は委任）
- daemon による親プロセスの終了の検知と自己終了: UI プロセスの終了を daemon が検知して自ら終了し、daemon が起動した terminal と provider のプロセスも終了させる。現状は検知経路が無く、これらの子プロセスを片付ける経路は一括停止の中にしかない。根拠: R-005「UI プロセスが終了した場合、daemon はそれを検知して自ら終了する。このとき daemon は一括停止（……）を行わない。daemon が起動した terminal と provider のプロセスも終了し、UI のない daemon とその子プロセスが残らない」、B-005。ルート: 一括停止（`ShutdownCoordinator`）を経由せず、terminal と provider のプロセスの片付けは一括停止の外で行う（「固定するルート」）。検知方式は委任
- Quit での daemon への停止要求と一括停止完了の待機: メニューとトレイの Quit が daemon へ停止要求を送り、一括停止の完了後に UI と daemon の両方を終了させる。現状は desktop プロセスだけを終了させ、`request_application_quit` を送らない。根拠: R-006「メニューまたはトレイの Quit を選ぶと、UI が daemon へ停止要求を送り、daemon の一括停止（……）が完了してから、UI と daemon の両方が終了する」、B-006。ルート: 委任
- Quit 開始後の再起動予約の解除: Quit を開始した後は再起動の予約を解除し、daemon の終了を契機に再 spawn しないようにする。自動再起動の待機中の Quit も同じにする。根拠: R-019「Quit を開始した後は再起動の予約が解除され、daemon の終了を契機に UI が daemon を再び起動することはない。自動再起動の待機中に Quit した場合も同じである」、B-022。ルート: 委任
- LaunchAgent の登録方式の移行と一本化: `tauri-plugin-autostart` が `~/Library/LaunchAgents/` へ書く現在の登録を変え、登録を 1 つに保ったまま、`.app` の削除でログイン時の起動が試みられなくなるようにする。根拠: R-010「Releash の LaunchAgent の登録は 1 つだけであり、UI と daemon で二重に登録されない」、R-011「`Releash.app` を削除した後は、ログインしても Releash の起動が試みられない」、B-011 / B-012。ルート: `SMAppService` の agent 方式（`SMAppService.agent(plistName:)`）を使い、plist を `.app` の `Contents/Library/LaunchAgents/` に同梱する（「固定するルート」）
- ログイン時に起動の設定と新しい登録方式の対応: 設定の有効・無効の切替を新しい登録方式に合わせ、有効なときはメニューバーのアイコンと daemon が起動し、無効なときはどちらも起動しないようにする。現状は renderer が `@tauri-apps/plugin-autostart` の `enable()` / `disable()` を呼び、表示値を OS の `isEnabled()` から読んでいる。根拠: R-008「ログイン時に起動の設定を有効にしてログインすると、メニューバーのアイコンと daemon が起動する。無効にしてログインした場合は、どちらも起動しない」、B-008 / B-009。ルート: 委任
- 最小化状態で起動と LaunchAgent の起動引数の対応: ログイン時の起動でウィンドウを表示せずメニューバーのアイコンだけを出す経路を、新しい plist の起動引数に合わせる。現状は起動引数の `--hidden` と `start_minimized` が真のときにだけ hide / minimize する。根拠: R-009「最小化状態で起動の設定が有効なとき、ログイン時の起動ではウィンドウが表示されず、メニューバーのアイコンだけが出る」、B-010。ルート: 委任
- UI のクラッシュ後に自動復活させないこと: UI がクラッシュしたら daemon も終了し、`Releash.app` を起動するまでどちらも起動し直されないようにする。根拠: R-012「UI プロセスがクラッシュした場合、daemon も終了する。`Releash.app` を起動するまで、UI も daemon も自動で起動し直されない」、B-013。ルート: launchd の `KeepAlive` を付けない（「固定するルート」）
- UI の単一インスタンス化: Releash が動作している状態で `Releash.app` を起動したときに、既に動作している UI をアクティブにし、2 つ目の UI プロセスを終了させ、2 つ目の daemon を起動しないようにする。現状は UI プロセスの重複起動を防ぐ仕組みが無い。根拠: R-028「Releash が既に動作している状態で `Releash.app` を起動すると、既に動作している UI がアクティブになり、2 つ目の UI プロセスは終了する。2 つ目の daemon は起動されない」、B-032。ルート: loopback ポートの bind を使わず、UI 側は既に動作している UI のアクティブ化で担う（「固定するルート」）。実現方式は委任
- 接続先インスタンスとリリースの一致の検証: 接続先が UI の起動した daemon インスタンスであることと、UI と daemon のリリースが一致することを確認してから通常の操作を受け付けるようにする。現状は discovery file の `pid` / `process_started_at` / `instance_id` の照合はあるが、UI が起動した子プロセスとの対応もリリースを照合する情報も無い。根拠: R-020「UI が通常の操作を受け付けるのは、接続先が UI の起動した daemon インスタンスであり、UI と daemon のリリースが一致することを確認した後である」、B-023 / B-024。ルート: 起動対象・接続先の検証は Rust が所有する（「固定するルート」）。リリースの一致を確認するための情報の持ち方は委任
- 更新の適用に伴う daemon の切替: 更新の適用で、必要な利用者の判断を経て一括停止を完了させ、旧 daemon の終了を確認してから新 daemon を起動する経路を設ける。現状は renderer が `@tauri-apps/plugin-updater` と `relaunch()` で desktop プロセスだけを再起動し、daemon を停止しない。根拠: R-021「更新の適用では、必要な利用者の判断を経て daemon の一括停止を完了し、旧 daemon の終了を確認してから新 daemon を起動する。実行中の workflow がある場合も同じである」、B-025。ルート: 更新に伴う停止・再起動は既存の `ShutdownCoordinator` と統合する。updater は UI shell に残し、Rust の切替制御と連携させる（「固定するルート」）
- 意図的な停止での再 spawn の抑止とデータ領域の排他: 更新・再起動のための停止では daemon の終了を契機とする自動の再起動を行わず、旧 daemon と新 daemon が同じデータ領域を同時に使用しないようにする。根拠: R-022「更新・再起動のための意図的な停止では、daemon の終了を契機とする自動の再起動は行われない。旧 daemon と新 daemon が同じデータ領域を同時に使用することはない」、B-026。ルート: 委任
- 切替中の操作受付の停止と再開: 切替の間は通常の操作を受け付けず、新 daemon の Ready、接続先とリリースの一致、認証済みのクライアント ws 接続、必要な状態の再取得を確認してから受付を再開するようにする。根拠: R-023「切替の間、UI は通常の操作を受け付けない。新 daemon が Ready に達し、接続先とリリースの一致と認証済みのクライアント ws 接続を確認し、必要な状態を再取得した後に受付を再開する」、B-025 / B-030。ルート: 切替状態は Rust が所有する（「固定するルート」）
- 停止結果が不明な場合の切替の停止: daemon の停止結果が不明なときに、停止完了とみなして切替を進めないようにする。現状の一括停止は preparation と decision の 2 つの期限を超えると `OutcomeUnknown` になる。根拠: R-024「daemon の停止結果が不明な場合、停止完了とみなして切替を進めない」、B-027。ルート: 停止完了の判定は Rust が所有する（「固定するルート」）
- 切替の失敗の段階と理由の表示: 更新の適用失敗、新 daemon の起動失敗、接続先またはリリースの不一致で、失敗した段階と理由を表示し、利用者が原因を確認して終了できるようにする。根拠: R-025「更新の適用失敗、新 daemon の起動失敗、接続先またはリリースの不一致では、失敗した段階と理由が表示され、利用者は原因を確認して終了できる」、B-023 / B-024 / B-028 / B-029。ルート: 委任
- 更新を伴わない再起動の経路: application quit の Restart の意図でも、旧 daemon の一括停止の完了と終了を確認してから新しい daemon と UI を起動するようにする。現状は `handle.request_restart()` が desktop プロセスだけを再起動する。根拠: R-026「更新を伴わない再起動（application quit の Restart の意図）でも、旧 daemon の一括停止の完了と終了を確認してから、新しい daemon と UI が起動し、R-020 と R-023 の確認の後に利用可能になる」、B-030。ルート: 既存の `ShutdownCoordinator` と統合する（「固定するルート」）
- 切替をまたぐ結果不明の変更要求の扱い: daemon の再起動、更新に伴う切替、更新を伴わない再起動のいずれをまたいでも、結果を確定できない変更要求が結果不明として扱われ、安全を確認できない再実行が行われないようにする。開始状態には backend のプロセスを再起動する経路自体が無く、#1201 が定めた規則をこの経路の上で成立させる必要がある。根拠: R-027「daemon の再起動、更新に伴う切替、更新を伴わない再起動をまたいで結果を確定できない変更要求は、結果不明として表示され、処理失敗としては表示されず、安全を確認できない再実行は自動でも利用者の再試行でも行われない」、B-031。ルート: 委任

## 固定するルート

- LaunchAgent の登録方式: `SMAppService` の agent 方式（`SMAppService.agent(plistName:)`）を使い、plist を `.app` の `Contents/Library/LaunchAgents/` に同梱する。登録は 1 つに統合し二重登録にしない。粒度は方式と plist の置き場所まで。理由は `.app` の削除で plist も消え、ログイン時の起動が試みられなくなるため。実機で確認した Ollama・Spotify と同じ方式。関係: R-010 / R-011、B-011 / B-012。
- launchd の `KeepAlive` は付けない。粒度は plist のキー指定まで。理由は UI のクラッシュ後に daemon を自動復活させないため。関係: R-012、B-013。
- 単一インスタンス: loopback ポートの bind は使わない。UI 側は既に動作している UI のアクティブ化、daemon 側は local event store の writer lock で担う。粒度は手段の選択まで（実現方式は委任）。理由は固定ポートが data_dir 単位の排他にならず、無関係なプロセスとのポート衝突で起動不能になりうるため。関係: R-013 / R-028、B-014 / B-032。
- 自動再起動の判定材料: daemon プロセスの終了の仕方（終了コードが 0 以外、またはシグナルによる終了）と起動期限の超過だけを用い、`StartupFailureKind` による分岐を作らない。粒度は判定材料の指定まで。理由は launchd の `KeepAlive`（`Crashed` / `SuccessfulExit`）と実機のアプリの作法に合わせるため。関係: R-018、B-017 / B-018 / B-020 / B-021。
- daemon の親プロセス終了時の終了経路: 一括停止（`ShutdownCoordinator`）を経由しない。daemon が起動した terminal と provider のプロセスの片付けは、一括停止の外で行う。粒度は一括停止を使わないという指定まで。理由は一括停止が `ReconciliationRequired` で利用者の判断を必要としうるため。関係: R-005、B-005。
- 更新に伴う停止・再起動は既存の `ShutdownCoordinator` と統合する。粒度は統合先の指定まで。理由は一括停止の経路を二重に作らないため。関係: R-021 / R-024 / R-026、B-025 / B-027 / B-030。
- updater は UI shell に残し、Rust の切替制御と連携させる。粒度は配置の指定まで。関係: R-021 / R-023、B-025。
- 起動監督・期限・再試行の判断、切替状態、停止完了の判定、起動対象・接続先の検証は Rust が所有する。粒度は所有者の指定まで。理由は `AGENTS.md`「Rust がロジックを所有する」。関係: R-015 から R-020、R-023、B-017 から B-024。
- CLI に daemon を単体起動する入口を作らない。粒度は入口の有無まで。関係: R-014、B-015 / B-016。

## 変えないもの

- 一括停止（`ShutdownCoordinator`）の停止段階、期限、`RecoveryAction` の規則そのもの。更新・再起動は既存の一括停止へ統合し、停止の経路を二重に作らないため。
- daemon 側の単一インスタンスの担保は、現行の local event store の writer lock のままとする。新しい排他機構を追加しない。固定ポートの bind が data_dir 単位の排他にならないため。

## 未確定・リスク

- 自動判断（Requirements の Assumptions に記録）: R-015 が列挙する失敗の段階のうち「起動後の異常終了」だけ、段階と理由の表示を判定する受入条件が無かったため、B-020 へ段階と理由の表示を追加し、対応表の R-015 の行に B-020 を加えた。
- 自動判断（Requirements の Assumptions に記録）: R-025 が列挙する 3 つの失敗のうち「接続先またはリリースの不一致」だけ、終了できることを判定する受入条件が無かったため、B-023 と B-024 へ終了できることを追加し、対応表の R-025 の行に B-023 と B-024 を加えた。
- 未決のまま残した要求は無い。`[DEFERRED]` で人間へ渡した件も無い。
- R-005 / B-005 は、一括停止を経由せずに daemon が起動した terminal の PTY と provider のプロセスを終了させることを求めるが、開始状態でこれらを片付ける経路は一括停止の中にしかない。一括停止の外で同等の片付けが成り立たない場合、B-005 の「UI のない daemon とその子プロセスは残らない」を満たせない。
- R-015 / B-018 は、クライアント ws が確立しない状態で backend の初期化失敗の段階と理由を UI が表示することを求めるが、開始状態では失敗の分類と correlation id が daemon の stderr と local log に留まり、終了コードは 7 種のいずれでも 1 で区別できない。UI が取得できる経路が無い場合、B-018 を満たせない。
- R-027 / B-031 は #1201 が定めた結果不明の規則を daemon の再起動と切替をまたいで成立させることを求めるが、開始状態には backend のプロセスを再起動する経路自体が無く、#1201 R-011 / B-013 は実際にプロセスを再起動した状態で未確認である（`docs/specs/issues-1201/requirements.md`）。
