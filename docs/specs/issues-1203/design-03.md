## 変える部分

- 起動・停止・切替の受理判断と失敗分類の所有: 停止完了・異常終了・期限超過の分類と、Quit と Update / Restart の停止完了の扱いを domain の判断として実行経路に置き、usecase が結論を自ら評価して domain へ渡す形を無くす。根拠: Thread `1910f237`（受入条件は、起動・停止・切替の受理判断と失敗分類が domain の判断として実行経路にあり、表示用の phase 文字列が独立した判断の正本にならないこと）。ルート: 委任
- 状態の再取得が完了するまでの操作受付の停止: 接続の検証と必要な状態の再取得が実際に完了するまで、通常の操作を受理せずキューにも入れないようにする。応答を受け取っただけで再取得完了とみなさない。根拠: Thread `e047d2e8`、R-023「切替の間、UI は通常の操作を受け付けない。新 daemon が Ready に達し、接続先とリリースの一致と認証済みのクライアント ws 接続を確認し、必要な状態を再取得した後に受付を再開する」、B-025 / B-030。ルート: 委任
- 更新のインストール中の終了要求の期限: 更新のインストールが戻らない場合でも、Quit と OS 起因の終了要求が有限時間で完了し、UI と daemon の両方が終了し、ログアウト・再起動・システム終了が妨げられないようにする。根拠: Thread `6b1ef363`、R-006「一括停止が有限の期限内に完了しない場合も、UI と daemon は終了する」、R-029、B-006 / B-033。ルート: 委任
- desktop client gateway の台帳と受付判定の所有: 未送信・結果不明・上限到達の判定を domain の規則として実行経路に置き、gateway が socket / reply ハンドルを越えた自前の台帳と受付判定を持たないようにする。根拠: Thread `9b7b197a`（受入条件は同判定が domain の規則として実行経路にあり、gateway が自前の台帳と受付判定を持たないこと）。ルート: 委任
- desktop client gateway の依存方向と handoff 手順: wire から domain への共有変換が controller 内部実装への依存にならないようにし、handoff の記録・破棄を usecase の責務として実行する。根拠: Thread `1760c30d`（受入条件は共有変換が controller 内部実装への依存にならず、handoff の記録・破棄が usecase の責務として実行されること）。ルート: 委任
- ログイン項目の登録・解除の可否の所有: 登録・解除の可否を domain の規則で説明できるようにし、OS 情報の取得と、その情報に対する判断の所有を分ける。根拠: Thread `3b33b0cc`（受入条件は登録・解除の可否が domain の規則で説明でき、OS 情報の取得と判断の所有が分かれていること）。ルート: 委任
- 承認待ち状態の意味づけの所有: `SMAppService` の承認待ち状態を内側の意味へ写す変換の所有者を一つにし、登録処理の成功条件を gateway の状態対応から追えるようにする。根拠: Thread `c72c3681`（受入条件は同変換の所有者が一つであり、登録処理の成功条件を gateway の状態対応から追えること）。ルート: 委任
- 監督の受理規則からの Tauri 入口名の除去: 入口が表す操作の意味と監督状態を受理判定の入力にし、Tauri の公開 command 名そのものが domain の規則に入らないようにする。根拠: Thread `d5b1e9cc`（受入条件は操作の意味と監督状態が受理判定の入力となり、公開 command 名が domain の規則に入らないこと）。ルート: 委任
- 更新を伴わない Restart の失敗段階の表示: 後継 UI の起動に失敗したとき、更新適用の失敗ではなく、実際に失敗した段階と理由を表示する。根拠: Thread `e9d6564d`、R-026、R-025「失敗した段階と理由が表示され、利用者は原因を確認して終了できる」。ルート: 委任
- 接続に使わない endpoint RPC と資格情報転送の除去: `get_client_endpoint` RPC と、その URL / client token の renderer への転送を残さず、接続開始がその成否に依存しないようにする。根拠: Thread `fb616b0c`（受入条件は同 RPC と転送が残らず、接続開始がその成否に依存しないこと）。ルート: 委任
- 効果のない `binaryType` の除去: 受信形式に影響しない `binaryType` プロパティと、その代入を残さない。根拠: Thread `7d2cf803`（受入条件は同プロパティと代入が残らないこと）。ルート: 委任
- `start_minimized` の mirror の除去: 本番動作で読まれない `start_minimized` の mirror とその更新、およびその値だけを確かめる検証を残さない。根拠: Thread `86e9d4de`（受入条件は同 mirror・更新・検証が残らないこと）。ルート: 委任
- 終了バナーのインライン描画フォールバックの除去: `container` 未指定のインライン描画分岐と、その旧契約を対象にするテストを残さない。根拠: Thread `297f1d6f`（受入条件は同分岐と旧契約依存のテストが残らないこと）。ルート: 委任。取り除く対象は当該インライン描画フォールバックと、それを対象にするテストの旧契約依存（`[FIX_POLICY]` が明示）。取り除き方とテストの書き換え方は委任
- ログイン項目の登録希望と実状態の規則の所在: 実状態と保存する登録希望の区別、およびどちらを永続化するかの規則を Rust に置き、同じ backend 操作を別の client surface から使っても同じ結果になるようにする。根拠: Thread `031fe129`、R-030。ルート: 委任
- 利用者向けガイドの設置契機の記述: ガイドの記述を現在の設置契機（設定での明示操作）と一致させ、その操作に到達できる案内にする。根拠: Thread `7381bf20`、R-034、B-040 / B-041。ルート: 委任
- OS 起因の終了の受入経路の検証: 稼働中の UI と daemon がある状態で OS 起因の終了要求が届き、一括停止を経て両プロセスが終了し、ログアウト・再起動・システム終了が妨げられないことを検証できるようにする。根拠: Thread `c56535b7`、B-033 / R-029。ルート: 委任
- 実行中 workflow を含む更新の一連の順序の検証: 一括停止、旧 daemon の終了確認、更新の適用、新 daemon の Ready と接続先・リリースの一致確認、必要な状態の再取得までの順序を、受入経路として検証できるようにする。根拠: Thread `47f8f92e`、B-025、R-021 / R-023。ルート: 委任
- 実 UI の強制終了を起点とする終了の検証: 実 UI プロセスの強制終了を起点に、daemon と子孫が終了し、`Releash.app` を起動するまで自動で起動し直されないことを検証できるようにする。根拠: Thread `3da32a69`、R-005 / B-005、R-012 / B-013。ルート: 委任
- 起動待ちの表示の検証: 起動待ちの状態で起動中であることを示す表示が出ることを component テストで検証し、その表示を取り除くとテストが失敗するようにする。根拠: Thread `735485ae`、B-036 / R-031。ルート: 委任
- 起動時に CLI を設置しないことの検証: 起動時に設置処理や管理者認証が再導入された場合にテストが失敗する、実際の設置境界に対する検証にする。根拠: Thread `ab09a220`、B-040 / R-034。ルート: 委任
- 非同期の送信失敗の分類の検証: desktop 送信境界からの非同期の `not_sent` と `unknown` が、それぞれ未送信と結果不明へ分類されることを検証でき、分類を入れ替える回帰でテストが失敗するようにする。根拠: Thread `8fefa1c7`、R-027 / B-031。ルート: 委任
- ws 接続だけを失った場合の監督の検証: daemon プロセスが生存したまま ws 接続だけを失った場合に、通常の操作受付が止まり、同じ子への再接続が行われ、期限超過時は子の終了確認の後に再起動されることを検証できるようにする。根拠: Thread `95cfd747`、B-002 / B-019、R-023。ルート: 委任

## 固定するルート

- 今周新たに人間が指定したルートは無い。
- Design 02 で固定した次のルートは今周も維持する。ログイン項目の操作は `SMAppService` の `register()` / `unregister()` / `status()` だけを使い、`launchctl` の `enable` / `disable` / `print-disabled` を呼ぶ経路を作らない。承認を必要とする状態（requiresApproval）は「無効」として扱い、承認が必要な旨と System Settings への導線を表示し、起動経路はこの状態で失敗させない。後方互換のための機能を追加せず、既存の後方互換経路も残さない。
- Design 01 で固定し Design 02 でも維持した次のルートは今周も維持する。LaunchAgent は `SMAppService` の agent 方式を使い plist を `.app` の `Contents/Library/LaunchAgents/` に同梱する。launchd の `KeepAlive` は付けない。単一インスタンスは loopback ポートの bind を使わず、UI 側は既に動作している UI のアクティブ化、daemon 側は local event store の writer lock で担う。自動再起動の判定材料は daemon プロセスの終了の仕方と起動期限の超過だけとし、`StartupFailureKind` による分岐を作らない。daemon の親プロセス終了時の終了経路は一括停止（`ShutdownCoordinator`）を経由しない。更新に伴う停止・再起動は既存の `ShutdownCoordinator` と統合する。updater は UI shell に残し Rust の切替制御と連携させる。起動監督・期限・再試行の判断、切替状態、停止完了の判定、起動対象・接続先の検証は Rust が所有する。CLI に daemon を単体起動する入口を作らない。

## 変えないもの

- 最小化状態で起動の設定が有効なときは、daemon の起動完了を待つ間のウィンドウも作らない。R-009 と B-010 を変更しない。人間が維持すると決めた条件である。
- Design 01 の「変えないもの」を維持する。一括停止（`ShutdownCoordinator`）の停止段階、期限、`RecoveryAction` の規則そのものと、daemon 側の単一インスタンスを local event store の writer lock で担う点を変えない。

## 未確定・リスク

- 自動判断（Requirements の Assumptions に記録、前周から維持）: R-015 が列挙する失敗の段階のうち「起動後の異常終了」だけ、段階と理由の表示を判定する受入条件が無かったため、B-020 へ段階と理由の表示を追加した。人間の確認は済んでいない。
- 自動判断（Requirements の Assumptions に記録、前周から維持）: R-025 が列挙する 3 つの失敗のうち「接続先またはリリースの不一致」だけ、終了できることを判定する受入条件が無かったため、B-023 と B-024 へ終了できることを追加した。人間の確認は済んでいない。
- 未決のまま残した要求は無い。`[DEFERRED]` で人間へ渡した件も無い。
- 更新のインストール中の終了要求に与える期限は、Requirements が値を定めていない。R-006 の「一括停止の完了を待ってから終了する」と R-029 の「ログアウト、再起動、システム終了を妨げない」は、OS が終了要求に与える時間を超える期限を置くと同時には満たせない。この期限の想定が外れると、R-006 と R-029 の一方を満たせない。
