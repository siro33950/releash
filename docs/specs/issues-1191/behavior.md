# Behavior

要求 (`requirements.md`) を、実装詳細を含まない観測可能な振る舞いとして Gherkin で定義する。

本 Issue は不具合修正（回帰疑いを含む）であり、新機能の追加ではない。したがって振る舞い定義の中心は
「Codex backend との会話においてメモリが会話量に比例して際限なく蓄積しない」という観測可能な特性と、
「既存の機能的振る舞いが本修正によって変化しない」という不変条件である。

## 仮定

- メモリ挙動の観測は、OS のメモリ使用量（RSS 等）の推移、もしくはクラッシュ／強制終了の有無として外部観測可能なものとして扱う。
  「際限なく増加しない」は「会話量・ターン数の増加に対してメモリ使用量が概ね頭打ちになり、線形に蓄積し続けない」ことを指す。
- 「v0.3.53 相当の安定挙動」は、v0.3.53 ビルドが実測で安定基準として成立する場合にのみ比較基準として扱う。
  v0.3.53 でも同型の増大が観測される場合は、修正前 HEAD と修正後ビルドの比較を基準にする。
- 「単一ターンの大量出力」は、1 ターン内で大量のストリーミング delta・ツール出力・diff を生成するシナリオを指す。
- 「機能的振る舞いが変化しない」は、ストリーミング表示・イベント永続化・workflow 進行のうち、
  ユーザーまたはクライアントが外部から観測できる出力（表示内容・永続化されるイベント・進行状態）が修正前後で一致することを指す。
- 原因経路の特定結果は Spec ディレクトリ内（`design.md` 等）に文書化される前提とする。本 behavior では「文書化されていること」を観測点とする。

Feature: Codex backend 会話におけるメモリ枯渇問題の解消

  Background:
    Given Codex backend を用いた agent セッションが利用可能である
    And アプリは本 Issue の修正を適用済みのビルドで動作している

  Rule: 会話量が増えてもメモリが際限なく蓄積しない

    Scenario: 長時間会話を継続してもメモリが頭打ちになる
      Given Codex backend との会話を開始している
      When 多数のターンにわたって会話を継続する
      Then アプリのメモリ使用量は会話量に比例して際限なく増加しない
      And アプリはメモリ枯渇によってクラッシュ／強制終了しない

    Scenario: 単一ターンで大量出力を扱ってもメモリが無制限に蓄積しない
      Given Codex backend との会話で 1 つのターンを実行している
      When そのターン内で大量のストリーミング delta・ツール出力・diff が生成される
      Then 単一ターン内でメモリが無制限に蓄積してクラッシュに至ることはない

  Rule: ターンで蓄積した一時バッファはターン完了後に解放される

    Scenario: ターン完了で一時バッファが解放され後続ターンへ持ち越されない
      Given あるターンでストリーミングパーツ等の一時バッファが蓄積している
      When そのターンが完了する
      Then そのターンで蓄積した一時バッファは解放される
      And 解放されなかったバッファが後続ターンへ持ち越されることはない

    Scenario: emit／ブロードキャスト失敗時も一時バッファが無制限に積み増されない
      Given ターン進行中に emit／ブロードキャストが失敗する状況が発生する
      When 失敗が繰り返し発生する
      Then 一時バッファが解放されないまま無制限に積み増される経路は存在しない

  Rule: 修正後のメモリ挙動を妥当な基準で確認できる

    Scenario Outline: v0.3.53 が安定基準として成立する場合は基準ビルドと同等水準に収まる
      Given v0.3.53 ビルドと修正後ビルドが用意されている
      And v0.3.53 ビルドでは同一シナリオのメモリ使用量が概ね頭打ちになることが確認されている
      When 両ビルドに同一プロンプト <prompt> を Codex に投げる
      Then 修正後ビルドのメモリ使用量の推移は v0.3.53 ビルドと同等水準に収まる

      Examples:
        | prompt                       |
        | 長時間会話シナリオのプロンプト   |
        | 単一ターン大量出力のプロンプト   |

    Scenario: v0.3.53 でも増大する場合は修正前 HEAD との比較で解消を確認する
      Given v0.3.53 ビルドでも同一シナリオでメモリ使用量が際限なく増加することが確認されている
      And 修正前 HEAD ビルドで同じ増大またはクラッシュが再現している
      When 修正後ビルドで同一シナリオを実行する
      Then 修正後ビルドのメモリ使用量は会話量に比例して際限なく増加しない
      And 修正後ビルドではメモリ枯渇によるクラッシュが発生しない

    Scenario: 修正前にクラッシュした再現シナリオが修正後はクラッシュしない
      Given 修正前ビルドでクラッシュした再現シナリオが確立されている
      When そのシナリオ（長時間会話／単一ターンの大量出力）を修正後ビルドで実行する
      Then 修正後ビルドではメモリ枯渇によるクラッシュが発生しない

  Rule: 原因経路が特定・記録されている

    Scenario: 原因経路と、回帰か構造的問題かの判定が文書化されている
      Given 原因切り分けが完了している
      When 修正完了時点の Spec を参照する
      Then 原因経路が特定され記録されている
      And v0.3.53 では発生せず後続バージョンで発生する回帰なのか、v0.3.53 でも発生する既存の構造的問題なのかが記録されている
      And 回帰であることが確認された場合は、どのリファクタ（#1167 / #1175 等）で混入したかが記録されている

  Rule: 既存の機能的振る舞いが本修正によって変化しない

    Scenario: Codex 会話・ストリーミング表示・workflow 進行の外部観測可能な振る舞いが不変
      Given 修正前ビルドでの Codex 会話・ストリーミング表示・workflow 進行の出力が観測されている
      When 同一の操作を修正後ビルドで実行する
      Then ストリーミング表示・永続化されるイベント・workflow 進行状態は修正前と一致する
      And 機能的な退行は発生しない

    Scenario: 既存テスト・lint が green である
      Given 本 Issue の修正を適用済みである
      When 既存のテスト（cargo test / pnpm test）と lint（cargo clippy -D warnings / pnpm lint）を実行する
      Then すべて成功する

## Open Questions

- v0.3.53 が安定基準として成立するか。静的調査では v0.3.53 にも同型の蓄積経路が存在するため、実測で確認する必要がある。
