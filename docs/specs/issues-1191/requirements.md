# Requirements

## Type

不具合修正（回帰疑い。v0.3.53 以前からの構造的問題である可能性も含む）

## Goal

Codex backend との会話中に、OS のメモリ枯渇によってアプリがクラッシュ／強制終了する問題を解消する。当初は v0.3.53 → v0.3.55 の回帰として扱っていたが、v0.3.53 でも同型の蓄積経路が存在する可能性を調査対象に含める。

完了時には、Codex backend と長時間会話しても、また 1 ターン内で大量のストリーミング出力・履歴・diff を扱っても、アプリのメモリ使用量が会話の進行に比例して際限なく増加しない状態を目指す。v0.3.53 が実測で安定基準として成立する場合はその水準へ戻す。成立しない場合は、従来から存在する構造的な無制限増大経路として是正し、修正前 HEAD と比較して増大・クラッシュが解消していることを基準にする。

## Background

- v0.3.53 では発生せず、v0.3.55（現 main `e939a164`）で再現する回帰として報告された。ただし静的調査では、単一ターン内の巨大出力・diff・履歴 clone に関わる複数の蓄積経路が v0.3.53 にも存在するため、この前提は実測で確認する必要がある。
- 長時間会話だけでなく、1 ターンのみでクラッシュするケースも報告されており、**単一ターン内でイベント／履歴／delta／diff を大量に複製・蓄積するパス**が疑われる。
- v0.3.53..HEAD で Codex backend 自体への直接変更はなく、クリーンアーキテクチャへの大規模リファクタ 2 件（`0d9d529e` workflow ドメイン移行 #1167、`e939a164` leaf ドメイン6種移行 #1175）が回帰の混入元として疑われていた。ただし app-server 化そのものは v0.3.53 以前に含まれており、v0.3.55 だけの原因とは見なしにくい。
- 初期調査で、`codex_app_server.rs` の `pending_approval_methods` クリア漏れは v0.3.53 以前から存在する既存バグであり、本問題の主因ではないと除外済み。

### 初期コード調査で観測された蓄積候補（仮説。原因特定で裏付け／棄却する）

- `infrastructure/agent_session/runtime/bridge_common.rs` の `streaming_parts`（`Vec<MessagePart>`）が **ターン単位で累積**し、リセットが「次ターン開始時」のみで、emit 失敗時の pending バッファ保持と相まって単一ターン内で無制限に増大しうる。
- 同 `prepare_streaming_flush` / `consolidate_parts` が flush のたびに `streaming_parts.clone()` を行い、大規模メッセージで複製コストが嵩む。
- `usecase/workflow/event_draft.rs` 等で run 全体のイベント履歴を読み込み、payload を clone するパスがあり、run が長くなるほどメモリ確保が増える。

> 上記はあくまで初期仮説であり、本 Spec の受け入れ基準は「特定の行の修正」ではなく「メモリ枯渇問題が解消されること」を基準とする。

## Users / Actors

- Releash で Codex backend を用いて会話・タスク実行するエンドユーザー
- Releash 内で agent セッション（AgentChat / workflow）を進行するバックエンド
- 原因切り分け・検証を行う開発者

## Scope

- Codex backend との会話で発生するメモリ枯渇クラッシュの**原因特定**（v0.3.53 と v0.3.55 のメモリ挙動比較、v0.3.53 が安定基準として成立するかの確認、疑わしいリファクタまたは従来から存在する構造的経路の切り分け、原因経路の特定）。詳細な候補（C1〜C10）と切り分けは `design.md` に記録する。
- 本 Issue では、振る舞い不変・低リスクな**メモリ純粋削減（A群: C2 / C3 / C4 / C7 / C8 / C9）をまとめて実装**する。同じ外部出力をより少ないメモリ／複製で生成する是正に限定する。C8（workflow turn complete 時の Text 全体 clone）は唯一の実回帰差分のため優先する。
- 問題が解消したことを確認するための検証手段の整備（メモリ挙動の比較確認、再現手順の確立）。

### スコープ外（別 Issue へ分離）

ライフタイム/解放の設計判断を要し、表示・永続化・履歴復元の振る舞いに影響しうる候補（B群）は本 Issue から分離し、個別 Issue で対応する。

- **C1（ターン完了時に `streaming_parts` を解放）→ #1194**
- **C6（フロント全メッセージ保持の退避/仮想化）→ #1195**
- **C10（terminal 後の workflow execution 解放）→ #1196**

方針: 先に A群を実装し実測する。クラッシュ・メモリ増大が解消しきらない場合は、診断で支配的と判明した B群 Issue を後追いで対応する。

## Non-goals

- Codex 以外の agent backend に固有のメモリ問題の調査・修正（本問題の原因が共通経路にある場合に副次的に解消されるのは可）。
- クリーンアーキテクチャ・リファクタ（#1167 / #1175）の全面的な巻き戻し（問題解消に必要な範囲を超えた revert は行わない）。
- `pending_approval_methods` クリア漏れ等、本 Issue の主目的ではない既存バグの修正（別 Issue として扱う）。
- ストリーミング表示やイベント永続化の機能仕様そのものの変更・再設計。
- メモリ使用量の新規モニタリング機能・常設プロファイラの製品化。

## Requirements

- A群（C2/C3/C4/C7/C8/C9）の純粋削減が実装され、Codex backend との会話・単一ターンの大量出力において、メモリの複製・蓄積・ピークが有意に低減されること。
- emit／ブロードキャストの失敗時にも、一時バッファが解放されず無制限に積み増される経路が増幅されないこと（cumulative ペイロードの再送に伴う `streaming_parts` の伸長を A群削減で抑制する）。
- 原因経路が特定され、文書化されていること（`design.md` の候補 C1〜C10 と切り分け）。回帰であることが実測で確認できた場合は混入元も記録する。v0.3.53 でも同型の増大が確認された場合は、従来から存在する構造的問題として記録する。
- 既存の Codex 会話・ストリーミング表示・workflow 進行の機能的な振る舞いが、本修正によって変化しないこと（A群は出力不変の削減に限定する）。

> ターン完了後の一時バッファ解放（C1）・会話全体での無制限蓄積の根治（C1/C6/C10）は本 Issue の範囲外とし、#1194 / #1195 / #1196 で扱う。本 Issue 単体での目標は「メモリ増幅の有意な低減＋退行なし」であり、クラッシュ完全解消は必要に応じて分離 Issue と合わせて達成する。

## Constraints

- 問題解消に必要な範囲に修正を限定し、クリーンアーキテクチャの構造そのものを不必要に変更しないこと。
- ストリーミング表示・イベント永続化・workflow 進行の外部から観測できる振る舞いを変えないこと。
- 既存のテスト（`cargo test` / `pnpm test`）および lint（`cargo clippy -D warnings` / `pnpm lint`）が通ること。
- 原因が複数経路にまたがる場合でも、本 Issue では Codex 会話のメモリ枯渇クラッシュ解消を主目的とし、無関係なリファクタを混在させないこと。

## Success Criteria

- A群（C2/C3/C4/C7/C8/C9）の削減が実装され、修正前 HEAD と修正後ビルドの比較で、Codex 会話・単一ターン大量出力時のメモリ複製／ピーク／蓄積が有意に低減することを実測で確認できる。
- 原因経路（候補 C1〜C10）が特定・記録されている。回帰であることが実測で確認できた場合は、それがどのリファクタ（#1167 / #1175 等）で混入したかも記録されている（C8 は #1167 由来の実回帰差分として裏取り済み）。v0.3.53 でも再現する場合は、既存の構造的問題として記録されている。
- 既存の Codex 会話・ストリーミング・workflow の機能的振る舞いに退行がない（A群は出力不変の削減に限定。既存テスト・lint が green）。

> 再現シナリオ（長時間会話／単一ターンの大量出力）でのクラッシュ完全解消は、本 Issue の A群削減のみでは達成されない場合がある。その場合は診断で支配的と判明した分離 Issue（#1194 / #1195 / #1196）を後追いで対応して達成する。

## Open Questions

- v0.3.53 が実測で安定基準として成立するか。静的調査では v0.3.53 にも同型の蓄積経路が存在するため、実測で確認する必要がある。
