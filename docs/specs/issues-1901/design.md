# Design

パスは、`proto/`・`.github/`・`AGENTS.md`・`releash-desktop/` で始まるもの以外は `src-tauri/src/` 起点。

## 変える部分

- 実行の状態の購読: 購読の対象 `workflow-execution:<execution_id>` を足し、`WorkflowExecutionView` を「無い」付きで配信する。根拠: R-001「実行の ID を指定して…購読でき」、B-001、B-002。ルート: 対象は `SubscriptionTarget::WorkflowExecution(String)`（`usecase/state_subscription/target.rs:5-40` の並び、文字列の対応は `adaptor/presenter/state_subscription_target.rs:33-103` の並び）。`StateValue::WorkflowExecution(Option<ExecutionTree>)` は Entity を持ち（`value.rs:22` の `Selection` と同じ並び）、wire への変換は presenter（`adaptor/presenter/workflow.rs:6-` の `workflow_execution_to_view`）が行う。wire は `NullableWorkflowExecutionView`（`NullableWorkflowDto` と同じ作り）を足し、`StatePayload` の 62 番に置く。`WorkflowExecutionView`（`proto/client.proto:1373-1391`）は残す。読み直しは `StateChangeSource::Worktree(_)` のどれでも（`target.rs:146-151` の `AgentSession(_)` と同じ並び）。ID の形が不正なとき（`ExecutionTreeId::new` の失敗）は今の読み取りの失敗（`StateReadFailure`）の経路。
- output の取得の購読: 購読の対象 `workflow-output:<execution_id>:<node_name>` を足す。根拠: R-002「提出済み…未提出…実行が無い」、B-003〜B-005。ルート: `SubscriptionTarget::WorkflowOutput(String, String)`、`StateValue::WorkflowOutput(Option<WorkflowGetOutputResult>)`（`usecase/workflow/query_service.rs:31-40` の型をそのまま持つ。実行が無い＝`None`）。読み取りは `usecase/workflow/output.rs:80-118` の `get_output`。Node が定義に無いとき（`:89-95`）は読み取りの失敗。wire は `WorkflowOutputView`（submitted／not_submitted。中身は今の `WorkflowGetOutputResponse`・`WorkflowGetOutputResponseSubmitted` と同じ）と `NullableWorkflowOutputView` を足し、`StatePayload` の 63 番に置く。読み直しは `WorkflowExecution` と同じ。
- 単発の取得と validate の削除: `WorkflowGetOutput` と `WorkflowValidateOutput` を削除する。根拠: R-010、B-015。ルート: RPC（`proto/client.proto:2604-2605`）、`WorkflowGetOutputRequest`・`WorkflowGetOutputResponse`・`WorkflowGetOutputResponseSubmitted`・`WorkflowValidateOutputRequest`・`WorkflowValidateOutputResponse`・`WorkflowValidateOutputResponseInvalid`（`:2257-2297`）、handler（`adaptor/controller/client/workflow/shared.rs` の `workflow_get_output`・`workflow_validate_output` の登録、`adaptor/controller/client/workflow/output.rs:79-` の 2 関数）、変換（`adaptor/presenter/client/conversions.rs:3351-3370` ほか）、この RPC だけが使う usecase のメソッド（`usecase/workflow/mod.rs:447-455` `WorkflowUsecase::validate_output`、`usecase/workflow/output.rs:30-39` `WorkflowOutputUsecase::validate_output`）を消す。`CommandRequest`／`CommandResult` の oneof の 180・181 は番号と名前を reserved にする。`validate_with_context`（`usecase/workflow/output.rs:58-78`）と HTTP の validate（`adaptor/controller/api/workflow.rs:265-283`、`validate_output_for_contract`）は残す。
- worktree を要求しない output の提出: `WorkflowSubmitOutputRequest` の `worktree_path` を削り、worktree の認可を外す。根拠: R-003、B-006。ルート: RPC と型は同じまま、field 1（番号と名前）を reserved にする（`proto/client.proto:2251-2255`）。認可の関数（`adaptor/controller/client/workflow/output.rs:19-39`、`usecase/workflow/mod.rs:275-333` の `authorize_execution_summary_for_worktree`・`authorize_execution_access_for_worktree`・`authorize_node_execution_access_for_worktree`）と、それだけを確かめるテスト（`usecase/workflow/mod_test.rs:531-557`、`:597-`）を消す。認可の関数を消すと呼び出し元が無くなる `authorize_execution_summary` と `WorkflowUsecase::get_execution`、本番の呼び出し元が無くなる `WorkspaceTreeRepository::load_node_by_node_execution_id`（trait・gateway の実装・`usecase/workspace_tree/test_support.rs` の実装）も、cfg で残さずに削除する。`load_node_by_node_execution_id` を使っていた受け入れの helper（`workflow_control_plane_acceptance.rs` の `workspace_node_status`）は、既存の読み取りで同じ情報を得る形に変える。`resolve_worktree_path` は残す（`usecase/workflow/workspace_tree.rs` から呼ばれている）。
- 優先度の表: 削除する RPC の名前を外し、足す RPC を段に入れる。根拠: R-009、R-010。ルート: `adaptor/controller/daemon.rs:8-26` の `client_priority_level`。`WorkflowValidateOutput`・`WorkflowGetOutput` を外し、`ReceiveProviderSignal` を "workflow" に入れる。ほかに足す RPC は "default"。
- directory を指定した診断: `DiagnoseWorkflowDirectory(DiagnoseWorkflowDirectoryRequest) returns (DiagnoseWorkflowDirectoryResponse)` を足す。根拠: R-004、B-007。ルート: request は `dir`（必須、絶対 path）、response は `DiagnosticReport report = 1;`。scope は operator。生成 handler に載せる（`CommandRequest`／`CommandResult` に足す）。対象は `WorkflowDiagnosticsTarget::from_optional_directory`（`usecase/workflow/ports.rs:103-114`）で作り、相対 path は今の `WorkflowError::Validation`。存在の検査は足さない（gateway の `adaptor/gateway/workflow/diagnostics_gateway.rs:32-45` が `WorkflowError::NotFound` を返し、`adaptor/presenter/connect.rs:252` が `NotFound` にする）。診断は同期の処理なので、既存の Connect の command と同じく blocking の包み（`adaptor/controller/client/worktree_mutation.rs:19` の `spawn_blocking`）で呼ぶ。
- review の書き手と worktree の解決: 入力を「Session の ID」か「worktree の path」として受けて (worktree, 書き手) を決める処理を usecase に 1 つ置き、review の Session の形と path の形の入口は全てこれを使う。根拠: R-005〜R-008。ルート: 今の CLI の規則（`cli/review.rs:110-131` 変更は Session が open であることを要求、`:133-163` 読み取りは lifecycle を見ない、`:179-210` path の形は `workspace_worktree_path` で解決し書き手は人）をサーバ側の usecase に移す。「書き手として使えるのは open な Session」という判断は controller に書かない。open でないときの失敗は、`InvalidInput` を使い回さず状態による拒否と分かる値で `ReviewError`（`domain/comment/mod.rs:316-324`）に足し、`adaptor/presenter/connect.rs:148-158` の対応に `FailedPrecondition` を足す。CLI の解決（`cli/review.rs`）は #1902 まで残る。
- review の一覧の購読（Session の形）: 購読の対象 `review-session-threads:<session_id>[:file=…][:state=…][:author=…][:unread=…][:thread=…]` を足す。根拠: R-005、B-008。ルート: 絞り込みは domain の `apply_filter`（`usecase/comment/mod.rs:79-93` の `list_threads` が `validate_filter`→`apply_filter`）で行う。引数は `notion-tasks` と同じ接頭辞付きの可変長（`adaptor/presenter/state_subscription_target.rs:85-87`、`:181-222`）。並び順は file、state、author、unread、thread の 1 通りで、thread は ID の昇順・重複なし。それ以外の並びは `from_parts` の往復の検査（`:20-22`）で `InvalidId` になる。値（`open|resolved`、`self|other`、`true|false`）の解釈は domain の値の parse にし、対象の解釈から呼ぶ（`ReviewBase::parse`／`ReviewSection::parse`、`:79-88` の先例）。Session が無いときは「無い」を配信する（wire は `NullableListReviewThreadDto` を足し、`StatePayload` の 64 番）。読み直しは `StateChangeSource::ReviewComments(_)` のどれでも。監視の要求（`usecase/state_subscription/target.rs:76-79` の `WatchRequirement::Files(review_comments_dir, ReviewComments(None))`）も付ける。
- review の一覧の購読（path の形）: 購読の対象 `review-worktree-threads:<path>[:file=…][:state=…][:thread=…]` を足す。根拠: R-006、B-009。ルート: path は workspace の worktree に解決する（`adaptor/gateway/workflow/worktree_context.rs:114-150` の `workspace_worktree_path_with`。通常の path は `:118-120` でそのまま、隔離 worktree の path は `:121-149` で親に寄せる）。解決できないときは読み取りの失敗。書き手は人。対象の型は author・unread を持てない形にし、対象の解釈の段階で拒否する。配信は既存の `StateValue::ReviewThreads`／`StatePayload.review_threads`（32 番）を使う。並び順・値の解釈・読み直し・監視の要求は Session の形と同じ。
- review の Thread と履歴の購読: 購読の対象 `review-session-thread:<session_id>:<thread_id>` と `review-session-thread-history:<session_id>:<thread_id>` を足す。根拠: R-007、B-010。ルート: Session の lifecycle は見ない。Session または Thread が無いときは区別せず「無い」。`StateValue` は Entity（`ReviewThread`、`Vec<ReviewHistoryEntry>`）を `Option` で持つ。wire は `NullableReviewThreadDto`、`ReviewHistoryEntryDto`（4 種の oneof。項目は今の `usecase/comment/dto.rs:166-204` と同じ）、`ListReviewHistoryEntryDto`、`NullableListReviewHistoryEntryDto` を足し、`StatePayload` の 65・66 番に置く。読み直しと監視の要求は Session の形の一覧と同じ。
- Session を指定した review の変更: `CreateSessionReviewThread`・`AppendSessionReviewComment`・`ResolveSessionReviewThread` を足す。根拠: R-008、B-011、B-012。ルート: request はそれぞれ `session_id`＋（`file_path`、`line_number`、`end_line`、`content`）／（`thread_id`、`content`）／（`thread_id`、`outcome`、`summary`）。response は `ReviewThreadDto thread = 1;`。scope は operator。生成 handler に載せる。Session が無いときは `NotFound`。既存の `CreateReviewThread`・`AppendReviewComment`・`ResolveReviewThread` は変えない。
- review の読み書きが返す型: review の usecase と `StateValue` は Entity（`ReviewThread`、`ReviewHistoryEntry`）を返す・持ち、Entity から転送の形への変換を presenter に置く。根拠: R-016「CLI と hook の振る舞い（出力の形を含む）は変わらない」、docs/architecture/USECASE.md「`From<Entity> for Dto` を書きたくなったら、向き（ドメイン起点）が誤っているサイン」。ルート: `usecase/comment/dto.rs` の `ReviewThreadDto`・`ReviewHistoryEntryDto` と Entity からの `From`（`:206-`）を usecase から無くし、転送の形として要るものは presenter に移す。既存の `StateValue::ReviewThreads`（`usecase/state_subscription/value.rs:50`）も Entity を持つ形に変える。参照元（本番）: `adaptor/controller/client/comment/commands.rs:7,25,36,49,60,74,86`、`adaptor/presenter/client/conversions.rs:1526-1529,2813-2815`、`cli/review.rs:14,315,358,392`、`integration_test_support.rs:356`、`usecase/comment/mod.rs:12`、`usecase/state_subscription/reads.rs:9,320`、`usecase/state_subscription/value.rs:4,50`。テスト: `tests/internal/cli_review.rs:15,668`、`tests/internal/usecase_comment_mod.rs:18,669`。controller は usecase の戻り値を presenter に渡すだけにする。画面と CLI の `--json` のキー名と値は変えない。
- provider の信号の RPC: `ReceiveProviderSignal(ReceiveProviderSignalRequest) returns (ReceiveProviderSignalResponse)` を足す。根拠: R-009、B-013、B-014。ルート: request は `provider`（既存の `AgentSessionProviderDto`、`proto/client.proto:821-828`）、`slot_id`、`binding_id`、`capability`、`agent_session_id`、`bytes payload`。response は oneof で applied／duplicate／rejected（理由）／ignored。scope は hook だけ。`api/client_service.rs` の手書きの handler にし（`get_server_info` と同じ並び。生成された prost の型を直接読む）、`CommandRequest`／`CommandResult` には足さない。handler は「65,536 byte を超えたら `InvalidArgument`（usecase を呼ぶ前）→ 引数への変換 → usecase の生の payload を受ける入口 → presenter で応答に変える」だけにする。SessionStarted が適用されたときの計測は、HTTP の handler（`adaptor/controller/api/provider_lifecycle.rs:38-55`）と同じ包み方にする。
- payload の解釈: domain の `provider_lifecycle` に解釈の trait を置き、今の `parse_provider_payload`（`adaptor/gateway/provider_lifecycle/payload.rs:21-`）を gateway でその実装にする。根拠: R-009。ルート: trait の戻り値は「信号」か「subagent の payload だった」という事実の 2 通りを domain の型で返す。事実を「無視」に結び付けるのは domain／usecase 側で、`ProviderLifecycleIngressResult`（`domain/provider_lifecycle/value_objects/provider_lifecycle_ingress_result.rs:4-8`）に `Ignored` を足す。gateway の `SubagentPayload` のエラーで無視を決める形（`payload.rs:29-31`）はやめる。usecase の ingress（`usecase/provider_lifecycle/ingress.rs`）に生の payload を受ける入口を足し、解釈 → 既存の `receive` の順に呼ぶ。解釈できない payload は `InvalidArgument`。trait の名前に「Gateway」「Port」を使わない。CLI（`cli/hook.rs:60-64`）は、戻り値の形が変わる分だけ追従する（振る舞いは変えない。解釈の実装は 1 つのまま）。
- method の scope: proto に scope を書き、付け忘れをビルドで落とす。根拠: R-011、B-016、B-017。ルート: `proto/client_options.proto` に `enum Scope { SCOPE_UNSPECIFIED = 0; SCOPE_OPERATOR = 1; SCOPE_HOOK = 2; }` と `extend google.protobuf.MethodOptions { repeated Scope scope = 51040; }` を足す（`:41` の `repeated ReconnectStatusCode` と同じ書き方）。`GetServerInfo` は operator と hook、`ReceiveProviderSignal` は hook、ほかの全 RPC は operator。`build.rs` の method の走査（`:96-101`）で、集合が空・`SCOPE_UNSPECIFIED` を含む・同じ値の重複がある method があればビルドを失敗させる。
- scope の判定: token を照合している認証の middleware（`require_client`、`adaptor/controller/api/auth.rs:62-143`）の中で、token の scope を決めた直後に、path の method が受け付ける scope の集合と比べ、入っていなければ拒否する。根拠: R-011、B-016。ルート: Connect の router 全体に掛かっている位置（`adaptor/controller/api/mod.rs:51-53`）で判定し、生成・手書き・streaming を区別しない。順序は 認証・scope → 同時実行の枠 → 受付。どの token とも一致しなければ今と同じ 401（`adaptor/presenter/api_error.rs:26-32`。既存の確認は `tests/client_api/mod.rs:72-92`）、scope が合わなければ Connect のクライアントが `PermissionDenied` として受け取る応答にする。path の method が ClientService に無いときは、token の照合（どれかの token と一致すること）だけを行って通し、connectrpc の応答（`Unimplemented`）に任せる（#1902 の互換の前提「同じメジャー版の中でサーバが新しい RPC を知らない場合は…その RPC だけ `Unimplemented` になる」を崩さないため。proto にある method の付け忘れは `build.rs` で落とす）。`DaemonAdmission`（`api/client_admission.rs`）と `Daemon::admits`（`domain/daemon/mod.rs:66-69`）は変えない。本文の「`build.rs` の method 走査で生成 handler に判定を埋め込む。手書きの RPC は個別に付ける」とは違う形にする。理由は、認証の置き場所が router 全体に掛ける 1 か所と決まっており（docs/architecture/CONTROLLER.md「認証は `api/mod.rs` が router 全体へまとめて掛ける」）、そこで判定すれば全 RPC に 1 か所で掛かるため。
- hook の token: 起動ごとに 1 つ作ってメモリに持ち、agent の起動の env で渡し、停止時に失効させる。根拠: R-012、B-018。ルート: 作るのは配線（Main）で、サーバの bind（`adaptor/controller/daemon.rs:482`）より前。agent の起動の gateway（`adaptor/controller/agent_session_wiring.rs:317`、`daemon.rs:241` の `compose_agent_sessions` から組み立てる）とサーバの両方に渡す。文字列は今の `generate_token`（`infrastructure/local_api/server.rs:227-`）で作る。持ち方は、照合と失効を持つ今の型（`infrastructure/local_api/client_token.rs`）と同じ。失効は client の token と同じ所（`server.rs:183-184`）。env の名前は `RELEASH_PROVIDER_LIFECYCLE_TOKEN` で、`adaptor/gateway/provider_lifecycle/launch_spec.rs:93-110` の並びに足す。ファイルには書かない。ファイルに書かれないことの確認は、「変えないもの」の env の経路を読んで行い、data dir を走査して無いことを確かめるテストは作らない（docs/architecture/TEST.md「削除済み機能が存在しないことを確かめるテスト」に当たる）。
- token の型の名前: `ClientBearerToken` を `BearerToken` に変える（中身は変えない）。根拠: R-012、R-013（operator と hook の token を同じ型で持つ）。ルート: 変えるのはこの型の名前だけで、`terminal_token`／`terminal_bearer_token` などの周りの名前には広げない。
- Origin: 付いていなければ通し、Rust 側の名乗りをやめる。根拠: R-014、B-020。ルート: `adaptor/controller/api/auth.rs:62-143` で、Origin があるときは今のまま（allowlist、CORS の header）、無いときは Origin の検査を飛ばして token・scope の検査に進み、CORS の header（`:131-141`）を付けない。OPTIONS で Origin が無いときは preflight として扱わず token の検査に回す。名乗りを消すのは `releash-desktop/src/adaptor/gateway/desktop_client.rs:81` と `client_api_acceptance.rs:207`。既存のテストは、`adaptor/controller/api/auth_test.rs:170` の `(None, "client", FORBIDDEN)` を「Origin なし＋正しい token が通り、CORS の header が付かない」に、同じ表の行と断定で合わせる（新しいテストは足さない）。`releash-desktop/tests/internal/daemon_supervision.rs:45` の origin の断定はその 1 行を消す（残りの断定は残す）。
- buf の設定: リポジトリ直下に `buf.yaml`（v2）を置く。根拠: R-015、B-022、B-023。ルート: `modules: [{path: proto}]`、`lint.use: [STANDARD]`、`breaking.use: [WIRE_JSON]`。今ある違反は `lint.ignore_only` で、違反している規則 ID ごとに違反しているファイルだけを並べて外す（ENUM_VALUE_PREFIX、ENUM_VALUE_UPPER_SNAKE_CASE、RPC_RESPONSE_STANDARD_NAME、RPC_REQUEST_RESPONSE_UNIQUE、ENUM_ZERO_VALUE_SUFFIX、RPC_REQUEST_STANDARD_NAME は `client.proto`、PACKAGE_DIRECTORY_MATCH は `client.proto` と `client_options.proto`）。規則ごと・区分ごとの `except`／`ignore` は使わない。`buf format` は入れない。
- CI: `quality` の job（`.github/workflows/ci.yml:444-468`）に `bufbuild/buf-action` の step を 1 つ足す。根拠: R-015、B-022。ルート: action の版はメジャー版の指定（`ci.yml` のほかの action と同じ書き方）。buf の版は `version: 1.47.2` で固定する（`ignore_only` の内訳と比較先の挙動を確かめた版。版が変わると STANDARD に入る規則が変わりうる。`ci.yml` が `ast-grep@0.40.0` を固定しているのと同じ扱い）。`input: proto`、`lint: true`、`format: false`、`push: false`、`archive: false`、`pr_comment: false`。breaking は action の既定（pull_request で `buf skip breaking` ラベルが無いとき）で、比較先は action の既定（`input` を指定すると、PR の base の commit の `subdir=proto` と比べる。buf-action `src/inputs.ts` の `getInputs`）。`pull_request` の types は変えない。
- AGENTS.md: hook の token の文と buf のコマンドを足す。根拠: R-017、B-025。ルート: セキュリティの該当行を「local API の master token を renderer JS へ渡さない。hook の token はファイルに書かず、provider の agent を起動する env だけで渡す。terminal 用は別 token を使う。」にする（元の文は master token が #1902 まで残るので消さない）。「ビルド・テスト・Lint」の品質ゲートの並びに `buf lint` と `buf breaking --against '.git#branch=main,subdir=proto'`（プロジェクトルート）を足し、CI が使う buf の版（1.47.2）を書き、近くに `buf skip breaking` ラベルを効かせる手順（ラベルを付けてから次の commit を push する、または PR を閉じて開き直す）を 1 文で書く。ほかの文（「CLI / hook 用は HTTP local API」など）は残す。
- 生成物: proto の変更に合わせて `src/generated/` を `pnpm generate:protocol`（`package.json:9`）で作り直す。根拠: R-015、R-016。ルート: 委任。

## 固定するルート

- 足す proto の要素は STANDARD の命名に従う: RPC ごとに `<Rpc>Request`／`<Rpc>Response` を持ち、enum の値は `ENUM_NAME_` 接頭辞付きの UPPER_SNAKE_CASE で 0 番は `_UNSPECIFIED`（先例 `proto/client.proto:2810-2817` の `ServingStatus`）。wire の message の名前は周りの並びに合わせる（workflow は `…View`、review は `…Dto`）。
- 既存の RPC の request・response の型は差し替えない（`RPC_SAME_REQUEST_TYPE`／`RPC_SAME_RESPONSE_TYPE` に当たる）。既存の RPC を変えるときは、型は同じままフィールドを reserved にして削る。
- 削除するフィールド、oneof の項目は番号と名前の両方を reserved にする（`proto/client.proto:6-74` と同じ書き方）。proto に RPC の reserved は無いので、RPC の削除は `CommandRequest`／`CommandResult` の oneof の番号と名前を reserved にすることで表す。
- 「無い」は失敗ではなく状態で配信する（`usecase/state_subscription/value.rs:24` `AgentSession(Option<…>)`、`:52` `Workflow(Option<…>)` と同じ）。引数の形の誤りと、後から変わらない定義との不一致は読み取りの失敗にする。
- usecase（`StateValue` を含む）は presenter の型を持たない。wire への変換は presenter が行う。
- 読み取りは購読、変更と入力に対する計算は単発の呼び出しにする（AGENTS.md「通信の原則」）。
- 判断（Session が書き手として使えるか、subagent の payload を無視するか）は controller・gateway に書かず、domain／usecase に置く。
- breaking の比較は `proto` の中どうしで行う。理由: main には `buf.yaml` が無く、リポジトリ直下を比較先にすると module root がリポジトリ直下として組み立てられ、`proto/client.proto:3` の `import "client_options.proto"` が解決できず失敗する（`buf breaking --against '<repo>/.git#branch=main'` → `import "client_options.proto": file does not exist`。`subdir=proto` を付けると通る。releash-e7 が buf 1.47.2 で確認）。

## 変えないもの

- HTTP `/v1`、`require_bearer`、master token と `local-api.json`、HTTP の validate（呼び出し側が contract を指定する意味論）、CLI と hook のプロセス側の振る舞い（`cli/`）。#1902 まで CLI と hook がこれを使い、マイルストーン #100 の「どの ISSUE の後でも CLI・hook が動く」を保つため。CLI 側の値の解釈（`cli/review.rs:241-272`）と存在の検査（`cli/diagnostics.rs:49-56`）、hook の health ファイルの読み書き（`cli/hook.rs:124-170`）も #1902 の範囲として残す。

- 発見ファイルの名前と形（`client-api.json`、`local-api.json`）と、画面側の検査（`adaptor/gateway/local_api.rs:196-236`）。

## 未確定・リスク

- 実行の ID・Session の ID で引く購読の対象（`workflow-execution`、`workflow-output`、`review-session-threads`、`review-worktree-threads`、`review-session-thread`、`review-session-thread-history`）は、購読している間、関係ない worktree（または review comment）の変化でも 1 度読み直す。`workflow-output` は読み直すたびに、その実行の event を 1 度全部読む（`usecase/workflow/output.rs:85`）。#1902 の CLI は最初の状態を受け取って閉じるので、今は読み直しが起きる使い手は無い。
- `buf skip breaking` ラベルは、buf-action が event の payload の `github.event.pull_request.labels` から読む（buf-action `action.yml` の `breaking` の既定）。job の再実行は元の event の payload を使うため、後から付けたラベルは再実行では効かない。
