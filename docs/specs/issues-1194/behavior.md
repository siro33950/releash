# Behavior

要求 (`requirements.md`) を、実装詳細を含まない観測可能な振る舞いとして Gherkin で定義する。

本 Issue はメモリ削減（不具合修正）であり、新機能の追加ではない。したがって振る舞い定義の中心は
「Codex backend との会話で、ターン完了後にアイドルとなった session が完了ターン分のストリーミング parts を
常駐させ続けない」という観測可能な特性（R1）と、
「ストリーミング表示・イベント永続化・履歴復元・workflow 通知の外部振る舞いが本修正によって変化しない」という
不変条件（R2/R3）である。

## 仮定

- 「外部から観測可能な振る舞い」とは、フロントへ送出される emit イベント内容、SessionStore へ永続化される
  メッセージ内容、履歴復元時に再現されるメッセージ内容、workflow turn-complete 通知の内容を指す。
  内部のバッファ構造・複製回数・メモリ常駐量はこれに含めない。
- R1 の「完了ターン分のストリーミング parts が常駐し続けない」ことは、テストまたはコード上の不変条件
  （ターン完了後に当該バッファが空である／保持されない）として外部観測する。本 behavior では
  「ターン完了後に完了ターン分の累積 parts が当該 session に保持されないこと」を観測点とする。
- 「アイドル session」とは、ターンが完了した後に次のターンが開始されていない状態の session を指す。
- 「post-turn イベント」とは、ターン完了後に到着するバックグラウンドタスクのツール完了・status 等の
  イベントを指す。
- close（明示クローズ）経路では既にプロセスが管理対象から除去され解放されるため、本 Issue の主対象は
  「アイドル session の常駐」であり、close 経路は新規対象としない。
- 実メモリ計測（RSS 等の比較）は C1 解放の有効性を補助的に確認するものであり、本 Issue 単体の必須合格条件
  ではない。中核の合格基準は R1〜R5（常駐経路の解消・外部振る舞いの不変・既存テスト/lint green）とする。

Feature: ターン完了後のストリーミング parts 常駐メモリ解放（Codex backend）

  Background:
    Given Codex backend を用いた agent セッションが利用可能である
    And アプリは本 Issue（C1）の修正を適用済みのビルドで動作している

  Rule: ターン完了後にアイドルとなった session は完了ターン分のストリーミング parts を常駐させない

    Scenario: ターンが完了し次ターンが来ない session で完了ターン分の parts が解放される
      Given Codex backend との会話で 1 つのターンを実行し、ストリーミング parts が蓄積している
      When そのターンが完了し、次のターンが開始されない（アイドル状態になる）
      Then 完了ターン分の累積ストリーミング parts は当該 session に常駐し続けない

    Scenario: 会話・session 数が増えても完了済みターン分の parts が累積し続けない
      Given 複数の Codex session でそれぞれ複数のターンを完了させている
      When いずれの session も次ターンが来ないアイドル状態のまま会話・session 数が増える
      Then 完了済みターン分のストリーミング parts が解放されず累積し続ける常駐経路は存在しない

  Rule: ターン完了時にフロントへ送出される確定メッセージは本変更の前後で変化しない

    Scenario: ターン完了時の確定メッセージの emit／永続化が修正前と一致する
      Given 修正前ビルドでのターン完了時の確定メッセージ（emit／永続化される内容）が観測されている
      When 同一のターンを修正後ビルドで完了させる
      Then フロントへ emit される確定メッセージの内容は修正前と一致する
      And SessionStore へ永続化されるメッセージの内容は修正前と一致する

    Scenario: ターン完了時の workflow turn-complete 通知が修正前と一致する
      Given 修正前ビルドでの workflow turn-complete 通知の内容が観測されている
      When 同一のターンを修正後ビルドで完了させる
      Then 送出される workflow turn-complete 通知の内容は修正前と一致する

  Rule: ターン完了後に到着する post-turn イベントの表示・永続化が本変更の前後で変化しない

    Scenario: 解放後に到着した post-turn イベントが既存メッセージに正しく反映される
      Given あるターンが完了し、完了ターン分の確定 parts が解放されている
      When そのターン完了後に post-turn イベント（ツール完了・status 等）が到着する
      Then post-turn イベント反映後に表示・永続化される最終メッセージ内容は修正前と一致する
      And post-turn イベントが既存メッセージの確定内容を欠落・上書き・重複させることはない

    Scenario: 複数の post-turn イベントが連続して到着しても最終メッセージが一致する
      Given あるターンが完了し、完了ターン分の確定 parts が解放されている
      When 複数の post-turn イベントが連続して到着する
      Then 反映後に表示・永続化される最終メッセージ内容は修正前と一致する

  Rule: 履歴復元時に再現されるメッセージが本変更の前後で変化しない

    Scenario: ターン完了・post-turn 反映後の会話を履歴から復元しても内容が一致する
      Given ターン完了および post-turn イベント反映を含む会話が永続化されている
      When その会話を履歴から復元する
      Then 復元されるメッセージ内容は修正前ビルドで復元した場合と一致する

  Rule: 本変更は C1 の範囲に限定され、既存の機能的振る舞いを退行させない

    Scenario: ストリーミング表示・イベント永続化・履歴復元の外部振る舞いが不変
      Given 修正前ビルドでの Codex 会話のストリーミング表示・イベント永続化・履歴復元の出力が観測されている
      When 同一の操作を修正後ビルドで実行する
      Then ストリーミング表示・永続化されるイベント・履歴復元されるメッセージは修正前と一致する
      And 機能的な退行は発生しない

    Scenario: 既存テスト・lint が green である
      Given 本 Issue の修正を適用済みである
      When 既存のテスト（cargo test / pnpm test）と lint（cargo clippy -D warnings / pnpm lint）を実行する
      Then すべて成功する

    Scenario: 新規ロジックに正常系・post-turn 追記エッジのテストが追加されている
      Given 本 Issue で C1 解放のロジックを追加・変更している
      When 追加されたテストを実行する
      Then ターン完了時の解放（正常系）と、解放後の post-turn 追記（エッジ系）の両方が検証される

  Rule: 修正後のメモリ解放を補助的に実測で確認できる（任意・確認用）

    Scenario: 修正前 HEAD と修正後ビルドの比較で完了ターン分の常駐メモリ解放を確認する
      Given 修正前 HEAD ビルドと修正後ビルドが用意されている
      When 長時間アイドルを含む会話進行シナリオを両ビルドで実行する
      Then 修正後ビルドでは完了ターン分のストリーミング parts に相当する常駐メモリが解放される
      And この実測はクラッシュ完全解消の保証ではなく C1 解放の有効性確認に用いる
