# Requirements

## Goal

`app_config` ドメイン（アプリ設定／トークン管理／TOML 永続化の各責務）と `mcp` ドメイン（MCP サーバの起動・停止・状態保持・ツール提供の各責務）を、`docs/architecture/` のクリーンアーキテクチャ規約に従ったレイヤー構成へ移行する。

完了時には、これらの責務がドメイン層・ユースケース層・アダプタ層・インフラ層の各規約に沿って配置され、ファイルシステム（TOML 設定ファイル）・HTTP サーバ（rmcp / axum）・Tauri 等の外部リソースへの依存がインフラ／ゲートウェイ層に閉じ込められた状態になる。あわせて旧構成のモジュール（`src-tauri/src/config.rs`、`src-tauri/src/mcp/`）が除去され、これらの責務がレイヤー規約に違反せず単一クレート内で再利用可能になっていることを成功とする。本移行を通じて、フロントエンド・リモートクライアントから見える設定および MCP サーバの基本機能は引き続き提供される。重複実装の整理等の移行作業に伴ってユーザー側の振る舞いに多少の変更が生じることは許容する。

本バッチは Issue #1169（[移行バッチ] config 系移行）として、子 Issue #979（`app_config`）と #976（`mcp`）を 1 PR にまとめて遂行する。

## Background

現状、`app_config` 関連のロジックは `src-tauri/src/config.rs`（約 1.4k 行）に、`mcp` 関連のロジックは `src-tauri/src/mcp/`（`mod.rs`／`server.rs`／`mcp_json.rs`／`state.rs`／`auth.rs`、合計約 1.9k 行）に、レイヤー分離のない構成で実装されている。設定構造体の定義・TOML シリアライズ／デシリアライズ・トークン生成・ファイル I/O が `config.rs` に集約され、MCP サーバの起動／停止・rmcp ハンドラ実装・JSON 変換・認証ミドルウェアが `mcp/` 配下に混在している。Tauri コマンドや WebSocket ハンドラからの呼び出しと密結合している。

この状態には以下の課題がある。

- ドメインロジックがファイルシステム・HTTP サーバ実装・Tauri に直接依存しており、CLI 等の別エントリポイントから再利用できない。
- ビジネスルールとインフラ詳細が同一モジュールにあるため、ドメイン単位のテストが書きづらい。
- 単一責務に基づくファイル分割が徹底されておらず、責務の所在が追いにくい。

リポジトリ全体で進行中のクリーンアーキテクチャ移行（マイルストーン「[12] クリーンアーキテクチャ移行」）の一環として、`app_config` および `mcp` ドメインを規約準拠の構成へ移行し、上記課題を解消する。先行事例として #977（`agent_session`）・#978（`pty_session`）のパターンを踏襲する。

## Users / Actors

- Releash デスクトップアプリを利用するエンドユーザー（アプリ設定 UI および MCP サーバ機能の利用者）
- リモートクライアント（モバイル／タブレット）から WebSocket 経由で設定を参照／変更する利用者
- 外部 MCP クライアント（Claude Desktop 等）から MCP サーバへ接続するツール
- `app_config` / `mcp` ドメインの機能を将来再利用する別エントリポイント（CLI 等）
- 本コードベースを保守する開発者

## Requirements

- `app_config` ドメインの各責務（設定値の保持・読込・書込・トークン生成等）が、`docs/architecture/` の各層規約に従って配置されること。
- `mcp` ドメインの各責務（MCP サーバの起動／停止・状態管理・ツール提供・認証）が、同規約に従って配置されること。
- ドメイン層が外部リソース（ファイルシステム・HTTP サーバ実装（rmcp／axum）・Tauri 等）を直接参照しないこと。
- ユースケース層がドメイン層の抽象（trait）のみに依存し、具体的な外部リソース実装に依存しないこと。
- 外部リソースへのアクセスが、ドメインが定義する抽象の実装としてゲートウェイ／インフラ層に閉じ込められること。
- Tauri コマンド／WebSocket ハンドラが、ユースケースを呼び出す薄い入口に徹すること（ビジネスロジックを持たないこと）。
- 移行対象の責務について、ドメイン層・ユースケース層・ゲートウェイ層のテストが存在すること。
- 移行後、旧構成の対応モジュール（`src-tauri/src/config.rs`、`src-tauri/src/mcp/`）が除去され、同一責務の重複実装が残らないこと（no-shim）。
- 本ドメインの Tauri コマンドが、起動時 DI 配線に整合して `register` 関数経由で登録されること。
- 移行後も、エンドユーザー・リモートクライアント・外部 MCP クライアントから見える基本機能（設定の参照／更新／永続化、MCP サーバの起動／停止／状態取得、外部クライアントへのツール提供等）が引き続き提供されること。重複実装の整理等の移行作業に伴ってユーザー側の振る舞いに多少の変更が生じることは許容する。

## Constraints

- レイヤー間の依存方向が規約（`infrastructure → adaptor（controller / gateway / presenter）→ usecase → domain`、依存は内向きのみ）に従い、逆方向（内側の層が外側の層に依存する向き）の依存を生まないこと。
- 既存の CI 品質チェック（フロントエンド lint／test／build、Rust fmt／clippy／test）が移行後も通過すること。
- 子 Issue #979（`app_config`）と #976（`mcp`）を分割せず、1 goal / 1 PR としてまとめて移行する。

## Scope

- Issue #979 が定める `app_config` の責務（`src-tauri/src/config.rs` 配下のロジック）を、クリーンアーキテクチャ規約に従ったレイヤー構成へ移行する。
- Issue #976 が定める `mcp` の責務（`src-tauri/src/mcp/` 配下のロジック）を、同規約に従ったレイヤー構成へ移行する。
- 上記責務に対応するドメイン層（エンティティ・値オブジェクト・永続化／外部リソースの抽象・ドメインサービス）を新構成で実装する。
- 上記責務の Command 側・Query 側ユースケースを新構成で実装する。
- 上記責務に対する外部リソース（ファイルシステム、rmcp／axum による HTTP サーバ、認証）アクセスの具体実装を、ドメインが定義する抽象の実装としてゲートウェイ／インフラ層に配置する。
- 上記責務に対応する Tauri コマンドを、ユースケースを呼び出す薄い入口としてアダプタ層へ再配置する。
- WebSocket 入口が存在する場合は、薄いハンドラとしてアダプタ層へ再配置する。
- ドメイン層・ユースケース層・ゲートウェイ層に対するテストを追加する。
- 移行完了後、旧構成の対応モジュール（`src-tauri/src/config.rs`、`src-tauri/src/mcp/`）を除去する。
- 本ドメインに属する Tauri コマンドの登録方式を、アプリ起動時の DI 配線に整合させる（`lib.rs` の `invoke_handler!` を `register` 関数経由に置き換え）。
- 移行の進行を妨げる既存 `docs/architecture/` 規約の不整合・曖昧さを、規約の意図を変えない範囲で修正・明確化する。
- 本移行の遂行に必要な範囲で発生する周辺整理（共有ユーティリティ・共有型の整理、依存先ドメインとの境界調整等）。

## Non-goals

- `app_config`・`mcp` 以外のドメイン（`agent_session`、`pty_session`、`repository`、`code`、`notion` 等）の移行。本移行ではこれらを依存先として参照するのみとする。
- 設定機能および MCP サーバ機能そのものの仕様追加・機能拡張（新しい設定項目の追加、新しい MCP ツールの追加、認証方式の変更等）。
- フロントエンド／リモートクライアント側のコード変更（移行に伴う必要な追従を除く）。
- 外部 MCP クライアントから見える MCP プロトコル仕様の変更。
