# Design

パスは `src-tauri/` を起点とする（`package.json`、`scripts/`、`tests/*.mjs`、`wdio.*.conf.ts`、`.github/`、`docs/`、`AGENTS.md` はリポジトリ直下）。行番号は main d5ee057c 時点。シェルのクレートのディレクトリを `releash-desktop/`（= `src-tauri/releash-desktop/`）と書く。

## 変える部分

- workspace 化: `Cargo.toml` を、root package がサーバのクレート（package 名 `releash-backend`、lib `releash_lib`、bin `releash-backend`）の workspace にし、`releash-desktop/` を member にする。`[workspace.package]` に版を置き、両方の package が `version.workspace = true` で継承する。`default-run` と GUI の bin `releash`（`Cargo.toml:8,19-21`）を root から外す。根拠: R-005、R-011、B-001、B-010。ルート: workspace の root は `src-tauri/` のまま。root package がサーバなので、`src-tauri/` でのフラグなしの cargo の実行はサーバだけが対象になる（https://doc.rust-lang.org/cargo/reference/workspaces.html）。サーバのコードの相対パス（`adaptor/gateway/workflow/builtin.rs` の `include_str!("../../../../../workflows/...")`、`CARGO_MANIFEST_DIR` 起点のテスト、`build.rs` の `../proto`）と、Cargo.lock・target の場所を変えない。Tauri CLI 2.12.1 は `[workspace.package]` の継承を読める（tauri-cli `interface/rust.rs` の `MaybeWorkspace`）。
- シェルのクレートの新設: `releash-desktop/` に package `releash-desktop`（lib と、GUI の bin `releash-desktop`）を置く。`src/main.rs`、`tauri.conf.json`・`tauri.conf.dev.json`・`tauri.conf.performance.json`、`capabilities/`、`icons/`、`launchagents/`、`Info.plist` をここへ移す。`mainBinaryName` は使わず、productName と identifier は変えない。根拠: R-005、R-009、B-008。ルート: Tauri CLI は cwd と `./src-tauri` に無ければ深さ `TAURI_CLI_CONFIG_DEPTH`（既定 3）まで tauri.conf.json を探す（tauri-cli `helpers/app_paths.rs`、https://v2.tauri.app/start/project-structure/）。`src-tauri/releash-desktop/tauri.conf.json` が既定の深さで見つかる根拠は「固定するルート」の「tauri.conf.json の探索」に書く。見つかる tauri.conf.json がリポジトリに 1 つだけであることを確かめる。`tauri_build::build()`・tauri.conf.json・capabilities/・gen/schemas は Tauri のクレートの package root が基準になる。main の bin は package 名と同じ名前の bin になる。公式は `mainBinaryName` より package 名か bin 名を変えることを勧めている（https://v2.tauri.app/reference/config/ の mainBinaryName）。
- シェルへ移すもの: 次をシェルのクレートへ移し、サーバのクレートから消す。`desktop.rs`（と `desktop_test.rs`）、`desktop_client_acceptance.rs`、controller の `command/`・`desktop_lifecycle`、`controller/application_lifecycle.rs` の `ApplicationQuitIngress`、presenter の `daemon_status`、gateway の `daemon_supervision`・`desktop_update`・`login_item`・`desktop_client`・`cli_install`、usecase の `client_connection`・`daemon_supervision`・`desktop_update`・`login_item`・`cli_install`・`test_helpers`、domain の `daemon_supervision`・`login_item`、infrastructure の `desktop_channel` と `platform` の `cli_install`・`desktop_restart`・`login_item`・`menu`・`native_drop`・`native_termination`・`single_instance`・`tray`・`window_lifecycle`、`tests/desktop_*.rs` と `tests/daemon_termination.rs`。`RetryBackoff::DESKTOP_POLL`（`common/retry.rs:19-21`）はサーバから消し、シェルに同じ値の定数を置く（`RetryBackoff::new` は `pub const fn`、`retry.rs:23`）。シェルの中での層の分け方は、今の層の分け方のまま移す。根拠: R-007、B-005。ルート: 委任。
- サーバに残して gate を外すもの: 別のクレートからは足せない次の項目を、サーバに残して `desktop` の gate を外す。`LocalLogProcess::Gui`（`infrastructure/local_log.rs:15-31`）、起動の計測（`StartupMetric::AppStartup`・`FirstWindowReady`、`metrics/attributes.rs:61-64,122-125`。`Startup` の再公開と `record_startup_from_origin`、`metrics/mod.rs:19,493-498`）、`matches_client`（`domain/daemon/identity.rs:31-34`）、`TryFrom<DesktopSettings> for DesktopSettingsDto`（`adaptor/presenter/client/mod.rs:135-150`）。根拠: R-007、B-005。ルート: enum の値・型のメソッド・サーバの型どうしの変換・サーバの非公開の部品を使う処理と、サーバの domain の規則は、サーバに残す。
- 発見ファイルから画面用の接続先を読む処理: `ClientConnectionFileQuery`（`adaptor/gateway/local_api.rs:189-240` 付近）が行う、発見ファイルの読み取り・形の検査・identity の照合（`daemon_identity`、`:252-260`、`matches_client`）は、サーバに残して関数として公開する。戻り値（url と token）とエラーはサーバ側の型にする。シェルへ移す `usecase::client_connection` の trait をサーバが実装する形はやめ、シェルの側がこの関数を自分の `ClientConnectionQueryService` に合わせる。根拠: R-005、R-007、B-001。ルート: サーバはシェルの型に依存しない。`adaptor/gateway/local_api_test.rs:478-` の断定は変えない。
- 生成コードの持ち方: 呼び出し表 `client_calls.rs` の生成はサーバの `build.rs` に残す。サーバのクレートの中の 1 つの非生成のモジュールで include し、`call` を公開の入口から見せる。`desktop_client.rs:460` と `client_api_acceptance.rs:462` の include はやめ、そのモジュールを使う。`tests/daemon_smoke.rs:28` は別のテストバイナリなので今の include のまま。`desktop_client.rs` の接続方針 `POLICY`（`:24-73`）はシェルへ移し、材料の descriptor の `pool`・`option` をサーバが見せる。根拠: R-006、B-005。ルート: build script の出力（OUT_DIR）は package ごとなので、生成した側のクレートが include して再公開する。同じ proto から 2 か所で生成しない。
- `COMMAND_NAMES` の生成: `build.rs:42` が `#[cfg(test)]` で生成している `COMMAND_NAMES` を、`#[cfg(any(test, feature = "test-support"))]` で生成し、公開の入口の `test-support` の区画から見せる。シェルのテスト（`adaptor/controller/command/mod.rs:154,243`、`command/client_test.rs` のうちシェルに残す部分）が使う。根拠: R-006、B-006。ルート: 使うのはシェルのテストだけなので、本番の区画には入れない。
- 公開の入口: サーバの lib（`lib.rs`）に、シェルが使う項目を再公開する公開のモジュールを 1 つ作る。項目は `pub` にし、層のモジュール（`adaptor`・`domain`・`usecase`・`infrastructure`・`common`）は非公開のままにする。並べる項目と、シェルで使う箇所は「固定するルート」の表のとおり。シェルのテストだけが使う項目は、同じモジュールの中の `cfg(feature = "test-support")` の区画に並べる。根拠: R-006、B-005、B-006。ルート: 「固定するルート」の表に無い項目を並べない。使う箇所の無い項目を並べない。
- feature `test-support`: サーバのクレートに `test-support`（`default` に入れない）を足す。シェルのテストが使うサーバの `#[cfg(test)]` の項目と、metrics・crash の `cfg(test)` の分岐を、`cfg(any(test, feature = "test-support"))` にする。対象は `telemetry/metrics/mod.rs` の `PERFORMANCE_CONFIGURED`・`PERFORMANCE_ENABLED`（`:23-26`）、`record_test_metric`（`:517-`）、`reset_test_metrics`（`:535-536`）、`test_metric_records`（`:547-548`）、`lock_test_telemetry`（`:560-561`）とその記録の分岐、`telemetry/crash.rs` の `reset_for_tests`（`:29-30`）と `tests` モジュールの `TEST_LOCK`・`install_test_exporter`（`:153-`、`:181`）。サーバ自身のテスト（`cfg(test)`）の振る舞いは今と同じにする。シェルは `[dependencies]` のサーバには付けず、`[dev-dependencies]` に同じサーバのクレートを `features = ["test-support"]` 付きで書く。根拠: R-006、B-006。ルート: resolver 2 は、test をビルドしないとき dev-dependency の feature を統合しない（https://doc.rust-lang.org/cargo/reference/resolver.html#features）。root package の edition は 2021（`Cargo.toml:6`）なので resolver は 2。確かめ方は `cargo tree -p releash-desktop -e features -i releash-backend`（本番）と、同じものに `-e features,dev` を付けた結果（テスト）の比較。`debug_assertions` は使わない（metrics の記録先が dev ビルドで変わるため）。
- 依存と feature: `desktop` feature と、サーバの `tauri`・`tauri-build`・tauri-plugin-*・objc2 系の依存（`Cargo.toml:32,37-43,93-95,99,102,110`）を消し、シェルのクレートの依存にする。`tauri` の dev-dependency（`test` feature）はシェルに置く。`staticlib`・`cdylib`（`Cargo.toml:17`）はサーバに付けず、シェルにも付けない。シェルに `vendored-openssl = ["releash-backend/vendored-openssl"]`、`performance = ["releash-backend/performance"]`、`performance-wdio = ["performance", "dep:tauri-plugin-wdio", "dep:tauri-plugin-wdio-webdriver"]` を置く。`deny.toml` を追従させる。根拠: R-001、R-002、R-015、B-001、B-002、B-014。ルート: `staticlib`・`cdylib` は Tauri のモバイル向けの要件（https://v2.tauri.app/start/migrate/from-tauri-1/#preparing-for-mobile）で、対応プラットフォームは macOS だけ（`AGENTS.md` のリリース節）。リポジトリにその出力を使う箇所は無い（`package.json`・`.github`・`scripts`・`tests` を `staticlib`・`cdylib`・`libreleash` で検索して該当なし）。
- `build.rs` の分割: サーバの `build.rs` は proto からの生成一式と telemetry の値の埋め込み（`build.rs:3-10`）を持つ。`tauri_build::build()`（`:11-12`）はシェルの `build.rs` へ移す。根拠: R-001、B-001。ルート: telemetry の値を読むのはサーバの `infrastructure::telemetry`（`env!`）で、シェルはサーバの lib 経由で使うので、埋め込みはサーバの 1 か所。
- テストの仕分け: 「固定するルート」のテストの仕分け表のとおりに、サーバのクレートのテストとシェルのクレートのテストに分ける。サーバへ移すテストは、Tauri の mock app を作らず、サーバの部品を直接組み立てる。`desktop_test_support.rs` の `build_client_dependencies`・`make_read_only_app`（`:26-73`）はサーバのテスト用の組み立てに置き換え、Tauri の state を使わない。`adaptor/controller/client/workflow/mod.rs:218,1289` の `app_config` 欄の gate を外す。根拠: R-008、B-004、B-007。ルート: 断定の式と期待値は変えない。
- シェルの統合テストのサーバの実行ファイル: `tests/desktop_daemon.rs:53,220,293`、`tests/desktop_status_channel.rs:59`、`tests/desktop_update.rs:139` の `env!("CARGO_BIN_EXE_releash-backend")` を、テストの実行ファイルの親の親（`target/<profile>/`）の `releash-backend` に置き換える。無ければ `cargo build -p releash-backend --bin releash-backend` を先に実行するよう示して失敗する。`tests/desktop_daemon.rs:68,233` の `CARGO_MANIFEST_DIR` の親（今はリポジトリのルート）は、深さが 1 段増えるので追従させる。根拠: R-013、B-012。ルート: テストの中から cargo を呼ばない。`CARGO_BIN_EXE_<name>` は同じ package の integration test にだけ設定される（https://doc.rust-lang.org/cargo/reference/environment-variables.html）。
- サーバの実行ファイルの同梱: `bundle.externalBin` に `binaries/releash-backend` を書き、.app を作るときだけ渡す設定ファイル（`releash-desktop/` に置く）に入れる。sidecar の元ファイルは `releash-desktop/binaries/` に書き出し、`.gitignore` に `src-tauri/releash-desktop/binaries/` を足す（externalBin のパスは tauri.conf からの相対）。基本の `tauri.conf.json` には書かない。sidecar の元ファイルは、その設定の `beforeBuildCommand` で `scripts/build-desktop-backend.mjs` が作る。`beforeBundleCommand`（`tauri.conf.json:10`、`package.json:33` のインライン JSON）はやめる。根拠: R-009、R-010、R-014、B-008、B-013。ルート: 「固定するルート」の同梱の経路のとおり。
- `scripts/build-desktop-backend.mjs`: arch ごとの `cargo build -p releash-backend --bin releash-backend --target <arch>` と universal の lipo（`:11-17`）を保つ。出力を sidecar の元ファイル `releash-desktop/binaries/releash-backend-<triple>` に書く（universal は `aarch64-apple-darwin`・`x86_64-apple-darwin`・`universal-apple-darwin` の 3 つ）。target と profile は今と同じく `TAURI_ENV_TARGET_TRIPLE`（`:7`）と `TAURI_ENV_DEBUG`（`:9`）で決める（beforeBuildCommand にも同じ値で渡る根拠は「固定するルート」の同梱の経路に書く）。`--manifest-path` と `--no-default-features` を追従させる。`--dev` の動き（`tauri dev` の前にサーバを `target/debug/releash-backend` にビルドする、`tauri.conf.json:7`）は保つ。根拠: R-010、R-012、B-008、B-011。ルート: 委任。
- GUI の実行ファイル名の追従: `launchagents/com.releash.app.plist:6-7` の `BundleProgram` と `ProgramArguments` を `releash-desktop` にする。`wdio.performance.conf.ts:6,52`、`wdio.client-streams.conf.ts:9`、`tests/helpers/desktop-bundle.mjs:41,52` を追従させる。根拠: R-009、B-009。ルート: 委任。
- CI: `rust-test-desktop`・`rust-test-headless`（`.github/workflows/ci.yml:216-316`）を、サーバのジョブとシェルのジョブに置き換える。サーバのジョブは `src-tauri/` でのフラグなしの cargo（Tauri の apt の依存と `--no-default-features` は不要）で、lib テスト・統合テスト・`state_subscription_scenarios`・`daemon_smoke` を走らせる。シェルのジョブは、先に `cargo build -p releash-backend --bin releash-backend` を実行してから `-p releash-desktop` の clippy・test を走らせる。`rust-lint` の `--no-default-features --bin releash-backend` の clippy（`:212-214`）はサーバのフラグなしの clippy に統合し、シェルの clippy（`test-support` ありの構成を含む `-D warnings`）を足す。集約ジョブ `rust`（`:320-337`）は、必須チェックの名前 `rust` を保ったまま、新しいジョブの結果で判定する。`rust-cache` の `workspaces`（`src-tauri`）は今のまま。nightly の `performance` ジョブ（`nightly.yml:100-108`）の lib テストは `--features performance --lib`（`--no-default-features` を外す）、`desktop_cli_install` は `-p releash-desktop --features performance --test desktop_cli_install`。`.github/scripts/workflows-test.mjs` の断定（`:55-96`、`:163-166`、`:210`、`:244-306`、`:435-437`、`:560-567`、`:912-918`、`:944-983`）を追従させる。根拠: R-003、B-003。ルート: サーバとシェルは cargo の実行を分ける（feature の統合を避ける。https://doc.rust-lang.org/cargo/reference/features.html#feature-unification）。
- coverage: nightly の coverage（`nightly.yml:168-169`）は、今と同じくサーバとシェルの両方のテストを対象にする。`src-tauri/` で `cargo llvm-cov clean --workspace`、`cargo llvm-cov --no-report --locked`（サーバ。サーバの integration test のために `releash-backend` が `target/llvm-cov-target/debug/` にビルドされる）、`cargo llvm-cov --no-report --locked -p releash-desktop`（シェル。前の実行で作られたサーバの実行ファイルを使う）、`cargo llvm-cov report --codecov --output-path rust-codecov.json` の順に実行する。`codecov.yml:26` の `rust` の flag の paths に `src-tauri/releash-desktop/src/` を足す。`workflows-test.mjs:258-283`（`:264` のコマンド、`:277` のアップロード）を追従させる。根拠: R-003、B-003。ルート: サーバとシェルを 1 回の実行にすると、サーバの実行ファイルに `test-support` が統合されるので、実行を分けて結果を合わせる（cargo-llvm-cov の README の「Merge coverages generated under different test conditions」）。
- 版上げ: `bump-version.yml:38-43`、`stable.yml:201-206` が、`src-tauri/Cargo.toml` の `[workspace.package]` の版と、Cargo.lock の `releash-backend`・`releash-desktop` の両方の行、`releash-desktop/tauri.conf.json` の版を書き換えるようにする。`stable.yml` の `add-paths` と、`workflows-test.mjs:560-567,944-983` を追従させる。`.github/dependabot.yml:4` の `directory: /src-tauri` は今のまま。根拠: R-011、B-010。ルート: 委任。
- そのほかのパスとコマンド: `package.json` の scripts（`:14,15,20,22,27,32,33`）、`tests/helpers/performance-daemon.test.mjs:30`、`tests/desktop-bundle.mjs:18-45`、`tests/desktop-login.mjs:52`、`scripts/generate-icons.sh:6`、`.gitignore:42-59`、`codecov.yml:26`、`AGENTS.md`（`:74-75` の実行ファイルの説明、`:100-145` のコマンド、`:193` の capabilities のパス）、`docs/architecture/README.md:3`、`docs/architecture/TEST.md:53` を追従させる。`AGENTS.md` に「サーバのクレートが Tauri に依存しない」の確かめ方（`cargo tree -p releash-backend -i tauri -e normal,dev,build --target all --all-features`）を、実装担当が実行して確かめた出力と終了コードとともに書く。根拠: R-016、B-015。ルート: 委任。

### tauri.conf.json の探索

- tauri-cli（tag tauri-cli-v2.12.1）`crates/tauri-cli/src/helpers/app_paths.rs:99-135` の `resolve_tauri_dir` は、`TAURI_APP_PATH`（無ければ cwd）を起点に、起点と `起点/src-tauri` に tauri.conf.json があるかを先に見る（`:102-118`）。無ければ `lookup`（`:59-87`）で起点から下へ探す。`lookup` は `ignore` crate の `WalkBuilder` に `max_depth(TAURI_CLI_CONFIG_DEPTH、既定 3)`（`:64-71`）を渡し、ディレクトリで tauri.conf.json を持つもの、または tauri.conf.json 自身を見つけた時点で返す（`:123-125`）。`WalkBuilder` の `max_depth` は walkdir の `max_depth` に渡され（tag tauri-cli-v2.12.1 の Cargo.lock の ignore 0.4.33、ripgrep の tag ignore-0.4.33 `crates/ignore/src/walk.rs:605-609`）、walkdir は起点を深さ 0、その直下を 1 と数える（同じ Cargo.lock の walkdir 2.5.0、`src/lib.rs:316-322`）。
- 起点がリポジトリのルートのとき、`src-tauri/`（深さ 1）には tauri.conf.json が無くなり、`src-tauri/releash-desktop/`（深さ 2、tauri.conf.json を持つディレクトリ）が見つかる。tauri.conf.json 自身は深さ 3 で、既定の上限の中にある。走査は `.gitignore` を読むので（`require_git(false)`、`:62`）、`src-tauri/target/` の中は探さない。
- `package.json` の scripts は、リポジトリのルートを cwd として `tauri` を起動する。tauri-action は `projectPath` を指定せず（既定はリポジトリのルート）、`tauriScript: pnpm tauri` で起動する（`nightly.yml:260`、`stable.yml:154`）ので、同じ探索になる。`TAURI_APP_PATH` は渡さない。

### サーバの実行ファイルの同梱の経路

- `bundle.externalBin` を使う。tauri-bundler（tag tauri-cli-v2.12.1）の `bundle/macos/app.rs` は、署名の対象に externalBin（`:99-104`）と package 自身の bin（`:106-110`）を足す。`bundle.macOS.files`（`:112` の `copy_custom_files_to_bundle`）と `bundle.resources` で実行ファイルを入れる形は採らない。
- externalBin は、.app を作るときに `tauri build --config <ファイル>` で渡す設定にだけ書く。`--config` は JSON Merge Patch で基本の設定に重なり（https://v2.tauri.app/develop/configuration-files/）、複数渡せる（tauri-cli `build.rs:58`、`helpers/config.rs:163-172`）。CLI は merge した値を環境変数 `TAURI_CONFIG` で渡し、tauri-build も同じ値を merge する（tauri-build 2.7.1 `lib.rs:656,682-685`）。基本の設定に書くと、sidecar のファイルが無いときに build script が失敗し（tauri-utils 2.10.1 `resources.rs:207`）、シェルのビルドのたびに `target/<profile>/releash-backend` が sidecar の元ファイルで上書きされる（tauri-build `lib.rs:140-163,293-301`）ので書かない。
- tauri-build は cargo の `TARGET` を付けた `releash-backend-<TARGET>` を探し（tauri-utils `resources.rs:46-60`）、universal のビルドでは arch ごとに cargo が走る。bundler は `releash-backend-universal-apple-darwin` を期待する（tauri-bundler `settings.rs:706-709`）。
- beforeBuildCommand と beforeBundleCommand は、どちらも同じ `helpers::run_hook`（tauri-cli `crates/tauri-cli/src/helpers/mod.rs:68-`）で、同じ `debug` と同じ interface から環境変数を作って起動される（`crates/tauri-cli/src/build.rs:203-209`、`crates/tauri-cli/src/bundle.rs:199-207`）。環境変数は `command_env(debug)`（`helpers/mod.rs:35-47`。`--debug` のとき `TAURI_ENV_DEBUG=true`）と `interface.env()`（`crates/tauri-cli/src/interface/rust.rs:294-297` の `TAURI_ENV_TARGET_TRIPLE` は `app_settings.target_triple`）。`target_triple` は `--target` の値そのもの（`rust.rs:1131`、interface は hook より前の `build.rs:113` で作られる）なので、`--target universal-apple-darwin` のときは `universal-apple-darwin` が渡る。hook の cwd はフロントエンドのディレクトリ（`helpers/mod.rs:80`）で、今と同じリポジトリのルート。beforeBuildCommand は cargo のビルドより前に走る。
- Merge Patch は値を置き換えるので、.app 用の設定の `build.beforeBuildCommand` は、フロントエンドのビルドを含める。`build:desktop:acceptance` は performance の設定（`tauri.conf.performance.json:6` の `pnpm build:performance`）と重ねるので、フロントエンドのビルドが `build:performance` のままになる形にする。
