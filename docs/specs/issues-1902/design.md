# Design

パスは、`proto/`・`.github/`・`scripts/`・`docs/`・`workflows/`・`AGENTS.md`・`releash-desktop/`・`releash-sdk/`・`releash/` で始まるもの以外は `src-tauri/src/` 起点。`releash-desktop/`・`releash-sdk/`・`releash/` は `src-tauri/` 起点。

## 変える部分

- 共有 crate の新設: `src-tauri/releash-sdk/`（package `releash-sdk`）を workspace に足し、proto からクライアント側のもの（prost の型、descriptor、Connect のクライアント）を生成して公開する。根拠: R-001「CLI の crate はサーバの crate に依存しない」。ルート: 型は 1 回だけ生成し、`releash-backend` はこの crate の型を使う（型を二重に生成しない）。サーバ側の生成（handler `client_service.rs`、command の codec `client_commands.rs`、scope の表 `client_scopes.rs`、`client_calls.rs`）は `releash-backend` の `build.rs` に残す。`build.rs` が descriptor を要るなら、同じ proto を自分で読んで作ってよい。
- 発見ファイルの読み取りと同一性の確認を共有 crate へ: `client-api.json` の読み取り（今の `infrastructure/local_api/client.rs:48-60` の読み方）と、指すプロセスが居るか・同一性が合うかの確認（`adaptor/gateway/local_api.rs:196-261` の `ClientConnectionFileQuery`・`assess_discovery`・`daemon_identity`、`infrastructure/local_api/discovery.rs:26-59` のプロセスの起動時刻の取得）を `releash-sdk` に置き、サーバと CLI が同じものを使う。根拠: R-003、R-005。ルート: 委任。
- 互換の判定: `Compatibility`（互換／サーバが古い／クライアントが古い）を `releash-sdk` に置く。根拠: R-004、B-003、B-004。ルート: 純粋な規則（値と判定だけ）。入力はクライアントの protocol（`releash-sdk` の descriptor の package `releash.client.v1` のメジャー版）と `ServerInfo.protocol`（`proto/client.proto` の `ServerInfo` field 8）。release は表示にだけ使う。
- CLI の crate の新設: `src-tauri/releash/`（package `releash`、bin `releash`）。依存は `releash-sdk` と外部 crate だけ。根拠: R-001、B-002。ルート: 今の `cli/` のコマンドと引数の定義を移し、`cli/` と `cli/` だけが使うもの（`render_long_help()`、`cli/api_client.rs`、`cli/file_direct.rs`、`cli/review.rs` のプロセス内組み立て、CLI の `--json` のためだけの serde の型）を `releash-backend` から消す。
- コマンドの流れ: 各コマンドは 発見 → `GetServerInfo` → 互換の判定 → 呼び出し の順で動き、状態を持たない。根拠: R-003。ルート: 読み取り（`workflow status`→`workflow-execution`、`output get`→`workflow-output`、`review list`→`review-session-threads` か `review-worktree-threads`、`review get`→`review-session-thread`、`review history`→`review-session-thread-history`）は `OpenStateStream`＋`StartStateSubscription` で購読し、最初の状態（snapshot か failure）を受け取ったら閉じる（先例 `releash-desktop/src/adaptor/gateway/desktop_client.rs:254-330`）。変更（`WorkflowSubmitOutput`、`CreateSessionReviewThread`・`AppendSessionReviewComment`・`ResolveSessionReviewThread`）と診断（`DiagnoseWorkflowDirectory`）は単発の呼び出し。operator の token は `client-api.json` の token。review の絞り込みの引数は file→state→author→unread→thread の順に並べ、thread は ID の昇順・重複なしにしてから送る（`docs/specs/issues-1901/design.md` の購読の対象の並び）。
- 「無い」の扱い: 購読で「無い」（Nullable の値が空）を受けたら、CLI は code `not_found` の失敗にする。根拠: R-006、B-007。ルート: 委任。
- 値の検査の削除: CLI 側の値の検査（`cli/common.rs:118-133` の execution ID と node、`cli/review.rs:241-272` の state・author・unread、`cli/diagnostics.rs:49-57` の dir の存在、`cli/output.rs:56-60,149-156` の空文字の検査）を持たない。根拠: R-009、B-012。ルート: サーバの判定に任せる。clap で表せる引数どうしの関係（必須、排他、`--author`・`--unread` が `--session-id` を要ること）は clap で表す。`--dir` の相対 path は CLI の cwd で絶対 path にしてから送る（今の `cli/diagnostics.rs:39-47` と同じ。表示用の入力の整形）。`--file` の読み込みと JSON の parse は CLI が行う（入力の受付）。
- 出力: 既定は人向け、`--json` は今と同じキー名と値。根拠: R-010、R-011、B-013、B-014。ルート: 受け取った proto の値から今の形へ変える（表示用フォーマット）。今の形の正は、消す前の serde の型（`adaptor/presenter/workflow_wire.rs`、`cli/output.rs:184-197`、`adaptor/presenter/comment.rs`）と `docs/guide/cli.md`。`review history` の人向け表示の形は委任（Rust の `Debug` は出さない）。
- エラーと終了コード: エラーは stderr。`--json` のときは `{"error":{"code","message"}}`。終了コードは 0／1／2／3。根拠: R-012、R-013、B-015、B-016。ルート: `code` は Connect の標準コード名（`connectrpc` のエラーの code をそのまま名前にする）。届かないとき（発見ファイルが無い・古い・壊れている・接続できない）は `unavailable`、互換でないときは `failed_precondition`。2 は clap の引数の構文の誤りだけ。3 は `workflow diagnostics` の結果に severity error の項目が 1 件以上あるとき（今の `cli/diagnostics.rs:68-82` と同じ数え方）。
- `releash completion <shell>`: clap_complete で足す。根拠: R-014、B-017。ルート: 委任。clap_complete のライセンスが `src-tauri/deny.toml` の allow list に入っているかを確かめる。
- `--data-dir`: 全コマンド共通の global な引数。根拠: R-015、B-018。ルート: `--data-dir` ＞ `RELEASH_DATA_DIR` ＞ 既定。既定の data dir の名前と解決（今の `infrastructure/platform/path_aliases.rs:45-50` の `default_data_dir_name_for_profile`、`:111-115` の `default_data_dir_for_profile`）は `releash-sdk` に置き、サーバと CLI が同じ関数を使う。
- hook: stdin を 65,536 byte まで読み、env の slot・binding・capability・agent session と hook の token（`RELEASH_PROVIDER_LIFECYCLE_TOKEN`）で `ReceiveProviderSignal` を呼ぶ。根拠: R-016、B-019、B-020。ルート: payload は解釈しない（`cli/hook.rs:58-112` の解釈と変換は消す）。上限を超えたら送らない。結果に関わらず exit 0、失敗は stderr。health ファイルの書き込みと消去（`cli/hook.rs:136-146`、`:155-173`）はやめる。今の stdout の `{}`（`cli/hook.rs:28-33`）は維持する。
- 実行ファイルの経路: 根拠: R-002、B-001。ルート: wrapper の指し先を daemon の実行ファイルの隣の `releash` にする（`infrastructure/platform/path_aliases.rs:79-95` の `exe_path`）。`/usr/local/bin/releash` の symlink の指し先を Tauri シェルの隣の `releash` にする（`releash-desktop/src/infrastructure/platform/cli_install.rs:40-43`）。`scripts/build-desktop-backend.mjs` で `releash` も作って `binaries/` に置き（universal は lipo）、`releash-desktop/tauri.conf.bundle.json` の `externalBin` に足す。dev（`--dev`）でも `releash` を作る。
- HTTP の削除: `adaptor/controller/api/workflow.rs`、`api/provider_lifecycle.rs`、`api/auth.rs` の `require_bearer`（WebSocket subprotocol の対応を含む）、`api/mod.rs` の `authenticated`・`local_ingress`・`local_priority_level`、`api/protocol.rs` のうち HTTP だけが使うもの、HTTP だけが使う presenter（`api_response`、`provider_lifecycle_response`、`workflow_api` のうち使い手が無くなるもの）、`adaptor/gateway/local_api.rs` の `LocalApiClientGateway` と `LocalApiClientError`、`infrastructure/local_api/client.rs` の `LocalApiHttpClient`、それらのテスト。根拠: R-017、B-022。ルート: 消すと呼び出し元が無くなる usecase のメソッドと型も cfg で残さずに消す。
- master token と `local-api.json`: サーバは master token を作らず、`local-api.json` を書かない（`infrastructure/local_api/server.rs:56-80`）。根拠: R-017、B-022。ルート: 発見ファイルは `client-api.json` だけ（名前と形は変えない）。
- 画面側の追従: `ClientConnectionFileQuery`（`adaptor/gateway/local_api.rs:186-224`）は `client-api.json` だけを読み、2 つのファイルの instance と token を突き合わせる検査は消す。Tauri シェルの pid の読み取り（`releash-desktop/src/adaptor/gateway/daemon_supervision.rs:337-358`）は `client-api.json` を読む。根拠: R-018、B-022。ルート: シェルは `desktop_api` の再公開（`desktop_api.rs`）のまま使い、`releash-sdk` へ直接切り替えない。
- テストの移し替え: HTTP `/v1` を通しているテストを Connect 経由に移す。根拠: R-017、R-018。ルート: `workflow_control_plane_acceptance.rs:716-901` の start・status・submit・approve・retry・abort・resume は対応する Connect の RPC と購読（`StartWorkflow`、`workflow-execution`、`WorkflowSubmitOutput`、`ApproveWorkflowNode`、`RetryWorkspaceNode`、`AbortWorkflow`、`ResumeWorkspaceSessionNode`）。実行ログを読む `workflow_log`（`workflow_control_plane_acceptance.rs:751-754`。使い手は `tests/workflow_control_plane_acceptance_test.rs:367,412,440,1442,1472,1522,1545`）は、`execution_direct`（`:756-760`）と同じくサーバの読み取りを直接呼ぶ形に変え、Connect の入口は足さず、テストの断定も変えない。受け入れテストの harness の `report_unavailable`（HEAD の `provider_lifecycle_acceptance.rs:491-527`。HTTP `POST /v1/provider-lifecycle/unavailable`）は Connect に移さず、Connect に unavailable の入口も足さない（#1901 の決定）。unavailable を報告する本番の呼び出し元は HTTP の handler だけで、HTTP を消すと到達できなくなるため、報告の経路を消す（次の項目）。`workflow_diagnostics_acceptance.rs:314` は `DiagnoseWorkflowDirectory`。実バイナリを起動する `tests/workflow_diagnostics_cli_test.rs`・`tests/local_log_cli_regression_test.rs` は CLI の crate の統合テストへ移し、期待値は新しい要求（終了コード・code）に合わせる。診断の `--json` の互換性（R-010）は、valid と invalid の fixture について、CLI の `--json` の出力を固定の JSON と比べて確かめる。固定の期待値は、変更前（main `5f24cff2`）の CLI を同じ fixture で実際に動かして取った出力で、手で書き起こさない。CLI と同じ変換（`releash::json::from_message`）で作った値を期待値にしない。受け入れの harness だけが使う読み取りのために、本番から呼ばれないコードを cfg で残さない。harness が要る読み取りは最小のものに置き換えるか、確かめ方を変え、消したことで断定できなくなる事実は既存の別の読み取りで確かめる。
- unavailable の報告の経路の削除: 本番の呼び出し元が無くなる次のものを消す。`ProviderLifecycleIngressPort`（`usecase/provider_lifecycle/ingress.rs:91-98`、実装 `:400-424`）、usecase の `report_unavailable`（`ingress.rs:309-`、`usecase/provider_lifecycle/mod.rs:206-226`）、domain の `ProviderLifecycleSlot::report_unavailable`（`domain/provider_lifecycle/entities/provider_lifecycle_slot.rs:70-`）と `ProviderLifecycleBinding::mark_unavailable`（`provider_lifecycle_binding.rs:146-`）、それだけが書く binding の `unavailable` の状態（`provider_lifecycle_binding.rs:18,63,169-172,194`）、`ProviderLifecycleUnavailableObservation`（`domain/provider_lifecycle/value_objects/provider_lifecycle_unavailable.rs:13-`）、test-support 限定の replay の unavailable の分岐（`provider_lifecycle_binding.rs:371-382`。記録済みの event を replay で受けたときの扱いは委任）、受け入れテストの unavailable の断定（`tests/provider_lifecycle_acceptance_test.rs:491-517`）とそれだけが使う harness（`provider_lifecycle_acceptance.rs` の `report_unavailable`・`AcceptanceUnavailableReason`・その変換）、`integration_test_support.rs:432,442` の再公開。根拠: R-017（HTTP の入口が無くなる）、Requirements の Non-goals の但し書き。ルート: 次は本番で使われているので残し、#1877 に任せる。理由の値 `ProviderLifecycleUnavailableReason`（`provider_lifecycle_unavailable.rs:5`）、記録済みの event の型 `ProviderLifecycleEvent::LifecycleUnavailable`（`domain/provider_lifecycle/value_objects/provider_lifecycle_event.rs:28-33,98-100`）とその読み書き（`adaptor/gateway/local_event_store/provider_lifecycle_codec.rs:43,148-153,204`）、projection（`adaptor/gateway/agent_session/agent_session_repository.rs:1084`）、hook の健全性の表示（`adaptor/presenter/agent_session.rs:22-35`、`provider_hook_health_codec.rs`、`hook_health_repository_impl.rs`、`usecase/provider_lifecycle/hook_health.rs`）。本番の binding は `ProviderLifecycleBinding::arm`（`usecase/provider_lifecycle/mod.rs:87,119`）で作られ、event からの復元（`rehydrate`、`provider_lifecycle_binding.rs:23` で test-support 限定）は本番で通らないため、replay の分岐を消しても記録済みの event の読み取りと表示は変わらない。

## 固定するルート

- crate の名前と置き場所: 共有 crate は `src-tauri/releash-sdk/`（package `releash-sdk`）、CLI は `src-tauri/releash/`（package `releash`、bin `releash`）。サーバの実行ファイルは `releash-backend` のまま。置き場所は仮置きで、移動は #1854 で行う。#1854 でディレクトリを移すとき、ディレクトリの移動と Cargo の path の書き換えだけで済むように、次を守る。
  1. crate どうしの参照は Cargo の依存（`path = …`）だけ。ほかの crate のソースや生成物をファイルの path で参照しない（`#[path]`・`include_str!`・`include!` でほかの crate の中を指さない。build.rs が別の crate の `OUT_DIR` や `src/` を読まない）。
  2. 実行時に実行ファイルやデータの場所をリポジトリの配置（`src-tauri`、`target` など）で決めない。CLI・サーバ・シェルの間は「自分の隣」（`current_exe()` の隣）と data dir だけで見つける。
  3. テストで実行ファイルを見つけるのは、同じ crate なら `CARGO_BIN_EXE_<name>`、別の crate なら `shell-integration` と同じ方法（先に `cargo build` し、target dir の既存の見つけ方に揃える）。テストに `../../src-tauri/…` のような上位の相対 path を書かない。
  4. `src-tauri` という文字列を新しく書くのは、Cargo の workspace の `members`、CI の job、AGENTS.md・TEST.md のコマンドと表、`scripts/build-desktop-backend.mjs` に限る。ソースコードの中には書かない。
  5. proto の読み方は今の `build.rs`（`../proto/` の相対 path）と同じ 1 行で済む形にする。
- 共有 crate に置くのは、サーバに依存してはならないクライアントが要るもの（クライアント側の生成物、発見ファイルの読み取りと同一性の確認、`Compatibility`）だけ。サーバはこの crate に依存する。型は二重に生成しない。
- `Compatibility` は共有 crate に置き、release を判定に使わない。
- Tauri シェルは `desktop_api` の再公開のまま動かす。
- 終了コードは 0／1／2／3。2 は clap の構文の誤りだけ、サーバ由来の失敗は全て 1。
- 届かないときは `unavailable`、互換でないときは `failed_precondition`。hook は互換でないときも送らずに exit 0。
- CLI 側に値の妥当性の判断を置かない。
- CI は crate ごとの job の組（`cli-*`／`cli`、`client-*`／`client`）。必須のチェックへの登録は merge 前に利用者が行う。

## 変えないもの

- Connect の入口（購読の対象・RPC・scope・hook の token の env 名）。#1901 で決めたものを使う。
- 発見ファイル `client-api.json` の名前と形。
- 各コマンドの `--json` の stdout のキー名と値。
- サーバ側の hook の健全性の監視（`RELEASH_PROVIDER_LIFECYCLE_HEALTH_FILE` の受け渡し、読む側、画面の表示）。#1877 で消す。
- review の書き手の判定単位（#1775）。

## 未確定・リスク

- prost の型を `releash-sdk` に移すと、`releash-backend` の `build.rs` が型に付けている inherent impl（`client_commands.rs` の `impl CommandRequest`・`impl command_request::Command`）と `#[cfg(feature = "test-support")]` の属性（`build.rs` の `message_attribute`）は、型を定義する crate の外からは付けられない。サーバ側の生成をこの制約の中で作り直す必要がある。
- 発見ファイルの同一性の確認は今、HTTP の identity の応答（`adaptor/gateway/local_api.rs:76-97` の `identity_status`）を使っている。HTTP を消した後は `GetServerInfo` の `daemon_id` 等で確認する必要がある。
