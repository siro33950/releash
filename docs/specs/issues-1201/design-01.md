## 変える部分

- push 購読の切替: desktop が Tauri `listen` で購読している backend 状態の push（`agent-session-changed` / `branch-list-sync` / `file-change` / `git-status-changed` / `repo-paths-changed` / `review-comments-changed`）を、クライアント ws の push 購読へ切り替える。根拠: R-001「backend 状態の push（…）の受信は、クライアント ws だけで行われ、変更前と同じ結果が画面へ反映される」、B-002。ルート: 固定するルート「ws クライアントの一元化」に従う（購読の実装方法は委任）
- frontend 内の Tauri event 送信の撤去: `src/components/workspace/WorkspaceList.tsx` の `emit("branch-list-sync")` による frontend 内通知を、Tauri event を使わない通知へ置き換える。根拠: R-002「desktop が Tauri の IPC（command 呼び出し・event・Channel・URI scheme）を使うのは、…に限られる」、B-003。ルート: 委任
- 未登録 command の Tauri invoke 呼び出しの撤去: `WorkspaceList.tsx` の `close_workspace_node`（backend に登録されていない command）の Tauri invoke 呼び出しを撤去する。根拠: R-002、B-003。ルート: 委任
- backend の push の Tauri emit の撤去: backend の push sink が 8 つの push を Tauri emit とクライアント ws の双方へ配っている経路から、Tauri emit を撤去する。根拠: R-001、R-002、B-002、B-003。ルート: 委任
- backend の Tauri invoke 受付の限定: Tauri invoke handler が受け付ける command を、R-002 の用途（menu、クライアント ws の接続情報の取得、起動結果の取得、起動失敗時の終了）に限定し、それ以外の command を Tauri invoke から共有 dispatch へ転送しない。根拠: R-003「backend は、R-002 の用途以外の command を Tauri invoke で受け付けず」、B-004、R-020、B-022（起動失敗画面の表示と終了は維持）。ルート: 委任
- terminal の Tauri Channel 経路の撤去: `Channel<TerminalSurfaceStreamItemV1>` を受け取る Tauri command `attach_terminal_surface` を撤去し、terminal の出力を Tauri Channel で配信しない。根拠: R-003「terminal の出力を Tauri Channel で配信しない」、B-005。ルート: 委任
- `review-blob:` URI scheme の置き換え: review の画像差分表示を、`review-blob:` URI scheme ではなくクライアント ws から取得したデータで表示するよう置き換え、scheme の登録と CSP の `review-blob:` を撤去する。根拠: R-004「`review-blob:` URI scheme を使わず、クライアント ws から取得したデータで行われ、変更前と同じ画像が表示される」、B-006。ルート: 委任
- E2E 経路の置き換え: Playwright の結合テストで、クライアント ws に載せた機能の応答を Tauri IPC mock（`window.__TAURI_INTERNALS__` の command→返り値の表、`plugin:event|emit` による push）から作る経路を、Tauri IPC の mock を介さない経路へ置き換える。根拠: R-005「クライアント ws に載せた機能を Tauri IPC の mock を介さずに実行する」、B-007。ルート: 委任
- レイテンシ予算の充足: この変更を加えた後のクライアント ws で、A1 と同じ計測条件の `get_current_branch` 逐次往復が p95 1 ms 以下かつ p99 2 ms 以下であることを成立させる。開始状態（proto エンベロープ化 #1799 の後）では同条件の計測値がない。根拠: R-006、B-008。ルート: 委任
- 変更要求の状態の区別: クライアント ws の切断・応答待ちの終了で応答待ちの要求をすべて同じ失敗として reject している扱いを改め、変更要求を未送信が確定した要求・結果不明の要求・結果が確定した要求に区別し、結果不明の要求を未実行・処理失敗として表示しない。根拠: R-007「変更要求は、未送信が確定した要求、結果不明の要求、結果が確定した要求のいずれかとして区別される。…結果不明の要求は、未実行または処理失敗として表示されない」、B-009、B-010、B-013。ルート: 固定するルート「ws クライアントの一元化」に従う（内部構造は委任）
- 未送信要求の期限付き待機: 接続がない間の変更要求を、その操作の期限内に接続が回復すれば元の操作として送り、期限内に回復しなければ未実行として表示し、期限後に回復しても送らない。期限の値は Rust が所有する。根拠: R-007「未送信が確定した変更要求は、その操作の期限内にクライアント ws の接続が回復した場合は元の操作として送られ、期限内に回復しなかった場合は未実行として表示される」、B-009、B-023。ルート: 固定するルート「ws クライアントの一元化」に従う（期限の具体値は委任）
- 冪等性による結果不明時の送り直し規則: 各 command の変更要求が冪等かの分類を Rust に置き、冪等でない変更要求は結果不明になっても新しい操作として自動再送せず、冪等な変更要求は期限内に自動で送り直せるようにする。根拠: R-008「冪等でない変更要求は、結果不明になった場合、新しい操作として自動で再送されない」、R-021「冪等な変更要求は、…その操作の期限内に自動で送り直されることがある。送り直された場合も、backend の状態はその要求を一度だけ実行した場合と同じになる」、B-024、B-025。ルート: 固定するルート「ws クライアントの一元化」に従う（分類の具体は委任）
- 再試行と元の操作の対応付け: 冪等でない変更要求を利用者が再試行したとき、元の操作と対応付けて副作用を重複させない（同じ操作の結果を確認できるか、重複を防いで再試行できる）ようにする。開始状態では agent session の作成・archive・削除・restore・履歴からの再開と application quit 以外の変更 command にこの仕組みがない。根拠: R-009「利用者が結果不明の変更要求を再試行した場合、その再試行は元の操作と対応付けられ、副作用が重複しない」、B-012。ルート: 固定するルート「既存の操作識別・照会機構の優先利用」に従う（既存機構に載せられない command は委任）
- 接続回復後の元の操作の結果の確定: 受理後・完了前、または完了後・応答前に切断された変更要求のうち結果を確定できるものを、接続の回復後に元の操作の結果として確定し、画面へ反映する。根拠: R-010、B-010、B-011。ルート: 固定するルート「既存の操作識別・照会機構の優先利用」に従う（既存機構に載せられない command は委任）
- 結果を確定できない変更要求の表示と再実行の抑止: backend の再起動などで結果を確定できない変更要求を結果不明として表示し、安全を確認できない再実行を自動でも利用者の再試行でも行わない。根拠: R-011、B-013。ルート: 固定するルート「既存の操作識別・照会機構の優先利用」に従う（既存機構に載せられない command は委任）
- 生存確認と接続の無応答判定: 生存確認のないクライアント ws に、同じ接続上の生存確認を加え、push や応答のない待機状態・正常な長時間処理を無応答と判定せず、接続を閉じない通信停止を有限の期限内に無応答と判定する。確認間隔と応答期限は Rust が所有する。根拠: R-012、B-014、B-015、B-018。ルート: 固定するルート「ws クライアントの一元化」に従う（間隔・期限の具体値は委任）
- 個別要求の操作別の期限: `get_current_branch` にだけある 10 秒の期限（超過で要求を reject する）を改め、個別要求に操作に応じた期限を設けて接続全体の無応答判定と分け、期限超過だけを根拠に接続を切断せず、backend の処理を中断せず、処理失敗と表示せず、同じ接続上の他の要求と terminal の入出力を巻き込まない。期限の値は Rust が所有する。根拠: R-013、R-014、B-017、B-018。ルート: 固定するルート「ws クライアントの一元化」に従う（期限の具体値は委任）
- 無応答・期限超過の表示: 接続の無応答または個別要求の期限超過を検知したとき、画面を待機中のまま残さず、通信状態を確認できないこと、または操作結果を確認できないことを表示する。根拠: R-015、B-015、B-017。ルート: 固定するルート「ws クライアントの一元化」に従う（検知と状態の扱いは `clientSocket.ts`、呼び出し側は結果と状態を受け取る。表示の方法は委任）
- 無応答時の再接続と回復後の復旧: 接続の無応答を検知したら再接続を試み、回復後に必要な状態の再取得、購読の復旧（接続の確立後に開始し直されていない監視（`start_watching` / `start_git_dir_watching`）を含む）、terminal の再同期を行って現在の状態を画面へ反映する。根拠: R-016、B-015、B-016。ルート: 固定するルート「ws クライアントの一元化」に従う（再接続の方式は委任）
- スリープ復帰時の生存確認: OS のスリープ復帰を扱う処理がない状態を改め、復帰後に生存確認を再実施してから無応答を判定し、backend が応答した場合は無応答と判定しない。根拠: R-018、B-021。ルート: 固定するルート「ws クライアントの一元化」に従う（検知方法は委任）
- 期限後の遅延応答の扱い: 期限を超えてから応答が届いた要求について、変更処理の副作用を重複させず、画面に現在の状態を反映する。根拠: R-019、B-019。ルート: 固定するルート「ws クライアントの一元化」に従う（内部構造は委任）

## 固定するルート

- ws クライアントの一元化: frontend の ws クライアントは `src/lib/clientSocket.ts` の 1 箇所に限る。この変更で導入する要求の追跡（未送信・結果不明・結果確定の区別）、未送信要求の期限付き待機、個別要求の期限、生存確認、接続状態の扱いも、呼び出し側（hook・component）ではなくこの 1 箇所で行い、呼び出し側は結果と状態を受け取るだけにする。期限の値と冪等性の分類は Rust が所有し、`clientSocket.ts` はそれを適用する側である。
  - 範囲: frontend のクライアント側処理全体。
  - 粒度: 配置の固定（内部構造は委任）。
  - 理由: 一般的なサーバクライアント方式と同じく、再送・期限・接続状態をクライアントライブラリに集約して呼び出し側へ分散させない。backend の独立後も差し替え箇所を 1 箇所にする。
  - 関係: R-007, R-008, R-012, R-013, R-014, R-015, R-016, R-021, B-009, B-015, B-017, B-023, B-024, B-025。
- 既存の操作識別・照会機構の優先利用: 冪等でない command の結果確認・重複防止には、既存の caller attempt 機構（local event store の caller_attempts / operation_bindings、(principal, installation_id, kind, caller_request_id) を鍵とする admission。agent session の作成・archive・削除・restore・履歴からの再開が使用）と、application quit の操作 journal（`list_pending_application_attempts` / `acknowledge_application_attempt` / `get_application_quit_operation`、`OutcomeUnknown`）を優先して利用する。既存機構に載せられない command の扱いは委任する。
  - 範囲: 冪等でない変更 command の結果確認・重複防止。
  - 粒度: 「優先して利用する」まで（全 command を既存機構へ寄せることは固定しない）。
  - 理由: Issue #1201 の指示の粒度を維持し、event store に事実を書かない command（git 操作等）の責務を event store に負わせない。
  - 関係: R-009, R-010, R-011, B-010, B-011, B-012, B-013。
