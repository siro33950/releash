## 変える部分

- 未送信要求への照会の交差による重複送信の防止: 未送信要求の結果照会を別要求の応答時にも送り、Ready の受信時に照会との対応や送信済みかを確かめずに Request を送るため、照会の応答が交差すると同じ要求 ID の Request を二度送り、読み取りを二重に実行し、処理中の変更要求を結果不明に変える状態を改め、未送信要求への照会が複数回送られその応答が交差しても、同じ要求を backend で一度だけ実行し、正常に処理中の変更要求を結果不明と表示しない。根拠: R-001「変更前と同じ結果が画面へ反映される」、B-001、R-007「結果不明の要求は、未実行または処理失敗として表示されない」、R-019「変更処理の副作用は重複せず」、Thread `c845ce83`。ルート: 委任（固定するルート「ws クライアントの一元化」は維持する）
- backend が未送信と応答した変更要求の未実行表示: 接続回復時の照会に backend が未送信（`not_sent`）と応答した経路では要求を reject して保持から除くだけで未実行の表示に残らない状態を改め、未送信が確定した変更要求は、期限切れの判定が frontend の定期処理によるものでも backend の応答によるものでも、同じく未実行として表示し、画面から消さない。根拠: R-007「未送信が確定した変更要求は、…期限内に回復しなかった場合は未実行として表示される」、B-023、Thread `6ecd5d86`。ルート: 委任（固定するルート「ws クライアントの一元化」は維持する）
- 応答未受領のまま期限を超えた監視開始の接続回復後の監視復旧: 監視開始の応答受領前に切断して期限を超えると、backend は未受領の監視を停止して記録を除き、frontend は同じ要求が保持中であるため監視の復旧を飛ばし、照会も結果不明のままで監視が再開されない状態を改め、元の監視開始要求の期限後の扱いは R-025 のとおり維持したまま、接続回復後に必要な監視を復旧して file / git の変更を画面へ反映する。根拠: R-016「接続の回復後は、…購読の復旧…が行われ、現在の状態が画面へ反映される」、B-016、R-025、Thread `bdbbb878`。ルート: 委任
- 保持期間で破棄・停止された監視への遅延成功応答の扱い: 受領確認されていない監視開始の記録を保持期間の経過で破棄・停止した後に成功応答の処理が遅れて届くと、frontend が停止済みの監視を有効として扱い、受領確認も backend で照合されずに食い違いが残る状態を改め、R-022 の破棄は維持したまま、frontend が停止済みの監視を有効な監視として扱わず実在する監視に対応した状態になり、以後の file / git の変更を画面へ反映する。根拠: R-016、B-016、R-019「期限を超えてから応答が届いた要求についても、…画面には現在の状態が反映される」、B-019、R-022、Thread `2af8bf5a`。ルート: 委任
- 他の操作の記録破棄と未受理要求の利用者再試行の区別: 同じ世代で一件でも記録を破棄すると世代全体に履歴喪失が立ち、caller attempt 以外の送信済み要求は利用者の再試行でも結果不明と判定され、破棄と無関係な未受理の要求まで実行できず、同じ対象の後続操作も止まる状態を改め、他の操作の記録破棄と当該要求の未受理を区別し、backend に受理されないまま期限を過ぎた変更要求の利用者再試行を元の操作として一度だけ実行して同じ対象への後続操作も止めず、記録が破棄された当該要求の照会・再試行は R-024 のとおり結果不明のままにする。根拠: R-024「保持期間の経過または保持数の上限により記録が破棄された変更要求は、…安全を確認できない再実行は自動でも利用者の再試行でも行われない」、R-025「期限を過ぎた後にその要求が実行されるのは利用者が再試行した場合だけであり、元の操作として重複を防いで一度だけ実行される」、B-031、Thread `831924f5`。ルート: 委任（固定するルート「既存の操作識別・照会機構の優先利用」は維持する）

## 固定するルート

今周に新たに固定する実装上の指定なし。

次は Design 01 で固定し、Design 02・Design 03 と今周も維持する。

- ws クライアントの一元化（Design 01）: frontend の ws クライアントは `src/lib/clientSocket.ts` の 1 箇所に限る。要求の追跡（未送信・結果不明・結果確定の区別）、未送信要求の期限付き待機、個別要求の期限、生存確認、接続状態の扱いは、呼び出し側（hook・component）ではなくこの 1 箇所で行い、呼び出し側は結果と状態を受け取るだけにする。期限の値と冪等性の分類は Rust が所有し、`clientSocket.ts` はそれを適用する側である。
  - 範囲: frontend のクライアント側処理全体。
  - 粒度: 配置の固定（内部構造は委任）。
- 既存の操作識別・照会機構の優先利用（Design 01）: 冪等でない command の結果確認・重複防止には、既存の caller attempt 機構（local event store の caller_attempts / operation_bindings、(principal, installation_id, kind, caller_request_id) を鍵とする admission）と、application quit の操作 journal（`list_pending_application_attempts` / `acknowledge_application_attempt` / `get_application_quit_operation`、`OutcomeUnknown`）を優先して利用する。既存機構に載せられない command の扱いは委任する。
  - 範囲: 冪等でない変更 command の結果確認・重複防止。
  - 粒度: 「優先して利用する」まで（全 command を既存機構へ寄せることは固定しない）。
