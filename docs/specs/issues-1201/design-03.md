## 変える部分

- 完了済みの操作記録の保持期間での破棄: backend が結果の受け取りを確認されていない変更要求の記録を受領確認でしか削除しない状態を改め、処理の完了から保持期間を過ぎた記録を破棄する。保持期間は最長の操作期限より長くし、期限内に接続が回復した要求は元の操作の結果として確定できるままにする。根拠: R-022「処理の完了から保持期間を過ぎた後に破棄する。保持期間は、最長の操作期限より長い」、B-026、B-027、Thread `c257f88e`。ルート: 委任（保持期間の値も委任。条件は最長の操作期限（開始状態では 120 秒）より長いこと、値は Rust が所有する）
- 保持数の上限到達時の受付: 記録が保持数の上限（開始状態では 1024 件）に達すると新しい変更要求を拒否する状態を改め、処理が完了した記録を古い順に破棄して新しい変更要求（terminal 入力を含む）を受け付け、処理が完了していない記録は破棄せず、上限を理由に拒否するのは処理中の記録だけで上限に達している場合に限る。根拠: R-023「処理が完了した変更要求の記録を古い順に破棄して、新しい変更要求を受け付ける。処理が完了していない変更要求の記録は破棄されない」、B-028、Thread `c257f88e`。ルート: 委任
- 記録が破棄された変更要求の照会・再試行: 記録が破棄された変更要求の照会・再試行を、未記録の要求として再実行可能と判定せず結果不明として表示し、処理失敗と表示せず、安全を確認できない再実行を自動でも利用者の再試行でも行わない。caller attempt など重複を防げる仕組みに載る要求は、利用者の再試行を元の操作として受け付けて副作用を重複させない。根拠: R-024「記録が破棄された変更要求は、照会または再試行された場合、結果不明として表示され、処理失敗として表示されず、安全を確認できない再実行は自動でも利用者の再試行でも行われない。重複を防いで再試行できる変更要求は、利用者の再試行が元の操作として受け付けられる」、B-027、B-028、B-029、R-009、R-010、B-010、B-011、B-012、Thread `c257f88e`。ルート: 委任（固定するルート「既存の操作識別・照会機構の優先利用」は維持する）
- 期限を過ぎた未受理の変更要求の自動実行の停止: caller attempt に載る要求の再実行可否が期限を見ず、接続回復後や定期の結果照会で backend に受理されていない要求を期限後に自動送信・実行しうる状態を改め、期限を過ぎた未受理の変更要求（別世代の backend への `request_application_quit` を含む）について自動で行うのは結果の照会だけにし、画面は結果不明の表示のままにする。根拠: R-025「利用者の操作なしに backend で実行されず、結果不明の表示のままになる。期限を過ぎた後にその要求について自動で行われるのは、結果の照会だけである」、B-030、Requirements Context「サーバは期限を過ぎた要求の処理を開始しない（gRPC deadline）」、Thread `b29bc5f4`。ルート: 委任（固定するルート「既存の操作識別・照会機構の優先利用」は維持する）
- 期限を過ぎた未受理の変更要求の利用者による再試行: 期限を過ぎた未受理の変更要求を実行するのは利用者が再試行した場合だけにし、その再試行を元の操作として重複を防いで一度だけ実行する。根拠: R-025「期限を過ぎた後にその要求が実行されるのは利用者が再試行した場合だけであり、元の操作として重複を防いで一度だけ実行される」、B-031、Thread `b29bc5f4`。ルート: 委任（固定するルート「既存の操作識別・照会機構の優先利用」は維持する）

## 固定するルート

今周に新たに固定する実装上の指定なし。

次は Design 01 で固定し、Design 02 と今周も維持する。

- ws クライアントの一元化（Design 01）: frontend の ws クライアントは `src/lib/clientSocket.ts` の 1 箇所に限る。要求の追跡（未送信・結果不明・結果確定の区別）、未送信要求の期限付き待機、個別要求の期限、生存確認、接続状態の扱いは、呼び出し側（hook・component）ではなくこの 1 箇所で行い、呼び出し側は結果と状態を受け取るだけにする。期限の値と冪等性の分類は Rust が所有し、`clientSocket.ts` はそれを適用する側である。
  - 範囲: frontend のクライアント側処理全体。
  - 粒度: 配置の固定（内部構造は委任）。
- 既存の操作識別・照会機構の優先利用（Design 01）: 冪等でない command の結果確認・重複防止には、既存の caller attempt 機構（local event store の caller_attempts / operation_bindings、(principal, installation_id, kind, caller_request_id) を鍵とする admission）と、application quit の操作 journal（`list_pending_application_attempts` / `acknowledge_application_attempt` / `get_application_quit_operation`、`OutcomeUnknown`）を優先して利用する。既存機構に載せられない command の扱いは委任する。
  - 範囲: 冪等でない変更 command の結果確認・重複防止。
  - 粒度: 「優先して利用する」まで（全 command を既存機構へ寄せることは固定しない）。
