## 変える部分

- 自動で発行された要求の元の操作への対応付けと利用者の再試行の区別: 自動で発行された要求（例: 定期の `acknowledge_application_attempt`）が結果不明の元の操作へ対応付けられる（`bound`）と、利用者の再試行と同じく再試行の扱いと期限の更新が行われ、backend に受理されないまま期限を過ぎた元の変更要求が利用者の操作なしに実行される状態を改め、自動の対応付けを利用者の再試行として扱わず、期限を過ぎた未受理の元の変更要求は利用者の操作なしに実行せず結果不明の表示のままにし、利用者が再試行した場合だけ元の操作として一度だけ実行する。根拠: R-025「期限を過ぎた後にその要求について自動で行われるのは、結果の照会だけである。期限を過ぎた後にその要求が実行されるのは利用者が再試行した場合だけであり、元の操作として重複を防いで一度だけ実行される」、B-030、B-031、R-009、Thread `e16c2801`。ルート: 委任（固定するルート「ws クライアントの一元化」「既存の操作識別・照会機構の優先利用」は維持する）
- 送信済みの削除・承認・workflow 設定保存の結果不明時の画面表示: 結果を待つ要求である `remove_worktree`・`delete_branch`・`approve_workspace_node`・`update_workflow_config` が送信済みのまま期限超過や切断で結果不明になると、呼び出し側が結果不明の通知を受け取らず、worktree 削除画面の Deleting...、workspace node の Approving...、設定画面の Save の spinner と操作無効が続く状態を改め、各画面は待機表示のまま残らず、処理失敗ではなく操作結果を確認できないことを表示し、後から結果が確定した場合は確定した結果を各画面へ反映する。根拠: R-015「個別要求の期限超過を検知した場合、画面は待機中のまま残らず、…操作結果を確認できないことが表示される」、B-017、R-007「結果不明の要求は、未実行または処理失敗として表示されない」、Design 03 変える部分「後から確定した変更要求の結果の利用画面への伝達」、Thread `e63c9f19`。ルート: 委任（固定するルート「ws クライアントの一元化」は維持する）
- provider availability フォームの開き直し後の前回の未保存入力の残存の解消（Design 04 からの残存）: 保存せず閉じた設定画面を開き直したとき、provider availability フォームは取得成功時には backend の現在値へ置き換わるが、取得中・取得失敗時には前回の値と未保存入力が残り、Save が取得中を見ずに有効なため前回の未保存入力を保存できる状態を改め、接続回復・期限後応答による再取得では編集中の入力を保ったまま、保存せずに閉じて開き直した場合は取得中・取得失敗時も含めて前回の未保存入力を表示にも保存対象にも残さない。根拠: R-001「変更前と同じ結果が画面へ反映される」、B-001、Design 04 変える部分「設定画面を開き直したときの backend 現在値の表示」、Thread `c35cc4f6`。ルート: 委任
- 無関係な対象範囲の完了を挟む復旧の最終状態と副作用の検証（Design 04 からの残存）: 後続操作の保護情報を対象範囲ごとに区別する実装は入ったが、その検証がテスト自身で状態と後続操作の情報を組み立てるものと、無関係な完了を挟まない `add_repo_path` / `remove_repo_path` の二操作の dispatch に限られる状態を改め、先行の冪等要求が結果不明の間に同じ対象範囲の後続操作が確定し、その後に別の対象範囲の操作（例: `update_crash_reporting` の後の `report_mounted_xterm_count`）が完了してから別世代へ再接続した場合も、確定済みの後続操作が取り消されず最終状態が元の操作順に一度ずつ実行した状態になることを、後続操作の情報を手で組み立てず状態を持つ dispatch 対象を通して検証する。`add_repo_path` と `remove_repo_path` の交差の既存の検証は維持する。根拠: R-021「送り直された場合も、backend の状態はその要求を一度だけ実行した場合と同じになる」、B-024、Design 04 変える部分「確定済みの後続操作の保護情報の無関係な完了による喪失の解消」、Thread `7c00c878`。ルート: 委任（固定するルート「ws クライアントの一元化」「既存の操作識別・照会機構の優先利用」は維持する）

## 固定するルート

今周に新たに固定する実装上の指定なし。

次は Design 01 で固定し、Design 02〜Design 04 と今周も維持する。

- ws クライアントの一元化（Design 01）: frontend の ws クライアントは `src/lib/clientSocket.ts` の 1 箇所に限る。要求の追跡（未送信・結果不明・結果確定の区別）、未送信要求の期限付き待機、個別要求の期限、生存確認、接続状態の扱いは、呼び出し側（hook・component）ではなくこの 1 箇所で行い、呼び出し側は結果と状態を受け取るだけにする。期限の値と冪等性の分類は Rust が所有し、`clientSocket.ts` はそれを適用する側である。
  - 範囲: frontend のクライアント側処理全体。
  - 粒度: 配置の固定（内部構造は委任）。
- 既存の操作識別・照会機構の優先利用（Design 01）: 冪等でない command の結果確認・重複防止には、既存の caller attempt 機構（local event store の caller_attempts / operation_bindings、(principal, installation_id, kind, caller_request_id) を鍵とする admission）と、application quit の操作 journal（`list_pending_application_attempts` / `acknowledge_application_attempt` / `get_application_quit_operation`、`OutcomeUnknown`）を優先して利用する。既存機構に載せられない command の扱いは委任する。
  - 範囲: 冪等でない変更 command の結果確認・重複防止。
  - 粒度: 「優先して利用する」まで（全 command を既存機構へ寄せることは固定しない）。

## 未確定・リスク

- 自動判断（Requirements の Assumptions）: R-002 と B-003 の Tauri IPC の用途に「起動が成功したか失敗したかを判定するための起動結果の取得」を含めた。この解釈が意図と異なる場合、起動成功時の判定を Tauri invoke 以外へ移す変更が R-002 を満たすために必要になる。
- 自動判断（Requirements の Assumptions）: R-024 で、冪等であることを「記録の破棄後も backend が操作の識別子で重複を防ぐ仕組みに載る」ことに含めなかった。この解釈が意図と異なる場合、記録が破棄された冪等な変更要求（例: `add_repo_path`）の利用者の再試行を元の操作として受け付ける変更が R-024 / B-029 を満たすために必要になり、その際に確定済みの後続操作を取り消さない条件（R-021）との両立が要る。

- `[DEFERRED]` で人間へ渡した件: なし。
