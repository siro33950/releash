# Design 01

## 開始状態

- 差分の基準は base ブランチ `main`、派生点は `feat/issues/1861` の `81ec380b`。Spec 工程でコードを変更していないため、この時点の実装をこの周の開始状態とする。
- 既存の `design-NN.md` はなく、この周が初回である。開始状態の挙動は `docs/specs/issues-1861/requirements.md` の Current Behavior を参照する。
- この周までに解消・見送りとなった Thread はない。

## 変える部分

- 更新中の一覧差し替えの撤去: 更新の開始を理由に Repository・Worktree・Session・Workflow の一覧表示を差し替えず、直前に取得できた一覧を表示し続ける。根拠: R-001「更新の開始を理由に Repository・Worktree・Session・Workflow の一覧表示を消さない」、B-001、B-002。ルート: 固定ルート②（一覧保持と Session・Workflow の再取得経路の変更を同じ周で扱う）
- 更新をまたぐ表示状態の維持: 更新の前後で存在し続ける対象について、展開状態・選択・Workspaces 一覧のスクロール位置を維持し、表示中の Session を切り替えない。根拠: R-002「更新をまたいで展開状態、選択、Workspaces 一覧のスクロール位置を維持し、表示中の Session を切り替えない」、B-003。ルート: 委任
- 更新の操作の位置の変更: Workspaces 行に更新の操作を一つ置き、Repository 行ごとの更新の操作を撤去する。根拠: R-003「Workspaces 行に更新の操作を一つ置く。Repository ごとの更新の操作はない」、B-004。ルート: 委任
- 失敗状態での操作の受付: 一覧の取得に失敗している状態でも Workspaces 行の更新の操作を実行できるようにする。根拠: R-004「一覧の取得に失敗している状態でも、Workspaces 行の更新の操作を実行できる」、B-005。ルート: 委任
- 更新対象の3階層への拡張: 登録 Repository 一覧、各 Repository の Worktree 一覧、各 Worktree 配下の Session・Workflow の一覧情報を、折りたたまれている Repository も含め、表示部品の再作成に依存しない経路で更新する。根拠: R-005「折りたたまれている Repository も対象に含み、表示部品の再作成に依存せずに更新する」、B-006、B-021。ルート: 固定ルート①（更新手順と結果の判定を Rust 側に置き、`RepositoryStateService` の走査処理と Workspace の一覧取得処理を再利用する）、固定ルート②、固定ルート④（手動更新と自動更新で内部の経路を分けない）
- 走査の再実行経路の追加: 更新時に Repository の走査を実際に再実行し、保存済みの結果をそのまま反映しない。根拠: R-006「保存済みの結果をそのまま反映しない」、B-007。ルート: 固定ルート①、固定ルート④
- 失敗状態からの再走査の受付: 自動更新に失敗した対象について、アプリを再起動せずに更新の操作から再走査を受け付け、成功した対象を最新の内容で表示する。根拠: R-007「自動更新に失敗した後も、アプリを再起動せず Workspaces 行の更新の操作から再取得でき、取得に成功した対象は最新の内容で表示される」、B-008。ルート: 固定ルート①
- 対象ごとの成否の分離: 一部または全部の対象で取得に失敗しても、成功した対象だけを更新し、失敗した対象は直前に取得できた一覧を表示し続ける。根拠: R-008「取得に成功した対象は更新し、失敗した対象は直前に取得できた一覧を表示し続ける」、B-009、B-011。ルート: 固定ルート①
- 更新失敗の表示: 取得に失敗した Repository・Worktree、および登録 Repository 一覧そのものの取得に失敗した場合の Workspaces 一覧全体に、更新に失敗したことと表示中の内容が前回取得の情報であることを示す。根拠: R-009、B-010、B-020。ルート: 固定ルート①（失敗の判定は Rust 側が持ち、frontend は受け取った更新状態とエラーを表示する）
- 取得状態の3区別: 初回取得中、初回取得の失敗、正常に取得した空の結果を区別して扱い、初回取得中と初回取得の失敗を「項目なし」として表示しない。正常に取得した空の結果と、正常な取得で確認できた削除は一覧へ反映する。開始状態では `mark_scan_failed` が version 0 の loading を下ろすため、初回走査に失敗した Repository が空で取得完了した snapshot として読み出される。根拠: R-010、R-014、B-012、B-013、B-014、B-018。ルート: 固定ルート①
- 失敗表示の解消: 再取得に成功した対象では、それまでの更新失敗の表示を解消する。根拠: R-011「再取得に成功した対象では、それまでの更新失敗の表示を解消する」、B-015。ルート: 委任
- 手動更新の進行表示と重複抑止: 手動更新の進行中は進行していることを示して同じ更新の重複した要求を受け付けず、成功・失敗のいずれで終わった後も再び操作できるようにする。根拠: R-012、B-016。ルート: 委任
- 更新結果の新旧判定: 自動更新と手動更新が重なって応答の順序が入れ替わっても、より古い取得結果でより新しい一覧を上書きしない。根拠: R-013、B-017。ルート: 固定ルート①（結果の判定は Rust 側）、固定ルート④

## 固定するルート

- 全体の更新手順と結果の判定を Rust 側に置き、既存の `RepositoryStateService` の走査処理と Workspace の一覧取得処理を再利用する。Frontend は受け取った一覧・更新状態・エラーを表示するだけにする。範囲: 更新手順全体。粒度: 再利用先を既存の2つに名指しで指定する。理由: `AGENTS.md` のアーキテクチャ原則（Rust がロジックを所有する）。
- 一覧を保持する変更と、Session・Workflow の再取得経路の変更を併せて行う。範囲: この周で両方を扱い、分割しない。理由: 開始状態では `WorktreeTreeItem` の mount に伴って `useWorkspaceTreeNodes` が子項目を取得しているため、一覧を保持するだけでは更新時の子項目の再取得が抜ける。
- 更新対象は Workspaces の一覧情報に限り、表示中の Session や実行中の Workflow の継続を保つ。範囲: 更新対象の範囲。理由: 一覧の更新が Session の表示や Workflow の実行に波及しないようにするため。
- 手動更新と自動更新で内部の経路を分けない。常に最もシンプルな形にする。範囲: 更新経路の構造全体。理由: 内部が呼び出し経路に依存するのを避けるため。

## 変えないもの

- 自動更新の周期と起動契機。対象範囲は手動更新と同じに広げるが、自動更新が始まる周期と契機そのものは現行のままとする。
- 手動更新に固有の時間上限。応答が返らない場合の打ち切りは、既存の client の deadline（`src/lib/client.ts` の Connect transport `defaultTimeoutMs`）に委ねる。
- 表示中の Session と実行中の Workflow の継続（R-015、B-019）。開始状態でも一覧の更新は Session の表示と Workflow の実行を中断しないため、この周では変更しない。

## 未確定・リスク

- 走査は debounce を挟む worker 経由で非同期に進み、開始状態には走査の完了を待ち合わせて結果を返す経路がない（`WorktreeState::invalidate` は通知のみ、`get_snapshot` は保存済み snapshot を返す）。完了の待ち合わせに既存の generation 列をそのまま使えるかは未確認で、使えない場合は R-006（走査の再実行結果の反映）、R-012（完了後の再操作）、R-013（結果の新旧判定）の実現方法が変わる。
- Session・Workflow の一覧取得は開始状態では Worktree 単位（`list_workspace_worktree_nodes`）しかなく、全 Worktree を対象にした場合の件数に上限がない。R-005 の「折りたたまれている Repository も対象に含む」と、`AGENTS.md` の full-retention / full-recompute 経路を増やさない方針を両立させる取得の粒度が未確定である。
