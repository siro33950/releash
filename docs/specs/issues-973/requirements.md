# Requirements

## Type

リファクタリング

## Goal

`repository` ドメイン（branch、commit、log、worktree、status、repo_paths、git_config の各責務）を、`docs/architecture/` のクリーンアーキテクチャ規約に従ったレイヤー構成へ移行する。

完了時には、これらの責務がドメイン層・ユースケース層・アダプタ層・インフラ層の各規約に沿って配置され、git2 やファイル I/O といった外部リソースへの依存がインフラ／ゲートウェイ層に閉じ込められた状態になる。あわせて旧構成のモジュールが除去され、これらの責務がレイヤー規約に違反せず単一クレート内で再利用可能になっていることを成功とする。本移行を通じて、フロントエンド・リモートクライアントから見える機能の振る舞いは一切変わらない。

## Background

現状、Git 関連のロジックは `src-tauri/src/git/`（branch、log、worktree、status、git_config、共有 util 等）と `src-tauri/src/repo_registry.rs`（repo_paths）に、レイヤー分離のない構成で実装されている。ビジネスロジックと git2／ファイル I/O が同一モジュール内に混在しており、Tauri コマンドや WebSocket ハンドラからの呼び出しと密結合している。

この状態には以下の課題がある。

- ドメインロジックが git2・ファイル I/O・Tauri に直接依存しており、CLI 等の別エントリポイントから再利用できない。
- ビジネスルールとインフラ詳細が同一モジュールにあるため、ドメイン単位のテストが書きづらい。
- 単一責務に基づくファイル分割が徹底されておらず、責務の所在が追いにくい。

リポジトリ全体で進行中のクリーンアーキテクチャ移行（ミルストーン「[12] クリーンアーキテクチャ移行」）の一環として、`repository` ドメインを規約準拠の構成へ移行し、上記課題を解消する。本ドメインに先行・後続の依存はない。

## Users / Actors

- Releash デスクトップアプリを利用するエンドユーザー（Git 操作 UI の利用者）
- リモートクライアント（モバイル／タブレット）から WebSocket 経由で Git 操作を行う利用者
- `repository` ドメインの機能を将来再利用する別エントリポイント（CLI 等）
- 本コードベースを保守する開発者

## Scope

- issue 973 が定める責務（branch、commit、log、worktree、status、repo_paths、git_config）のロジックを、クリーンアーキテクチャ規約に従ったレイヤー構成へ移行する。
- これらの責務に対応するドメイン層（エンティティ・値オブジェクト・永続化／外部リソースの抽象・ドメインサービス）を新構成で実装する。
- これらの責務の Command 側・Query 側ユースケースを新構成で実装する。
- これらの責務に対する外部リソース（git2、ファイルシステム）アクセスの具体実装を、ドメインが定義する抽象の実装としてゲートウェイ／インフラ層に配置する。
- これらの責務に対応する Tauri コマンドを、ユースケースを呼び出す薄い入口としてアダプタ層へ再配置する。
- これらの責務に対応する WebSocket 入口が存在する場合、薄いハンドラとしてアダプタ層へ再配置する。
- ドメイン層・ユースケース層・ゲートウェイ層に対するテストを追加する。
- 移行完了後、旧構成の対応モジュールを除去する。
- 本ドメインに属する Tauri コマンドの登録方式を、アプリ起動時の DI 配線に整合させる。
- `repository` 移行に必要な範囲で、`git/` 配下の共有ユーティリティ・共有型を整理する（後述の `code` ドメイン所属ファイルにも影響が及ぶことを許容する）。
- 移行の進行を妨げる既存 `docs/architecture/` 規約の不整合・曖昧さ（用語の誤用や責務分離の記述漏れ等）を、規約の意図を変えない範囲で修正・明確化する。これは本移行の受け入れ基準を確定させるために必要な作業として本 issue のスコープに含む。

## Non-goals

- 外部から観測可能な機能の振る舞い（Tauri コマンドの引数・戻り値・エラー表現、WebSocket メッセージ形式、UI 上の操作結果）の変更。
- `code` ドメインに属する責務（ファイル内容、diff、hunk、patch、staging、language、file_mention、visible/hidden ranges）そのものの新構成への移行。これは別 issue の範囲とし、本移行では `git/` 配下にこれらのファイルが残ることを許容する。
- `app_config` ドメイン（アプリ設定 TOML）の移行。本移行が扱うのはリポジトリ単位の git_config に限る。
- `repository` 以外のドメインの移行。
- Git 操作そのものの仕様変更・機能追加（新しい Git コマンドや操作の追加）。
- フロントエンド／リモートクライアント側のコード変更（バックエンド I/F が不変であるため不要）。

## Requirements

- `repository` ドメインの各責務（branch、commit、log、worktree、status、repo_paths、git_config）が、`docs/architecture/` の各層規約に従って配置されること。
- ドメイン層が git2・ファイル I/O・Tauri などの外部リソースを直接参照しないこと。
- ユースケース層がドメイン層の抽象（trait）のみに依存し、具体的な外部リソース実装に依存しないこと。
- 外部リソースへのアクセスが、ドメインが定義する抽象の実装としてゲートウェイ／インフラ層に閉じ込められること。
- Tauri コマンド／WebSocket ハンドラが、ユースケースを呼び出す薄い入口に徹すること（ビジネスロジックを持たないこと）。
- 移行対象の責務について、ドメイン層・ユースケース層・ゲートウェイ層のテストが存在すること。
- 移行後、旧構成の対応モジュールが除去され、同一責務の重複実装が残らないこと。
- 本ドメインの Tauri コマンドが、起動時 DI 配線に整合して登録されること。
- 移行前後で、各 Tauri コマンドの引数・戻り値・エラー表現が等価であること。
- 移行前後で、各 WebSocket メッセージの形式・意味が等価であること。

## Constraints

- 外部から観測可能な振る舞い（Tauri コマンド I/F、WebSocket メッセージ形式、Git 操作の結果）を一切変えない純粋移行とすること。
- 上記「純粋移行」の例外として、`dirty_count`（worktree の未コミット変更件数）の算出条件は全経路で未追跡ディレクトリ配下のファイルを個別計上する（`recurse_untracked_dirs(true)`）方式に統一する。旧構成は一覧 / ブランチカード / `remove_worktree` 経路が未追跡ディレクトリを「1 件」計上し、`get_worktree_dirty_count` コマンドのみ配下ファイルを個別計上するという経路間非一貫を抱えていた。これを是正する**意図的変更**であり、未追跡ディレクトリ（配下にファイルを持つ）を含む worktree では `list_worktrees` / `list_branches_with_status` の `dirty_count`・`WorktreeListResponse`・`remove_worktree` の拒否件数が移行前と変わりうる。これ以外の I/F・振る舞いは従来どおり完全保持する。
- レイヤー間の依存方向が規約（`infrastructure → adaptor（controller / gateway / presenter）→ usecase → domain`、依存は内向きのみ）に従い、逆方向（内側の層が外側の層に依存する向き）の依存を生まないこと。
- `code` ドメイン所属ファイルへの影響は、`repository` 移行に必要な範囲（共有ユーティリティ・共有型の整理）に限定し、`code` ドメインの責務そのものを移行しないこと。
- 既存の CI 品質チェック（フロントエンド lint／test／build、Rust fmt／clippy／test）が移行後も通過すること。

## Success Criteria

- `repository` ドメインの各責務が新アーキテクチャの各層に規約準拠で配置され、依存方向の規約に違反していない。
- ドメイン層が外部リソースを直接参照していない。
- 移行対象責務のドメイン層・ユースケース層・ゲートウェイ層にテストが存在し、通過する。
- 旧構成の対応モジュールが除去され、同一責務の重複実装が残っていない。
- 本ドメインの Tauri コマンドが起動時 DI 配線に整合して登録されている。
- 移行前後で、デスクトップ UI・リモートクライアントから見た Git 操作の振る舞い（コマンド I/F・WebSocket メッセージ形式・操作結果）が等価である。
- Rust の fmt／clippy／test、およびフロントエンドの lint／test／build が通過する。

## Open Questions

- なし（スコープ境界および振る舞い保持の方針は確認済み。`code` ドメイン所属ファイルは対象外、共有部分のみ整理対象、外部 I/F は完全保持の純粋移行とする）。
