# Requirements

## Goal

releash のワークフロー構成を、以下の 4 つの独立した builtin ワークフローへ再編する。

1. **Spec作成** — レビューループをやめ、ユーザーとの対話で構築する
2. **Specを元に実装** — 軽量モデルによる軽量レビューループ（最大 2 回、Human-in-the-Loop なし）で実装精度を保証する
3. **フルレビュー** — 全観点・全高性能モデル、モデル単位の妥当性チェック、Human-in-the-Loop あり
4. **フルレビュー後修正** — フルレビューの指摘を元に修正する

達成判定:

- 上記 4 つのワークフローが組み込みワークフローとして定義され、各ワークフローが意図した設定（Spec作成＝対話のみ、実装＝軽量モデル・最大 2 回ループ・Human-in-the-Loop なし、フルレビュー＝全高性能モデル・Human-in-the-Loop あり、修正＝指摘反映）で実行できる。
- 既存のワークフローは全て削除し、新 4 ワークフロー構成へ完全に置き換える（従来構成を残さない）。

## Background

現状のワークフローは Spec をレビューループで磨く方式を取っているが、Spec のレビューループは有効に機能していない。レビューが細かい指摘ばかりになり、根本的な問題は詳細まで読み込まないと発見できない。レビューループでは Spec の本質的な妥当性を担保できていない。

そのため、Spec はレビューループではなくユーザーとの対話で構築する方が良い。

実装ワークフローで軽量モデルの軽量レビューループ（最大 2 回、Human-in-the-Loop なし）を導入する動機は、要求を満たしていない段階で高精度レビューをかけても意味が薄くコスパが悪いためである。まずは軽量・高速に「要求を満たした実装」へ到達させる仕組みをこのワークフローで作り、高精度なレビューは後段のフルレビューに集約する。

フルレビュー（全観点・全高性能モデル、モデル単位の妥当性チェック、Human-in-the-Loop あり）を導入する動機は、低速・高精度のレビューとその結果を人間が逐次確認する形式が最も精度を上げられるためである。実装が完了したものを人間が高精度に確認する工程が品質保証として必要である。

フルレビュー後修正を独立したワークフローとして切り出す動機は、フルレビュー自体もその後の修正もコンテキストが広くなる可能性が高いためである。Thread 機能を使って文脈を共有しつつ、修正は新しいセッションで実施する方が効率的である。

## Users / Actors

- **人間ユーザー（開発者）** — Spec作成ワークフローでエージェントと対話し Spec を構築する。フルレビューワークフローで Human-in-the-Loop として逐次確認・判断する。
- **エージェント** — 各ワークフローの主体。Spec作成では対話相手、実装では実装＋軽量レビューループの実行、フルレビューでは全観点レビューの実行、フルレビュー後修正では指摘反映を担う。

## Requirements

### R1. Spec作成ワークフロー

- Spec はレビューループ方式ではなく、ユーザーとエージェントの対話によって構築できる。
- 従来の Spec レビューループは廃止する。

### R2. Specを元に実装ワークフロー

- Spec を元に実装を行う。
- 実装精度の保証のため、軽量レビューループを実施する。
  - レビュー指摘は Thread を利用する。
  - レビューに用いるモデルは軽量モデルとする。
  - レビュー観点は「Spec を満たしているか」「最低限の実装方針・アーキテクチャが合っているか」とする。
  - Human-in-the-Loop は不要。
  - 既存指摘も確認し、ループに陥っていないかをチェックする。
- レビューによる妥当性検証の結果、指摘があれば修正し、再度レビューする。
- 軽量レビューループの実施回数は最大 2 回とする。

### R3. フルレビューワークフロー

- 既存の `multi-agent-code-review` ワークフローと同等の構成でフルレビューを実施する。
  - 全観点（acceptance / structure / quality / test / security / architecture）について、全高性能モデル（claude-opus-4-8 / gpt-5.5）でレビューを行う。
  - モデル単位で妥当性チェック（verify）を独立に実施する。
  - Human-in-the-Loop（Summary 段で人間が逐次確認・判断する）を含む。

### R4. フルレビュー後修正ワークフロー

- 既存の `implement-from-threads` ワークフローをベースとし、フルレビューで得られた指摘（Open Thread）を元に修正を実施する。
- Thread の最終状態は Open / resolve の二択のみとする（申し送り Comment は廃止）。
  - 対応済み → resolve
  - 対応見送り → resolve
  - 後で対応する／対応中 → Open のまま
- Human-in-the-Loop ありで実施する（approval ノード）。

### R5. 既存ワークフロー及び関連ファセットの全廃

- 既存の builtin ワークフロー定義（`bug-fix.yml`, `implement-from-threads.yml`, `multi-agent-code-review.yml`, `spec-authoring.yml`, `spec-driven-development.yml`, `spec-driven-development-gpt-5-5.yml`, `spec-implement.yml`, `spec-plan.yml`, `spec-review.yml`, `spec-review-auto.yml`）を全て削除する。
- 既存の builtin ファセット（`builtin_facets/` 配下の contracts / instructions / knowledge / policies）も全て削除対象とする。
- 新ワークフローおよびそれが必要とするファセットは新規に定義する。既存資産を内部的に流用するかどうかは要求の範囲外（実装方針として別途定める）。

## Constraints

- 修正対象は builtin ワークフロー（定義および関連ファセット）と、それを搭載・登録するための実装に限定する。
- ワークフロー実行エンジン等、それ以外の基盤コードには手を入れない。

## Scope

- R1〜R5 すべてを今回のスコープに含める。
