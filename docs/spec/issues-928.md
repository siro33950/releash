## 要求

**種別**: 改善
**ゴール**:
- ワークフローパネルでステップが増えて縦に伸びても、最新ステップを一目で判断できる。
- 具体的には以下の3点を実現する:
  1. 新しいステップが追加されたときに自動スクロールで最下部に追従し、最新ステップが視野に入る。
  2. ワークフロー全体ステータス（Running / Waiting for approval / Completed / Failed / Aborted 等）はスクロール領域外のヘッダーに固定表示し、どこまでスクロールしても見えるようにする。
  3. ワークツリーを切り替えた直後は自動で最下部（最新ステップ）にスクロールし、自動追従モードにリセットする。

**背景**: ワークフローパネル（`WorkflowPanel`）はステップを上から下に古→新で並べる縦スクロールUIで、現在は全体ステータスを表示する `CurrentAction` ブロックもスクロール領域の内側にある。ステップが増えて縦に伸びると、最新ステップも全体ステータスも画面外に出てしまい、ワークフローが今どの段階にあるか一目で判断できない。

**影響範囲**:
- `WorkflowPanel` の実行中タブ（`WorkflowActivePanel`）と過去実行タブ（`ExecutionView`）の両方。
- `WorkflowTrace` 内の `CurrentAction` 相当の表示を、各タブのヘッダー領域（スクロール外）へ移動する。
- `WorkflowTrace` のスクロール領域に自動スクロール（最下部追従）を適用する。
- ワークツリー切替時には自動スクロール状態を初期化して最下部から再開する。

## アーキテクチャ概要

### 責務配置

- `WorkflowPanel`（タブコンテナ）: タブ表示・切替、`worktreePath` 変化時のタブ初期化を担当する / 個別パネル内のスクロール状態・自動追従モードは持たない。
- `WorkflowActivePanel`（実行中タブ）: 自タブのヘッダー（全体ステータス・アクションバー・承認/拒否UI・エラー表示）を、スクロール領域の外側に配置する責務を持つ / ステップ一覧の表示そのものは担当しない。
- `ExecutionView`（過去実行タブ）: 自タブのヘッダー（全体ステータス）をスクロール外に配置し、`historyState` を取得する責務を持つ / `WorkflowActivePanel` 固有の操作系UI（Approve/Reject/Stop）は持たない。
- ヘッダー内ステータス表示コンポーネント（`CurrentAction` 相当）: ワークフロー全体の現在状態を表示する単一責務のプレゼンテーションコンポーネント / 自前でスクロール監視や状態管理を行わない。
- `WorkflowTrace`（ステップ一覧）: スクロール領域として振る舞い、ステップ列のレンダリング・自動追従モードの維持・スクロール末尾追従処理・ユーザースクロール検知を担当する / 全体ステータス表示は担当しない（ヘッダーへ移譲）。
- 自動追従ロジック（`WorkflowTrace` 内部のカスタムフック）: スクロール要素ref・追従モードフラグ・スクロールイベントハンドラ・末尾検知・新ステップ追加時の `scrollToBottom` 実行を担う / グローバル状態やバックエンドとの通信は持たない。

### データ/通信フロー

- ワークフロー状態反映: バックエンドからのworkflowイベント → 既存経路で `workflowState` prop が更新 → タブ側ヘッダーに全体ステータスが反映、`WorkflowTrace` に新ステップが追加 → 追従モードが有効なら末尾までスクロール。
- ユーザースクロール: スクロール領域の `onScroll` → 末尾判定 → 追従モードのON/OFFを切替（末尾なら有効化、末尾より上なら解除）。
- タブ切替: `WorkflowPanel` の `activeTab` 変化 → 切替先タブの `WorkflowTrace` が `key` により新規マウント → 自動追従モード初期値=有効、初期スクロール位置=末尾。
- ワークツリー切替: `worktreePath` 変化 → `WorkflowPanel` 既存の `useEffect` がタブを `current` にリセット → タブ配下の `WorkflowTrace` も `key` の一部に `worktreePath` を含めることで再マウント → 自動追従モードリセット。

### 状態Owner

- 全体ステータス（`workflowState.state.type`）: バックエンド（Rust）が真のOwner。フロントは prop / `invoke` 経由で受信して表示するのみ。
- 表示中タブ（`activeTab`, `openPastIds`）: `WorkflowPanel`（既存）。本タスクで変更しない。
- 自動追従モード（有効/解除）: `WorkflowTrace` 内部のカスタムフック（ローカルstate）。タブごと・ワークツリーごとに独立して `key` 再マウントでリセットされる。
- スクロール位置: ブラウザDOM（スクロール要素）が物理Owner。フロントはref経由で読み書きする。
- 過去実行の `historyState` / `events`: データ取得経路（API契約・fetchロジック）は `ExecutionView` 内部（既存）で本タスクでは変更しない。取得状態（loading・error）のUI反映は本タスクで `ExecutionView` のローカルUI状態として追加する。

### 境界

- バックエンド境界: スクロール位置・自動追従モードはCLAUDE.mdの「UIの表示・レイアウト制御」「ユーザー入力の受付」のフロント責務に純粋に含まれるため、本タスクではRust側に追加・変更を持ち込まない。ドメイン判断（ワークフロー状態の遷移、ステップの追加・並列ステップの更新など業務状態の決定）はRust/既存WorkflowStateが担い、フロントは受信した状態に応じてDOM/UI操作（スクロール位置の制御、ref経由のスクロール実行、ユーザースクロール検知）のみを行う。これらUI状態は永続化せず、ワークツリー/タブの再マウントでリセットされる範囲に閉じる。
- パネル境界: `WorkflowActivePanel` / `ExecutionView` はヘッダー（スクロール外）と本文（スクロール内 = `WorkflowTrace`）の二層構造を維持する。ヘッダーには `WorkflowTrace` を内包させない。
- スクロール境界: スクロール領域は一段のみ（現状の二重 `overflow-auto` を解消）。自動追従ロジックは「スクロール領域として振る舞う単一要素」を前提とする。
- 再マウント境界: `WorkflowTrace` の `key` には少なくとも「タブ識別子（`current` または `executionId`）」と「`worktreePath`」を含める。これによりタブ切替・ワークツリー切替時にフックの内部状態が確実にリセットされる。
- 末尾判定境界: スクロール領域の「末尾」とは `scrollHeight - scrollTop - clientHeight` が小さなマージン以内であることと定義する（具体的なマージン値は実装に委ねる）。判定は純粋関数（例: `isAtBottom(metrics, threshold)`）として切り出し、入出力でテスト可能とする。Scenario上の「末尾までスクロールされている」「最下部より上の位置」はこの判定基準を満たす状態／満たさない状態として解釈する。
- テスト境界: 自動追従モードの状態遷移・末尾判定ロジックはカスタムフックおよび純粋関数単位でテストする。コンポーネントレベルのテストはヘッダー配置（スクロール外であること）と `key` による再マウントの再現性に集中する。jsdom 上でのDOMスクロール実測テストの網羅は行わない。

### 実装に委ねること

- カスタムフックの命名・ファイル配置（例: `useAutoFollowScroll.ts` を `WorkflowPanel/` 配下に置くか `hooks/` 配下にするか）。
- 末尾判定の許容マージンの具体値（何ピクセル以内を末尾とみなすか）。判定式・概念は「末尾判定境界」で定義済み。
- スクロール実行手段（`scrollTo`, `scrollIntoView`, `requestAnimationFrame` の併用要否）と、レンダリング後タイミングを揃えるための副作用の組み立て方。
- `CurrentAction` 相当をヘッダーに置く際の具体的なコンポーネント分割（`WorkflowTrace` 内の関数を切り出して再利用するか、各パネル用に薄いヘッダーコンポーネントを新設するか）。
- 二重 `overflow-auto` 解消の具体的な書き換え方（`WorkflowTrace` 外側 div の `overflow-auto` を外す／親側を外す の選択と、`h-full` / `flex-1 min-h-0` の整合確認）。
- `key` の構成方法（文字列結合の区切り、`executionId` が無いActiveタブでの代替トークン）。
- 既存ヘッダー（アクションバー・承認UI・エラー表示）と新規ステータス表示の縦並び順、間仕切り（border）の扱い。
- テストケースの具体的な配置（`WorkflowTrace.test.tsx` への追加 vs フック単体テストファイル新設）。
- 自動追従ロジックの検証はカスタムフック単体（純粋ロジック・状態遷移）と末尾判定純粋関数の入出力テストを主とし、jsdom 上のDOMスクロール実測の網羅テストは行わない。これは後段の実装・レビューで過剰なテスト追加によるフレーキー化を防ぐためのガードレールである。
- 過去実行データ取得失敗時のエラー表示の具体的な日本語文言（テスト時のアサートはエラー表示要素の存在で行うため、文言自体は実装裁量とする）。
