# UI Review — スクリーンショット分析 → GitHub ISSUE 自動作成

既存のスクリーンショットをVisionで分析し、UI改善提案をGitHub ISSUEとして作成するスキル。

## 実行手順

以下のステップを順番に実行してください。

---

### Step 0: ラベル準備

```bash
gh label create "ui-improvement" --color "1d76db" --description "UI改善提案" 2>/dev/null || true
```

`ui-improvement` と `enhancement` ラベルが使えることを確認する。

---

### Step 1: マスクなしスクリーンショット撮影

UIレビュー用にマスクなしのスクリーンショットを撮影する。

```bash
UI_REVIEW=1 pnpm test:screenshots:update
```

- `UI_REVIEW=1` により `xtermMask` / `monacoMask` が無効化され、ターミナルやエディタ領域もマスクなしで撮影される
- **テスト失敗の場合**: エラー内容を報告し、以下を実行してスクリーンショットを復元してから終了
  ```bash
  git checkout -- tests/__screenshots__/
  ```
- **成功の場合**: Globツールで `tests/__screenshots__/chromium/*.png` を取得し、枚数を報告してStep 2に進む

**重要**: 分析完了後（Step 5の後）に必ず以下を実行してマスク付きスクリーンショットを復元する:

```bash
git checkout -- tests/__screenshots__/
```

---

### Step 2: バッチ分析

スクリーンショットを以下の7バッチに分割し、**順番に**分析する。各バッチでは、対象の全PNGファイルをReadツールで読み込み（Visionで画像として認識される）、分析する。

#### バッチ構成

| # | プレフィックス | 対象 |
|---|---------------|------|
| 1 | `worktree-editor-*` | エディタ画面全般 |
| 2 | `worktree-file-tree-*` | ファイルツリー |
| 3 | `worktree-source-control-*` + `worktree-dialog-*` | ソース管理 + ダイアログ |
| 4 | `worktree-search-*` + `worktree-pull-request-*` + `worktree-review-*` | 検索・PR・レビュー |
| 5 | `worktree-settings-*` | 設定画面 |
| 6 | `workspace-kanban-*` | カンバンボード |
| 7 | `workspace-issues-*` + `workspace-notion-*` + `workspace-remote-*` + その他の `workspace-*` | Issues・Notion・リモート等 |

#### 各バッチの分析手順

1. バッチ内の全PNGファイルをReadツールで**並列に**読み込む
2. 以下の観点で分析する:

**A. 個別画面の改善**
- 視覚的一貫性（フォント・間隔・色・アイコンの統一感）
- レイアウト（余白バランス・整列の正確さ）
- インタラクション（ボタンの視認性・クリック領域の適切さ）
- 状態表現（空状態・エラー状態・ローディング状態の適切さ）
- アクセシビリティ（コントラスト比・テキストサイズ・操作対象の大きさ）
- 情報設計（情報の優先順位・認知負荷の適切さ）

**B. ビジュアルデザイン**
- 配色（ダークテーマの色のバランス・コントラスト・アクセントカラーの効果的な使用）
- タイポグラフィ（フォントサイズの階層・ウェイトの使い分け・行間の適切さ）
- 洗練度（角丸・シャドウ・ボーダーの一貫性、モダンなデザインパターンとの乖離）
- 余白とリズム（要素間のスペーシングの一貫性・視覚的なリズム感）
- 視覚的階層（重要度に応じた強調・グルーピング・セクションの区別）
- 全体的な印象（プロフェッショナル感・洗練されたツールとしての見た目）

**C. コンポーネント共通化の候補（メモ）**
- 他のバッチで見た類似UIパターンを記録しておく
- 同じ目的のUIが画面ごとに微妙に異なっている箇所をメモする

3. バッチごとに **0〜3個** の改善点を抽出する。軽微な問題（ピクセル単位のズレ等）はスキップし、実装インパクトのある改善のみ抽出する。

4. 各改善点には以下を記録する:
   - 問題の概要（1-2文）
   - 該当スクリーンショットのファイル名（複数可）
   - 改善提案（具体的な実装方針）
   - 影響度（高/中/低）

---

### Step 2.5: 横断分析（コンポーネント共通化）

全バッチの分析完了後、メモした共通パターンを横断的に分析する。

検出すべきパターン:
- **同一パターンの重複実装**: 異なる画面で同じ見た目・機能のUI要素が個別に実装されている箇所（例: 空状態メッセージ、リスト表示、フィルタUI、エラー表示）
- **類似だが微妙に異なるUI**: 同じ目的のUIが画面ごとに少しずつ異なっている箇所（統一すべき候補）
- **共通コンポーネント化の提案**: 抽出可能な共通パターンと、それを共通コンポーネントにした場合の影響範囲

共通化の提案も0〜3個程度に絞る。

---

### Step 3: 整理・承認

#### 3-1: 重複排除

全改善点を一覧にし、内容が重複しているものを統合する。

#### 3-2: ISSUE一覧の提示

以下のフォーマットでユーザーに一覧を提示する:

```
## UI改善提案一覧

### 個別改善
1. **[高]** <タイトル> — <概要1文> (対象: <スクリーンショット名>)
2. **[中]** <タイトル> — <概要1文> (対象: <スクリーンショット名>)
...

### ビジュアルデザイン改善
1. **[高]** <タイトル> — <概要1文> (対象: <スクリーンショット名>)
...

### コンポーネント共通化
1. **[中]** <タイトル> — <概要1文> (対象: <スクリーンショット名>)
...

合計: N件のISSUEを作成します。
```

#### 3-3: ユーザー承認

AskUserQuestionツールで承認を取得する:
- 選択肢1: 「全件作成する」
- 選択肢2: 「選択して作成する」（番号指定を求める）
- 選択肢3: 「キャンセル」

「キャンセル」の場合はここで終了する。
「選択して作成する」の場合は、ユーザーが指定した番号のISSUEのみ作成する。

---

### Step 4: ISSUE作成

承認された各改善点について、以下の手順でISSUEを作成する。

#### 4-1: 重複チェック

作成前に既存ISSUEとの重複を確認する:

```bash
gh issue list --label "ui-improvement" --state open --limit 100 --json title -q '.[].title'
```

同一タイトルまたは非常に類似するタイトルのISSUEが既にある場合はスキップし、ユーザーに報告する。

#### 4-2: ISSUE作成

`gh issue create` で1件ずつ作成する。

**タイトル規則**:
- 個別改善: `UI: <動詞><対象><改善内容>`（60文字以内、日本語）
- ビジュアル改善: `UI/デザイン: <対象><改善内容>`（60文字以内、日本語）
- 共通化提案: `UI/共通化: <共通化対象パターン>を共通コンポーネント化する`

**本文フォーマット**:

```markdown
## 概要

<現状の問題を1-2文で説明>

## 現状のスクリーンショット

<!-- tests/__screenshots__/chromium/ 内の該当ファイルを表示 -->
| 画面 | スクリーンショット |
|------|-------------------|
| <画面名> | ![<画面名>](https://raw.githubusercontent.com/siro33950/releash/main/tests/__screenshots__/chromium/<ファイル名>) |

## 改善提案

<具体的な改善内容を箇条書きで記述。実装可能なレベルの具体性で書く>

## 影響範囲

- **対象コンポーネント**: `src/components/...`
- **影響度**: 高/中/低
- **分析元**: スクリーンショットVision分析

---
*このISSUEは `/ui-review` による自動分析で作成されました*
```

**作成コマンド**:

```bash
gh issue create \
  --title "<タイトル>" \
  --label "ui-improvement" \
  --label "enhancement" \
  --body "$(cat <<'EOF'
<本文>
EOF
)"
```

#### 4-3: エラーハンドリング

- 作成に失敗した場合、エラー内容を記録して次のISSUEに進む
- 最後に失敗分をまとめて報告する

---

### Step 5: サマリー報告

全ISSUE作成完了後、以下のサマリーを出力する:

```
## UI Review 完了

- 分析したスクリーンショット: N枚
- 作成したISSUE: M件
  - 個別改善: X件
  - ビジュアルデザイン改善: V件
  - コンポーネント共通化: Y件
- スキップ（重複）: Z件
- 失敗: W件

### 作成したISSUE
1. #<番号> <タイトル>
2. #<番号> <タイトル>
...
```

#### スクリーンショット復元

サマリー報告後、マスク付きスクリーンショットを復元する:

```bash
git checkout -- tests/__screenshots__/
```
